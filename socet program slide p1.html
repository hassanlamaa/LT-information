Slide 3

The InetAddress class

java.net.InetAddress is Java's representation of an IP address, both IPv4 (subclass Inet4Address) and IPv6 (subclass Inet6Address).

Key characteristics:

  • No public constructor: you obtain instances through static factory methods.
  • Immutable (its value never changes after creation), and therefore safe to share between threads.
  • Handles both hostname resolution (name → IP, using DNS) and IP address representation.

CreateInetAddress.java

import java.net.InetAddress;
import java.net.UnknownHostException;

public class CreateInetAddress {
    public static void main(String[] args) throws UnknownHostException {
        // Get local machine address
        InetAddress localHost = InetAddress.getLocalHost();

        // Resolve hostname to IP (performs a DNS lookup)
        InetAddress google = InetAddress.getByName("google.com");

        // Get all addresses for a host (IPv4 and IPv6)
        InetAddress[] allAddresses = InetAddress.getAllByName("www.google.com");

        // Create from IP string (no DNS lookup needed for a literal IP)
        InetAddress fromIP = InetAddress.getByName("8.8.8.8");

        System.out.println(localHost + " | " + google + " | "
                + allAddresses.length + " addresses | " + fromIP);
    }
}
Speaker notes

Demo opportunity: run the code live and ask students to predict the output first. Printing an InetAddress shows hostname/IP, for example google.com/142.250.185.78. For a literal IP the hostname part is empty: /8.8.8.8.

Important: InetAddress has no constructor; you call a static method instead. This design pattern is called a factory method. It lets Java return the right subclass (IPv4 or IPv6) and reuse cached lookups.

Discussion point: why is InetAddress immutable? Because it is shared: Java caches DNS results and hands the same object to many threads. If one thread could change it, every other thread would see a wrong address. Immutability gives thread safety and makes caching safe.

Common error: forgetting to handle UnknownHostException. It is a checked exception, so the code will not compile until you catch it or declare throws.

The InetAddress class

Q1In CreateInetAddress, the variable fromIP was created with getByName("8.8.8.8"). How does it appear in the printed line?

An InetAddress prints as hostname/IP, and for a literal IP the hostname part stays empty because no reverse lookup was done. dns.google/8.8.8.8 is tempting, but it appears only after getHostName() fills in the name.

Q2You delete throws UnknownHostException from main and add no try/catch. What happens?

Checked exceptions are enforced by the compiler, which is the "common error" in the notes. "Crashes only when DNS fails" is tempting because that would be true of an unchecked exception, but this code never gets that far.

Q3True or false: InetAddress objects are immutable, which makes them safe to cache and share between threads.

True. Java caches DNS results and hands the same object to many threads; if one thread could change it, others would see a wrong address.

InetAddressDemo.java (practical example)

import java.io.IOException;
import java.net.InetAddress;

public class InetAddressDemo {
    public static void main(String[] args) {
        try {
            InetAddress local = InetAddress.getLocalHost();
            System.out.println("Local Host: " + local);
            System.out.println("Host Name: " + local.getHostName());
            System.out.println("IP Address: " + local.getHostAddress());

            // Test reachability (ICMP needs admin/root rights on most systems)
            boolean reachable = local.isReachable(5000);
            System.out.println("Is reachable: " + reachable);
        } catch (IOException e) {   // also catches UnknownHostException
            e.printStackTrace();
        }
    }
}
Speaker notes

getByName() vs getAllByName(): use getByName() when you just need one address to connect to. Use getAllByName() when you want every address, for example to try the next one if the first fails, or to list IPv4 and IPv6 addresses.

Real-world scenario: large websites publish several IP addresses for the same hostname to spread load across servers (DNS load balancing), so getAllByName() often returns more than one result.

Warning: isReachable() may not work on all systems. It sends an ICMP echo ("ping") only if the program has the privilege to do so; otherwise it tries a TCP connection to port 7 (the echo port). Firewalls often block both, so false does not prove the host is down.

Exercise idea: write a program that lists all IP addresses of your university's website.

InetAddress: key methods

Q1Which method returns ALL IP addresses for a hostname?

getAllByName() returns an InetAddress[] with every address DNS gives (often several IPv4 and IPv6 addresses). getByName() returns only one; getHostAddress() just formats an address you already have as text.

Q2Which method never performs a DNS lookup?

getHostAddress() only formats the IP it already holds, such as "192.168.1.10". getHostName() is tempting because it only "returns" a value, but it may trigger a reverse DNS lookup.

Q3True or false: if isReachable(5000) returns false, the host is definitely down.

False. It needs privileges for ICMP, otherwise it tries TCP port 7, and firewalls often block both. A running host can still return false.

Slide 5

Socket programming basics

A socket is an endpoint for two-way communication between machines.

Key idea

Socket address = IP address + port number. Example: 192.168.1.10:8080 (IP:port). A TCP connection is identified by both ends: client IP:port and server IP:port.

Client socket

  • Initiates the connection to the server
  • Created with the remote IP and port
  • java.net.Socket class
  • Example: a web browser connecting to a website

Server socket

  • Listens for incoming connections
  • Binds to a specific port
  • java.net.ServerSocket class
  • Example: a web server waiting for requests
Speaker notes

Analogy: sockets are like electrical sockets: a standard point of connection. Once plugged in, data flows both ways.

Port numbers explained: the IP address is the building; the port is the apartment number. The IP gets the data to the right computer; the port gets it to the right program on that computer.

Port ranges: well-known 0–1023 (system services), registered 1024–49151, dynamic/ephemeral 49152–65535 (picked automatically for the client side of a connection).

Common ports to mention: 80 (HTTP), 443 (HTTPS), 22 (SSH), 25 (SMTP), 53 (DNS).

Visual aid: draw the client on the left, the server on the right, and the connection between their two sockets.

Socket programming basics

Q1Which class listens for incoming TCP connections?

ServerSocket binds to a port and its accept() method returns a new Socket for each client. DatagramSocket is for UDP, and NetworkSocket does not exist.

Q2In the socket address 192.168.1.10:8080, what does 8080 identify?

The IP finds the computer and the port finds the program on it: building and apartment number. "The host" is tempting, but that is what the IP part 192.168.1.10 does.

Q3Which port range is used for dynamic (ephemeral) client ports?

IANA defines 0–1023 as well-known (system services such as 80, 443, 22), 1024–49151 as registered, and 49152–65535 as dynamic/private ports picked automatically for clients. (Some operating systems use a slightly different ephemeral range by default.)

Slide 6

TCP vs UDP: choosing the right protocol

FeatureTCP (Transmission Control Protocol)UDP (User Datagram Protocol)
ConnectionConnection-oriented: requires a handshakeConnectionless: no handshake
ReliabilityReliable: lost data is retransmittedUnreliable: no delivery guarantee
OrderingIn-order deliveryNo ordering guarantee
ControlFlow control and congestion controlNo flow control
Data unitByte stream (no message boundaries)Datagrams (each message separate)
OverheadHigher overhead, more latencyLower overhead, lower latency
Java classesSocket, ServerSocketDatagramSocket, DatagramPacket
Use casesWeb (HTTP/1.1, HTTP/2), email, file transfer, SSHDNS, VoIP, gaming, live streaming, HTTP/3 (via QUIC)
Simple rule

Need reliability? Use TCP. Need low latency? Use UDP. Need both? Implement reliability on top of UDP. That is exactly what QUIC does, and HTTP/3 runs on QUIC over UDP.

Speaker notes

Real-world examples:

  • TCP: loading a web page. You need every byte, in order, or the page is broken.
  • UDP: a video call. It is better to skip a late frame than to freeze the call waiting for a retransmission.

Fun fact: DNS uses UDP for normal queries but falls back to TCP for large responses (and for zone transfers).

Update: "the web uses TCP" is no longer the whole story. HTTP/1.1 and HTTP/2 use TCP, but HTTP/3 (RFC 9114) uses QUIC, which runs over UDP and adds its own reliability and TLS 1.3 encryption.

Discussion: why would online games use UDP despite its unreliability? Because an old position update is useless once a newer one exists; waiting for a retransmission would only add lag.

TCP vs UDP: choosing the right protocol

Q1TCP is to UDP as ______ is to ______.

TCP guarantees delivery and order; UDP does not. "Fast / Slow" is backwards: UDP usually has lower latency because it skips the handshake and retransmissions.

Q2Which application fits UDP best?

For a call, a late frame is useless, so skipping it beats waiting for a retransmission. The others need every byte in order, which is TCP's job; a broken PDF or a missing SSH keystroke is not acceptable.

Q3True or false: HTTP always runs over TCP.

HTTP/1.1 and HTTP/2 use TCP, but HTTP/3 (RFC 9114) runs over QUIC, which is built on UDP and adds its own reliability and TLS 1.3 encryption.

Slide 7

How a TCP connection starts: the three-way handshake

  1. SYN: the client asks to open a connection and sends its starting sequence number.
  2. SYN-ACK: the server agrees, acknowledges the client's number and sends its own.
  3. ACK: the client acknowledges the server's number. Both sides now agree the connection is open.
Speaker notes

The handshake is why TCP is called connection-oriented: before any data moves, both sides agree on starting sequence numbers. Those numbers are what let TCP put data back in order and notice gaps to retransmit.

In Java you never send SYN yourself. The operating system does it. new Socket("localhost", 12345) returns only after the handshake succeeds; if nothing is listening on that port the server's OS replies with a reset and Java throws ConnectException: Connection refused.

Closing uses a separate exchange of FIN and ACK segments, one in each direction. UDP has no handshake at all, which is one reason it has lower latency.

How a TCP connection starts: the three-way handshake

Q1What is the correct order of the TCP three-way handshake?

The client sends SYN, the server answers SYN-ACK, the client confirms with ACK. FIN is used to close a connection; "hello/finished" messages belong to the TLS handshake, which runs after TCP's.

Q2A client runs new Socket("localhost", 12345) but nothing is listening on port 12345. What happens?

The server's operating system answers the SYN with a reset, and Java reports "Connection refused". UnknownHostException is tempting for any failure, but localhost resolves fine; the problem is the empty port.

Q3True or false: your Java code must build and send the SYN and ACK segments itself.

False. The operating system performs the handshake inside new Socket(...) and accept(). Java code only sees a connected socket, or an exception.

Slide 8

TCP socket programming in Java

Two key classes: Socket (client, and each accepted connection on the server) and ServerSocket (server, listening).

TCP connection lifecycle (fragment, server and client shown together)

// Server side
try (ServerSocket serverSocket = new ServerSocket(12345);
     Socket clientSocket = serverSocket.accept()) {   // waits here
    // talk to the client via clientSocket.getInputStream() / getOutputStream()
}   // both sockets are closed automatically here

// Client side (another program)
try (Socket socket = new Socket("localhost", 12345)) {
    // both sides can now communicate via:
    // socket.getInputStream()
    // socket.getOutputStream()
}   // socket closed automatically, even if an exception was thrown

Important notes:

  • ServerSocket.accept() blocks until a client connects.
  • Each client connection creates a new Socket instance on the server.
  • Always close sockets: use try-with-resources (preferred since Java 7) rather than a manual finally block.
  • Handle exceptions: UnknownHostException, IOException, SocketException.
Speaker notes

Blocking nature: accept() and read() block (pause) the thread until something happens. A server with one thread can therefore serve only one client at a time, which is why real servers use multiple threads (slide 9) or virtual threads (slide 12).

Resource management: always close sockets. Every open socket holds an operating-system file descriptor and a port; if you forget, a long-running server eventually fails with "Too many open files". try-with-resources closes them for you, even when an exception is thrown.

Demo: run an echo server and client side by side and type messages to show communication in real time.

Common mistake: not flushing output streams, so data stays in the buffer and the other side waits forever. Use new PrintWriter(..., true) (auto-flush on println) or call flush().

TCP socket programming in Java

Q1What does serverSocket.accept() do?

accept() blocks (waits) until the handshake with a client completes, then returns a dedicated Socket. The client initiates the handshake, not the server, and reading data is a separate step.

Q2In the server fragment, when are serverSocket and clientSocket closed?

Both are declared in the try-with-resources header, so Java closes them in reverse order however the block ends. The finally option is tempting because it was the old pattern, but try-with-resources replaces it.

Q3Why is try-with-resources preferred for sockets?

Resources declared in try (...) are closed automatically, in reverse order, however the block ends. This prevents leaked sockets and file descriptors. It does not retry, and the compiler does not force it.

Slide 9

Complete TCP example: echo server and client

EchoServer.java

import java.io.BufferedReader;
import java.io.IOException;
import java.io.InputStreamReader;
import java.io.OutputStreamWriter;
import java.io.PrintWriter;
import java.net.ServerSocket;
import java.net.Socket;
import java.nio.charset.StandardCharsets;

public class EchoServer {
    public static void main(String[] args) throws IOException {
        try (ServerSocket serverSocket = new ServerSocket(12345)) {
            System.out.println("Echo Server started on port 12345");
            while (true) {
                Socket clientSocket = serverSocket.accept();
                System.out.println("Client connected: " + clientSocket.getInetAddress());
                // Handle each client in a new thread so many clients can connect
                new Thread(() -> handleClient(clientSocket)).start();
            }
        }
    }

    private static void handleClient(Socket socket) {
        try (socket;   // Java 9+: closes the socket when done
             BufferedReader in = new BufferedReader(new InputStreamReader(
                     socket.getInputStream(), StandardCharsets.UTF_8));
             PrintWriter out = new PrintWriter(new OutputStreamWriter(
                     socket.getOutputStream(), StandardCharsets.UTF_8), true)) {
            String inputLine;
            while ((inputLine = in.readLine()) != null) {
                System.out.println("Received: " + inputLine);
                out.println("Echo: " + inputLine);
            }
        } catch (IOException e) {
            System.err.println("Error handling client: " + e.getMessage());
        }
    }
}

EchoClient.java

import java.io.BufferedReader;
import java.io.IOException;
import java.io.InputStreamReader;
import java.io.OutputStreamWriter;
import java.io.PrintWriter;
import java.net.Socket;
import java.nio.charset.StandardCharsets;

public class EchoClient {
    public static void main(String[] args) throws IOException {
        try (Socket socket = new Socket("localhost", 12345);
             BufferedReader in = new BufferedReader(new InputStreamReader(
                     socket.getInputStream(), StandardCharsets.UTF_8));
             PrintWriter out = new PrintWriter(new OutputStreamWriter(
                     socket.getOutputStream(), StandardCharsets.UTF_8), true);
             BufferedReader keyboard = new BufferedReader(new InputStreamReader(
                     System.in, StandardCharsets.UTF_8))) {
            System.out.println("Connected. Type a line (Ctrl+D / Ctrl+Z to quit):");
            String line;
            while ((line = keyboard.readLine()) != null) {
                out.println(line);                  // send (auto-flushed)
                System.out.println(in.readLine());  // wait for "Echo: ..."
            }
        }
    }
}

Key features shown: multi-threaded server (handles multiple clients) · proper resource management with try-with-resources · explicit UTF-8 encoding · clean separation of concerns (accept loop vs per-client handler).

Run it

Terminal 1: java EchoServer.java. Terminal 2: java EchoClient.java, then type hello and see Echo: hello. (Java 11+ can run a single source file directly.)

Speaker notes

Multi-threading importance: without a thread per client, the server would be stuck inside one client's readLine() loop and could not accept() anyone else.

Try-with-resources: show how it automatically closes sockets and streams in reverse order, even if an exception is thrown. The server socket itself is also in a try-with-resources block, so it is closed if accept() fails.

Encoding: InputStreamReader without a charset uses the platform default, which differs between machines (Java 18+ defaults to UTF-8, older versions do not). Always pass StandardCharsets.UTF_8 so Arabic, French accents and emoji survive the trip.

Security note: real servers need input validation and size limits (for example a maximum line length and a read timeout) to prevent denial-of-service attacks where a client sends endless data or never sends anything.

Extension ideas: add logging, timeout handling (setSoTimeout), or protocol commands such as QUIT.

Complete TCP example: echo server and client

Q1The client types hello. What does the client's window print?

The server answers out.println("Echo: " + inputLine) and the client prints that reply. Received: hello is tempting, but it is printed on the server's console, not sent to the client.

Q2In handleClient, when does the while ((inputLine = in.readLine()) != null) loop end?

null means end of stream: the client closed (for example with Ctrl+D or Ctrl+Z). An empty line is tempting, but that is "", which is not null, so the loop echoes it and continues. This code sets no timeout.

Q3True or false: if you replace new Thread(() -> handleClient(clientSocket)).start() with a direct call handleClient(clientSocket), the server still serves two clients at once.

False. The main thread would sit in the first client's readLine() loop and never return to accept() until that client leaves.

Slide 10

UDP in Java: DatagramSocket and DatagramPacket

With UDP there is no connection and no stream. You put bytes into a DatagramPacket, address it, and send() it through a DatagramSocket. The receiver calls receive(), which blocks until one whole datagram arrives.

UdpEchoServer.java

import java.io.IOException;
import java.net.DatagramPacket;
import java.net.DatagramSocket;
import java.nio.charset.StandardCharsets;

public class UdpEchoServer {
    public static void main(String[] args) throws IOException {
        try (DatagramSocket socket = new DatagramSocket(9876)) {
            System.out.println("UDP echo server on port 9876");
            byte[] buf = new byte[1024];
            while (true) {
                DatagramPacket request = new DatagramPacket(buf, buf.length);
                socket.receive(request);   // blocks until a datagram arrives
                String text = new String(request.getData(), 0, request.getLength(),
                        StandardCharsets.UTF_8);
                byte[] reply = ("Echo: " + text).getBytes(StandardCharsets.UTF_8);
                // Reply to whoever sent the request (address and port are in the packet)
                socket.send(new DatagramPacket(reply, reply.length,
                        request.getAddress(), request.getPort()));
            }
        }
    }
}

UdpEchoClient.java

import java.io.IOException;
import java.net.DatagramPacket;
import java.net.DatagramSocket;
import java.net.InetAddress;
import java.net.SocketTimeoutException;
import java.nio.charset.StandardCharsets;

public class UdpEchoClient {
    public static void main(String[] args) throws IOException {
        try (DatagramSocket socket = new DatagramSocket()) {   // any free local port
            socket.setSoTimeout(2000);                         // wait at most 2 s for a reply
            InetAddress server = InetAddress.getByName("localhost");
            byte[] data = "Hello UDP".getBytes(StandardCharsets.UTF_8);
            socket.send(new DatagramPacket(data, data.length, server, 9876));

            byte[] buf = new byte[1024];
            DatagramPacket reply = new DatagramPacket(buf, buf.length);
            try {
                socket.receive(reply);
                System.out.println(new String(reply.getData(), 0, reply.getLength(),
                        StandardCharsets.UTF_8));
            } catch (SocketTimeoutException e) {
                System.out.println("No reply within 2 s: the request or the reply was lost.");
            }
        }
    }
}
Common mistake

Using new String(packet.getData()) without 0, packet.getLength(). The buffer is 1024 bytes, but the datagram may be 9; without the length you print the leftover bytes too.

Speaker notes

Compare this with the TCP echo pair: there is no accept(), no streams and no ServerSocket. One DatagramSocket on the server talks to every client, because each packet carries the sender's address and port.

Because UDP can lose packets, the client sets a timeout with setSoTimeout; otherwise receive() could wait forever. A real UDP application decides what to do on timeout: retry, skip, or report an error. That decision is "reliability on top of UDP".

Each datagram is a separate message: if the client sends "A" then "B", the server receives two packets, possibly in the order B, A, or only one of them.

UDP in Java: DatagramSocket and DatagramPacket

Q1Which Java classes do you use for UDP?

UDP sends independent datagrams: you fill a DatagramPacket and send it with a DatagramSocket. Socket/ServerSocket are TCP.

Q2How does UdpEchoServer know where to send each reply?

UDP has no connection, so the reply goes back to the address stored in the received packet. accept() is tempting from the TCP version, but DatagramSocket has no accept() at all.

Q3The client sends Hello UDP (9 bytes). The server decodes with new String(request.getData(), StandardCharsets.UTF_8), without the length. What is the result?

getData() returns the whole buffer, not just the received bytes, so the string is 1024 characters long. "Exactly Hello UDP" is tempting; you get that only with 0, request.getLength().

Slide 11

Network exception handling

Network operations can fail in many ways: always handle exceptions.

UnknownHostException

The hostname cannot be resolved to an IP address (DNS failure or typo).

ConnectException

Connection refused by the remote host (nothing listening on that port, or a firewall rejected it).

SocketTimeoutException

A connect or read timeout expired.

RobustClient.java (best practice: robust error handling)

import java.io.BufferedReader;
import java.io.IOException;
import java.io.InputStreamReader;
import java.io.OutputStreamWriter;
import java.io.PrintWriter;
import java.net.ConnectException;
import java.net.InetAddress;
import java.net.InetSocketAddress;
import java.net.Socket;
import java.net.SocketTimeoutException;
import java.net.UnknownHostException;
import java.nio.charset.StandardCharsets;

public class RobustClient {
    public static void main(String[] args) {
        try (Socket socket = new Socket()) {           // closed automatically
            InetAddress address = InetAddress.getByName("example.com");
            socket.connect(new InetSocketAddress(address, 80), 5000); // 5 s CONNECT timeout
            socket.setSoTimeout(5000);                                // 5 s READ timeout

            PrintWriter out = new PrintWriter(new OutputStreamWriter(
                    socket.getOutputStream(), StandardCharsets.UTF_8));
            BufferedReader in = new BufferedReader(new InputStreamReader(
                    socket.getInputStream(), StandardCharsets.UTF_8));
            out.print("HEAD / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n");
            out.flush();
            System.out.println("Server says: " + in.readLine());  // e.g. HTTP/1.1 200 OK
        } catch (UnknownHostException e) {
            System.err.println("Cannot resolve hostname: " + e.getMessage());
            // Suggest checking network/DNS
        } catch (SocketTimeoutException e) {
            System.err.println("Connection or read timed out");
            // Retry logic or notify user
        } catch (ConnectException e) {
            System.err.println("Connection refused: is the server running?");
        } catch (IOException e) {
            System.err.println("Network error: " + e.getMessage());
            // General network failure
        }
        // No finally needed: try-with-resources already closed the socket
    }
}
Correction

setSoTimeout(ms) is a read timeout: it limits how long read()/readLine() waits. It does not limit connecting. To limit the connection attempt, create an unconnected Socket and call connect(new InetSocketAddress(host, port), ms). new Socket(host, port) uses the operating system's default connect timeout, which can be over a minute.

Exam tip

Catch order matters: catch specific exceptions before IOException. UnknownHostException, SocketTimeoutException and ConnectException are all subclasses of IOException; if catch (IOException e) came first, the later blocks would be unreachable and the code would not compile.

Speaker notes

Importance of timeouts: without timeouts, clients can hang indefinitely, for example when a server accepts the connection and then never answers.

Recovery strategies: retry (with a growing delay between attempts), switch to a fallback server, or show cached previous results.

User experience: do not just print stack traces; give user-friendly messages such as "Cannot reach the server. Check your connection."

Real-world scenario: mobile apps must handle network drops gracefully when the phone switches from Wi-Fi to mobile data.

Network exception handling

Q1What exception is thrown for unresolved hostnames?

java.net.UnknownHostException (a subclass of IOException) is thrown when DNS cannot resolve the name. NetworkException and ResolutionException do not exist in java.net.

Q2What does socket.setSoTimeout(5000) limit?

setSoTimeout is a read timeout. To limit connecting, use socket.connect(new InetSocketAddress(host, port), ms). Nothing closes the socket automatically; your code decides what to do when the exception is thrown.

Q3In RobustClient, what happens if you move catch (IOException e) to be the first catch block?

Catch blocks are checked in order, and IOException is the parent of UnknownHostException, SocketTimeoutException and ConnectException. "Java picks the most specific" is tempting, but it does not reorder catches; it rejects the code.

Modern Java: virtual threads and HttpClient

Many clients: one platform thread per client (slide 9) works, but each platform thread is an operating-system thread with its own large stack, so thousands of clients become expensive. Java 21 added virtual threads: you keep the simple blocking style, and the JVM runs huge numbers of them on a few OS threads.

VirtualThreadEchoServer.java (Java 21+)

import java.io.BufferedReader;
import java.io.IOException;
import java.io.InputStreamReader;
import java.io.OutputStreamWriter;
import java.io.PrintWriter;
import java.net.ServerSocket;
import java.net.Socket;
import java.nio.charset.StandardCharsets;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class VirtualThreadEchoServer {
    public static void main(String[] args) throws IOException {
        try (ServerSocket server = new ServerSocket(12345);
             ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) {
            while (true) {
                Socket client = server.accept();
                pool.submit(() -> handle(client));   // one cheap virtual thread per client
            }
        }
    }

    static void handle(Socket socket) {
        try (socket;
             BufferedReader in = new BufferedReader(new InputStreamReader(
                     socket.getInputStream(), StandardCharsets.UTF_8));
             PrintWriter out = new PrintWriter(new OutputStreamWriter(
                     socket.getOutputStream(), StandardCharsets.UTF_8), true)) {
            String line;
            while ((line = in.readLine()) != null) {
                out.println("Echo: " + line);
            }
        } catch (IOException e) {
            System.err.println("Client error: " + e.getMessage());
        }
    }
}

Talking HTTP: you can speak HTTP over a raw Socket (slide 11), but for real code use java.net.http.HttpClient (Java 11+). It supports HTTP/1.1 and HTTP/2, HTTPS, timeouts, and async requests.

HttpClientDemo.java (Java 11+)

import java.io.IOException;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.time.Duration;

public class HttpClientDemo {
    public static void main(String[] args) throws IOException, InterruptedException {
        HttpClient client = HttpClient.newBuilder()
                .connectTimeout(Duration.ofSeconds(5))
                .build();
        HttpRequest request = HttpRequest.newBuilder(URI.create("https://example.com/"))
                .timeout(Duration.ofSeconds(10))
                .GET()
                .build();
        HttpResponse<String> response = client.send(request, HttpResponse.BodyHandlers.ofString());
        System.out.println("Status: " + response.statusCode());
        System.out.println("Protocol: " + response.version());   // HTTP_1_1 or HTTP_2
    }
}
Outdated code to avoid

new URL("https://...") is deprecated since Java 20. Use URI.create("https://..."), and call .toURL() on it if an older API needs a URL.

Speaker notes

Think of platform threads as full-time employees (expensive, limited number) and virtual threads as tasks on a to-do list that a few employees pick up whenever another task is waiting. When a virtual thread blocks in readLine(), the JVM parks it and uses the OS thread for someone else.

The alternative for very high performance is NIO (java.nio.channels: Selector, SocketChannel), where one thread watches many connections. NIO is powerful but harder to write; virtual threads give most of the benefit with the simple code you already know.

ExecutorService is AutoCloseable since Java 19, which is why it can sit in the try-with-resources header.

Modern Java: virtual threads and HttpClient

Q1A server must handle 10,000 mostly idle clients with simple blocking code. Which Java 21 feature fits best?

Virtual threads are cheap, so one per client scales to many thousands while keeping blocking code. 10,000 platform threads would cost a lot of memory; no threads would serve one client at a time; switching to UDP changes the protocol, not the threading problem.

Q2Which is the modern replacement for new URL("https://example.com") (deprecated since Java 20)?

Build a URI first (it validates the syntax) and convert with toURL() when an older API needs a URL; HttpClient takes the URI directly. InetAddress and Socket expect a hostname, not a URL with a scheme, and URL.parse is not a standard Java method.

Q3True or false: ExecutorService can be declared in the try-with-resources header because it is AutoCloseable since Java 19.

True. Closing the executor waits for its submitted tasks to finish. On older Java versions you had to call shutdown() yourself.

Practical applications and best practices

Where you will use these skills:

  • Web servers: HTTP servers, REST APIs
  • Chat applications: real-time messaging
  • File transfer: FTP/SFTP clients and servers
  • Monitoring tools: network diagnostics
  • IoT devices: smart device communication

Best practices

  • Always close resources, using try-with-resources (it replaces the old finally pattern)
  • Use timeouts to prevent hanging (connect timeout and read timeout)
  • Validate all network input, and limit its size
  • Log network events for debugging
  • Handle exceptions gracefully
  • Use TLS (SSLSocket or HTTPS) for anything sensitive

Common pitfalls

  • Forgetting to flush output streams
  • Blocking the UI thread with network calls
  • Not handling partial reads/writes
  • Ignoring character encoding issues (always state UTF-8)
  • Hardcoding port numbers
Speaker notes

Career relevance: these skills are needed for backend development, DevOps, and full-stack roles; even if you later use frameworks, they are built on exactly these sockets.

Security emphasis: network code is exposed to anyone who can reach the port, so it is a target for attacks. Always validate input and never trust what the other side sends.

Partial reads: TCP is a byte stream, so one write of 1000 bytes may arrive as two reads of 600 and 400. Your protocol needs a way to mark message ends (a newline, as in our echo server, or a length prefix).

Next steps: NIO (non-blocking I/O) for high-performance servers, and virtual threads (Java 21) for simple code that still scales.

Final thought: "The internet runs on sockets; now you know how to build it."

Practical applications and best practices

Q1Why must the TCP client call flush() (or use an auto-flushing PrintWriter)?

Writers buffer output for efficiency. Until the buffer fills or is flushed, nothing is sent. new PrintWriter(out, true) flushes on every println.

Q2A client sends 1000 bytes with one write, and the server's first read returns only 600 bytes. What is going on?

TCP keeps no message boundaries, so a protocol uses a newline or a length prefix. "Data was lost" is tempting, but TCP is reliable: the rest arrives, just in a separate read.

Q3True or false: making network calls on the UI thread is fine as long as you set a timeout.

False. Even with a timeout, the interface freezes for as long as the call blocks, which is listed as a common pitfall. Run network calls on another thread.

Final review: mixed questions from the whole deck

Q1What is the right order to create a client socket with both timeouts?

That is what RobustClient does: connect with a time limit, then set the read timeout. The first option is tempting, but new Socket(host, port) is already connected, so a later connect fails.

Q2True or false: on a UDP server, one DatagramSocket can talk to every client.

True. There is no per-client socket as with TCP's accept(); each packet carries the sender's address and port, and the server replies to it.

Q3Which pairing of "waits for the other side" calls is correct?

A TCP server blocks in accept() for connections; a UDP server blocks in receive() for single datagrams. The first option is the same pair swapped, which is the tempting confusion.

Q4Why do the deck's examples pass StandardCharsets.UTF_8 to every reader and writer?

If the two sides use different default encodings, Arabic, French accents and emoji get garbled. It does not encrypt anything; for that you need TLS.

Q5True or false: socket.setSoTimeout(5000) also limits how long new Socket(host, port) may take to connect.

False. setSoTimeout is a read timeout. new Socket(host, port) uses the OS default connect timeout, which can be over a minute; use connect(address, ms) instead.

Q6Which of these is a best practice from this deck?

Network code is reachable by anyone who can reach the port, so input must be validated and size-limited. "Use SSL" is tempting, but SSL 3.0 is insecure; today use TLS 1.2 or 1.3 (SSLSocket or HTTPS).

Summary

  • InetAddress represents an IP address; get one with getLocalHost(), getByName() or getAllByName(), and handle UnknownHostException.
  • A socket endpoint is IP + port. TCP (Socket/ServerSocket) is connection-oriented, reliable and ordered; UDP (DatagramSocket/DatagramPacket) is connectionless and faster but unreliable.
  • TCP connections start with the SYN, SYN-ACK, ACK handshake, which Java performs inside new Socket() and accept().
  • Close everything with try-with-resources, state UTF-8 explicitly, flush output, and set both a connect timeout and a read timeout (setSoTimeout).
  • Serve many clients with a thread per client, preferably virtual threads (Java 21); use HttpClient (Java 11+) for HTTP and URI instead of the deprecated new URL(String).
