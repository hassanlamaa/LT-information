What is client/server?

Client/server is a network model in which each program is either a client or a server. A client requests a service; a server provides it. Clients rely on servers for resources such as files, devices (printers, storage) and processing power.

  • Clients: PCs and workstations running user applications, and today also phones, browsers, apps and IoT devices.
  • Servers: computers that store and manage shared files and applications. Usually more powerful and always on, but the word describes a role: a single physical machine can host dozens of virtual servers, and one program can be a server to some programs and a client of others (a web application server is a client of the database server).
Analogy

A library. Readers (clients) come to the desk and ask for a book. The librarian (server) checks the catalogue, fetches the book and hands it over. Readers never go into the stacks themselves, and the library decides who may borrow what. If the only librarian goes home sick, nobody gets a book: that is the single point of failure.

The communication pattern

Clients and servers exchange messages using a request-response pattern. The two programs are separate processes, usually on separate machines, so they need Inter-Process Communication (IPC). Across a network, IPC almost always means sockets (section 3). Both sides must use a common protocol, and the server uses a scheduling system to handle many client requests at the same time.

Key idea

The client initiates, the server listens and responds. The server must be running and reachable at a known address and port before any client can connect.

Advantages and disadvantages, explained

Advantages

  • Centralised management: one place to back up, patch and audit.
  • Scalability: clients can be added easily; server capacity can grow by upgrading (scale up) or adding servers behind a load balancer (scale out).
  • Enhanced data sharing: everyone works on the same up-to-date data instead of private copies.
  • Improved security: authentication and permissions are enforced centrally.

Disadvantages

  • Server cost: hardware or cloud bills, licences, administrators.
  • Complex configuration: network, DNS, firewall, certificates and services must all be right.
  • Single point of failure: one server down means everyone is down, unless you add redundancy (clusters, replicas, failover).
  • Traffic congestion: many simultaneous requests can saturate the server or its network link (a denial-of-service attack exploits exactly this).

Basic client/server template in Java

The two programs below are the skeleton of almost every TCP service. The server opens a ServerSocket, loops on accept(), and gives each connection its own thread. The client connects, sends lines typed by the user, and prints each reply.

BasicServer.java: basic server structure

import java.io.*;
import java.net.*;

public class BasicServer {
    private ServerSocket serverSocket;

    public BasicServer(int port) {
        try {
            serverSocket = new ServerSocket(port);
            System.out.println("Server started on port " + port);
        } catch (IOException e) {
            System.err.println("Could not start server: " + e.getMessage());
        }
    }

    public void start() {
        while (true) {
            try {
                // Wait for client connection
                Socket clientSocket = serverSocket.accept();
                System.out.println("Client connected: " + clientSocket.getInetAddress());

                // Handle client request in a new thread
                ClientHandler handler = new ClientHandler(clientSocket);
                new Thread(handler).start();
            } catch (IOException e) {
                System.err.println("Error accepting client: " + e.getMessage());
            }
        }
    }

    // Inner class to handle client requests
    private static class ClientHandler implements Runnable {
        private Socket clientSocket;

        public ClientHandler(Socket socket) {
            this.clientSocket = socket;
        }

        @Override
        public void run() {
            try (
                BufferedReader in = new BufferedReader(
                    new InputStreamReader(clientSocket.getInputStream()));
                PrintWriter out = new PrintWriter(clientSocket.getOutputStream(), true)
            ) {
                String inputLine;
                while ((inputLine = in.readLine()) != null) {
                    // Process client request
                    String response = processRequest(inputLine);
                    out.println(response);
                }
            } catch (IOException e) {
                System.err.println("Error handling client: " + e.getMessage());
            } finally {
                try {
                    clientSocket.close();
                } catch (IOException e) {
                    System.err.println("Error closing socket: " + e.getMessage());
                }
            }
        }

        private String processRequest(String request) {
            // Implement your request processing logic here
            return "Processed: " + request;
        }
    }

    public static void main(String[] args) {
        BasicServer server = new BasicServer(8080);
        server.start();
    }
}

BasicClient.java: basic client structure

import java.io.*;
import java.net.*;

public class BasicClient {
    private String host;
    private int port;

    public BasicClient(String host, int port) {
        this.host = host;
        this.port = port;
    }

    public void connect() {
        try (
            Socket socket = new Socket(host, port);
            PrintWriter out = new PrintWriter(socket.getOutputStream(), true);
            BufferedReader in = new BufferedReader(
                new InputStreamReader(socket.getInputStream()));
            BufferedReader stdIn = new BufferedReader(
                new InputStreamReader(System.in))
        ) {
            System.out.println("Connected to server " + host + ":" + port);

            String userInput;
            while ((userInput = stdIn.readLine()) != null) {
                // Send request to server
                out.println(userInput);

                // Get response from server
                String response = in.readLine();
                System.out.println("Server response: " + response);

                if ("exit".equalsIgnoreCase(userInput)) {
                    break;
                }
            }
        } catch (UnknownHostException e) {
            System.err.println("Unknown host: " + host);
        } catch (IOException e) {
            System.err.println("I/O error: " + e.getMessage());
        }
    }

    public static void main(String[] args) {
        BasicClient client = new BasicClient("localhost", 8080);
        client.connect();
    }
}
  1. Bind: new ServerSocket(8080) reserves port 8080 and starts listening.
  2. Accept: accept() blocks until a client connects, then returns a new Socket just for that client.
  3. Hand off: a new thread runs ClientHandler, so the main loop can go straight back to accept().
  4. Talk: both sides wrap the socket streams in a reader and writer and exchange text lines. PrintWriter(..., true) turns on auto-flush, so each println is sent immediately.
  5. Close: try-with-resources closes the streams; the finally block closes the socket.
Common mistake

Forgetting autoFlush (the true in new PrintWriter(out, true)). Without it the reply waits in a buffer, the client's readLine() waits forever, and the program looks frozen.

Tip

If new ServerSocket(port) fails (for example "Address already in use"), this template prints an error but start() then crashes with a NullPointerException. In real code, let the constructor throw the IOException instead of swallowing it.

Quiz: foundations

Q1What does serverSocket.accept() return?

accept() blocks until a client connects and then returns a dedicated Socket for talking to it. The ServerSocket itself only listens for new connections.

Q2True or false: one program can be a server to some programs and a client of others.

True. A web application server serves browsers but is itself a client of the database server. Client and server are roles in a particular conversation.

Q3Why does BasicServer start a new thread for each client?

Without threads, the server would serve one client at a time: a slow client would block everybody. This is the "scheduling system" the course mentions.

Q4Which technique reduces the "single point of failure" disadvantage?

Redundancy means another server takes over if one fails. Giving each client a private copy would destroy the main benefit (shared, consistent data), and the transport protocol does not change server availability.

Fat client vs fat server

Fat client: more functions run on the client side, and the client knows how the data is organised (table names, columns). Fat server: more functions run on the server side; the client only calls services, which makes the system easier to manage and deploy. A thin client is the extreme of a fat server: a browser that only displays what the server sends.

2-tier, 3-tier and N-tier

Every application has three logical jobs: presentation (show data, collect input), business logic (rules, calculations, validation) and data management (store and retrieve). A tier is a place where some of these jobs run.

  • 2-tier: Client + Database Server. Presentation and logic on the client; data on the server.
  • 3-tier: Client + Application Server + Database Server. Each job has its own tier.
  • N-tier: the extended architecture with specialised components: a load balancer, several web or application servers, caches, message queues, separate microservices, and so on.

2-tier vs 3-tier comparison

Feature2-Tier3-Tier
System administrationMore logic on the client to manageCentrally managed on the server
PerformancePoor (many SQL statements over the network)Good (only service requests and responses)
ScalabilityPoor / low (each client holds a database connection)Excellent (distribute load across servers; pool connections)
Application reusePoor (application lives on the client)Excellent (reuse services and objects)
SecurityDatabase exposed to every clientOnly the app server reaches the database
Ease of developmentHigh (simple)More complex
Example

A university registration system. 2-tier version: a desktop program on each secretary's PC sends SQL straight to the database; changing a fee rule means reinstalling the program everywhere. 3-tier version: staff and students use a browser; the rules live in one application server; the database is reachable only from that server. N-tier version: during registration week a load balancer spreads students over four application servers and a cache keeps the course list in memory.

Common mistake

Mixing up layers and tiers. Layers are a logical split of the code (UI classes, service classes, data-access classes). Tiers are a physical split across machines or processes. A 3-layer program can still run as a single tier on one PC.

Exam tip

For "advantages of 3-tier", give at least four from the table and justify each one: central administration, better performance over the network, scalability, reuse, and security (the database is not exposed). Mention the cost: more complex development.

Multi-threaded server with a thread pool

Creating a brand-new thread for every client (as in section 1) is simple, but thousands of clients would mean thousands of threads. A thread pool reuses a fixed number of threads, which puts a ceiling on resource use.

MultiThreadedServer.java: handling multiple clients concurrently

import java.io.*;
import java.net.*;
import java.util.concurrent.*;

public class MultiThreadedServer {
    private ServerSocket serverSocket;
    private ExecutorService threadPool;

    public MultiThreadedServer(int port, int poolSize) {
        try {
            serverSocket = new ServerSocket(port);
            threadPool = Executors.newFixedThreadPool(poolSize);
            System.out.println("Multi-threaded server started on port " + port);
        } catch (IOException e) {
            System.err.println("Could not start server: " + e.getMessage());
        }
    }

    public void start() {
        while (true) {
            try {
                Socket clientSocket = serverSocket.accept();
                System.out.println("New client connected: " + clientSocket.getInetAddress());

                // Submit client handling to thread pool
                threadPool.submit(new ClientHandler(clientSocket));
            } catch (IOException e) {
                System.err.println("Error accepting client: " + e.getMessage());
            }
        }
    }

    private static class ClientHandler implements Runnable {
        private Socket clientSocket;

        public ClientHandler(Socket socket) {
            this.clientSocket = socket;
        }

        @Override
        public void run() {
            try (
                BufferedReader in = new BufferedReader(
                    new InputStreamReader(clientSocket.getInputStream()));
                PrintWriter out = new PrintWriter(clientSocket.getOutputStream(), true)
            ) {
                String inputLine;
                while ((inputLine = in.readLine()) != null) {
                    System.out.println("Received from " + clientSocket.getInetAddress() + ": " + inputLine);

                    // Echo back the message
                    out.println("Echo: " + inputLine);

                    if ("bye".equalsIgnoreCase(inputLine)) {
                        break;
                    }
                }
            } catch (IOException e) {
                System.err.println("Error handling client: " + e.getMessage());
            } finally {
                try {
                    clientSocket.close();
                    System.out.println("Client disconnected: " + clientSocket.getInetAddress());
                } catch (IOException e) {
                    System.err.println("Error closing socket: " + e.getMessage());
                }
            }
        }
    }

    public static void main(String[] args) {
        MultiThreadedServer server = new MultiThreadedServer(8080, 10);
        server.start();
    }
}

Explanation: this server uses a thread pool to handle multiple clients concurrently. Each client connection is processed by one of the pool's threads, so the server serves several clients at once without blocking. With a pool of 10, the 11th client waits in the pool's queue until a thread is free.

StrategyHowGood forWatch out for
Thread per clientnew Thread(handler).start()Teaching, few clientsMemory use grows with every client
Fixed thread poolExecutors.newFixedThreadPool(n)Predictable loadClients queue when all n threads are busy
Virtual threads (Java 21+)Executors.newVirtualThreadPerTaskExecutor()Many thousands of mostly-waiting connectionsRequires Java 21 or later
Updated for modern Java

Since Java 21, virtual threads make the simple thread-per-client style scale again. Change one line, threadPool = Executors.newVirtualThreadPerTaskExecutor();, and every client gets its own cheap virtual thread.

Quiz: server types and tiers

Q1Which design is easiest to update when a business rule changes?

With a fat server the rule lives in one place, so you deploy once. With a fat client every installed copy must be updated.

Q2A web application server differs from a plain web server because it:

A web server can serve static files on its own. A web application server (Tomcat, Node.js) executes code per request to build the response, for example a page listing your own orders.

Q3True or false: a program split into UI, service and data-access classes is automatically a 3-tier system.

False. That is three logical layers. It is only 3-tier when those parts run as separate tiers (processes or machines), such as browser, application server and database server.

Q4In MultiThreadedServer with a pool of 10 threads, what happens to the 11th simultaneous client?

newFixedThreadPool keeps exactly n threads and an unbounded queue. The connection is accepted, but the handler only runs when one of the 10 threads finishes.

3Core Communication Technologies

Sockets and ports

Sockets provide the communication mechanism between two computers using IP addresses and ports. A socket is one end of a connection; a TCP connection is uniquely identified by four values: client IP, client port, server IP, server port. That is how a web server on port 443 can keep thousands of connections apart: each one has a different client IP/port pair.

Analogy

A phone call. The IP address is the phone number of a company, the port is the extension (sales = 80, support = 443). A socket is the handset at each end once the call is connected.

TCP vs UDP

TCP is connection-oriented, reliable and gives ordered delivery. Before any data flows, the two sides perform a three-way handshake; afterwards every segment is numbered and acknowledged, and lost segments are retransmitted. UDP is connectionless and faster, with no delivery guarantees: each datagram is sent on its own. UDP is used for voice, video, DNS and DHCP, where speed matters more than perfect delivery, and as the base of QUIC (HTTP/3).

Exam tip

"Why does a voice call use UDP?" Because a retransmitted voice packet arrives too late to be played; it is better to skip it than to pause the call. Give the trade-off in one sentence: TCP trades speed for reliability, UDP trades reliability for speed.

TCP and UDP communication examples

TCPServer.java and TCPClient.java: the client sends a sentence, the server returns it in capitals

// TCP Server
import java.io.*;
import java.net.*;

public class TCPServer {
    public static void main(String args[]) throws Exception {
        ServerSocket welcomeSocket = new ServerSocket(6789);

        while(true) {
            Socket connectionSocket = welcomeSocket.accept();
            BufferedReader inFromClient = new BufferedReader(
                new InputStreamReader(connectionSocket.getInputStream()));
            DataOutputStream outToClient = new DataOutputStream(
                connectionSocket.getOutputStream());

            String clientSentence = inFromClient.readLine();
            System.out.println("Received: " + clientSentence);

            String capitalizedSentence = clientSentence.toUpperCase() + '\n';
            outToClient.writeBytes(capitalizedSentence);
            connectionSocket.close();   // added: release the connection after replying
        }
    }
}

// TCP Client
import java.io.*;
import java.net.*;

public class TCPClient {
    public static void main(String args[]) throws Exception {
        BufferedReader inFromUser = new BufferedReader(
            new InputStreamReader(System.in));

        Socket clientSocket = new Socket("localhost", 6789);

        DataOutputStream outToServer = new DataOutputStream(
            clientSocket.getOutputStream());
        BufferedReader inFromServer = new BufferedReader(
            new InputStreamReader(clientSocket.getInputStream()));

        String sentence = inFromUser.readLine();
        outToServer.writeBytes(sentence + '\n');

        String modifiedSentence = inFromServer.readLine();
        System.out.println("FROM SERVER: " + modifiedSentence);

        clientSocket.close();
    }
}

The server has two sockets: welcomeSocket only accepts; connectionSocket talks to one client. The original version never closed connectionSocket, which leaks one connection per client; the added close() fixes that. Put each class in its own .java file, start the server first, then the client.

UDPServer.java and UDPClient.java: the same capitalising service over UDP

// UDP Server
import java.io.*;
import java.net.*;

class UDPServer {
    public static void main(String args[]) throws Exception {
        DatagramSocket serverSocket = new DatagramSocket(9876);
        byte[] receiveData = new byte[1024];
        byte[] sendData = new byte[1024];

        while(true) {
            DatagramPacket receivePacket = new DatagramPacket(receiveData, receiveData.length);
            serverSocket.receive(receivePacket);

            // Fixed: use only the bytes actually received (getLength),
            // not the whole 1024-byte buffer
            String sentence = new String(receivePacket.getData(), 0, receivePacket.getLength());
            InetAddress IPAddress = receivePacket.getAddress();
            int port = receivePacket.getPort();

            System.out.println("Received from " + IPAddress + ":" + port + " - " + sentence);

            String capitalizedSentence = sentence.toUpperCase();
            sendData = capitalizedSentence.getBytes();

            DatagramPacket sendPacket = new DatagramPacket(
                sendData, sendData.length, IPAddress, port);
            serverSocket.send(sendPacket);
        }
    }
}

// UDP Client
import java.io.*;
import java.net.*;

class UDPClient {
    public static void main(String args[]) throws Exception {
        BufferedReader inFromUser = new BufferedReader(
            new InputStreamReader(System.in));
        DatagramSocket clientSocket = new DatagramSocket();

        InetAddress IPAddress = InetAddress.getByName("localhost");

        byte[] sendData = new byte[1024];
        byte[] receiveData = new byte[1024];

        String sentence = inFromUser.readLine();
        sendData = sentence.getBytes();

        DatagramPacket sendPacket = new DatagramPacket(
            sendData, sendData.length, IPAddress, 9876);
        clientSocket.send(sendPacket);

        DatagramPacket receivePacket = new DatagramPacket(receiveData, receiveData.length);
        clientSocket.setSoTimeout(5000);   // added: give up after 5 s if the reply is lost
        clientSocket.receive(receivePacket);

        String modifiedSentence = new String(receivePacket.getData(), 0, receivePacket.getLength());
        System.out.println("FROM SERVER: " + modifiedSentence);

        clientSocket.close();
    }
}

No accept() and no streams: each receive() gets one whole datagram, and the server learns where to reply from the packet itself (getAddress(), getPort()). Two fixes from the original: new String(getData()) turned the entire 1024-byte buffer into text, including leftover zero bytes, so the output had invisible garbage; and without a timeout, a lost UDP packet would make the client wait forever.

InetAddressExample.java: InetAddress usage

import java.net.*;

public class InetAddressExample {
    public static void main(String[] args) {
        try {
            // Get local host address
            InetAddress localHost = InetAddress.getLocalHost();
            System.out.println("Local Host: " + localHost);

            // Get by host name
            InetAddress googleAddress = InetAddress.getByName("google.com");
            System.out.println("Google: " + googleAddress);

            // Get all addresses for a host
            InetAddress[] allAddresses = InetAddress.getAllByName("google.com");
            System.out.println("All Google addresses:");
            for (InetAddress addr : allAddresses) {
                System.out.println("  - " + addr);
            }

            // Get host name from IP
            InetAddress address = InetAddress.getByName("8.8.8.8");
            System.out.println("Host name for 8.8.8.8: " + address.getHostName());

            // Check if address is reachable
            System.out.println("Is Google reachable? " + googleAddress.isReachable(5000));

        } catch (Exception e) {
            e.printStackTrace();
        }
    }
}
  • getByName performs a DNS lookup; getAllByName returns every address, often both IPv4 and IPv6 for big sites.
  • getHostName() on an IP does a reverse lookup: for 8.8.8.8 it prints dns.google.
  • isReachable uses ICMP ping only when the program has the privilege; otherwise it tries a TCP connection to port 7. Firewalls often block both, so false does not prove the host is down.
Common mistake

Expecting TCP to keep message boundaries. If the client writes "Hello" then "World", the server may read "HelloWorld" in one go or "Hel" + "loWorld". That is why these examples end every message with '\n' and read with readLine(): the newline marks where a message ends.

Quiz: communication technologies

Q1What are the three messages of the TCP handshake, in order?

The client sends SYN, the server replies SYN-ACK, the client confirms with ACK. Only then can data flow. FIN is used to close a connection.

Q2Which Java class do you use to listen for incoming UDP datagrams?

UDP has no connections, so there is no "server socket" that accepts. A DatagramSocket bound to a port both receives and sends DatagramPackets. ServerSocket is TCP only.

Q3In the original UDP server, why could the printed sentence contain garbage at the end?

A datagram fills only the first getLength() bytes of the buffer; the rest are zeros (or old data). new String(data, 0, packet.getLength()) uses just the received part.

Q4Port 49800 most likely belongs to:

49152–65535 is the IANA dynamic/ephemeral range. When a client opens a socket without choosing a port, the OS picks one for it. (Exact ranges vary: Windows uses 49152–65535, Linux defaults to 32768–60999.)

4Application Protocols (Case Studies)

Sockets move bytes; an application protocol says what those bytes mean. We study three: HTTP, FTP and the tiny Daytime protocol.

HTTP

HTTP is an application-level protocol for distributed, collaborative, hypermedia information systems. Hypermedia means documents that link to other documents and media: the Web. Its key features:

Stateless
The server keeps no memory of previous requests. Each request must carry everything needed (cookies, tokens). This makes servers simple and easy to scale, because any server in a cluster can answer any request.
Media independent
Any type of data can be sent, as long as client and server agree on its type through the Content-Type header (text/html, application/json, image/png).
Connection handling
Older course notes say "connectionless": in HTTP/1.0 the client connected, sent one request, got one response, and the connection closed. Updated: since HTTP/1.1, connections are persistent by default and reused for many requests; HTTP/2 multiplexes many requests on one connection; HTTP/3 uses QUIC. What stayed true is that HTTP is stateless.

Anatomy of an HTTP/1.1 exchange

Request (client to server)

GET /courses/index.html HTTP/1.1      <- request line: method, path, version
Host: www.example.com                  <- mandatory in HTTP/1.1
User-Agent: Mozilla/5.0
Accept: text/html
                                       <- empty line ends the headers

Response (server to client)

HTTP/1.1 200 OK                        <- status line: version, code, reason

Content-Length: 1532
                                       <- empty line

Analogy

HTTP/1.1 is a single-lane road where cars (responses) must leave in the order they entered. HTTP/2 paints several lanes on the same road, but one accident (a lost TCP packet) still blocks all lanes. HTTP/3 gives each lane its own road, so an accident only stops one lane.

Key idea

Every safe method is idempotent, but not every idempotent method is safe. PUT and DELETE change the server, yet doing them twice ends in the same state as doing them once.

Common mistake

Using GET for actions that change data, such as GET /deleteStudent?id=7. Browsers prefetch links and crawlers follow them, so a "safe" GET that deletes data can wipe records by accident. Use POST or DELETE for changes.

FTP

FTP is a protocol for transferring files between computers, classically from your computer to a web server. It uses two separate TCP connections:

  • Control connection, port 21: stays open for the whole session and carries text commands (USER, PASS, LIST, RETR to download, STOR to upload).
  • Data connection: opened for each file or directory listing. In active mode the server connects back to the client from port 20. In passive mode (the default in modern clients) the client connects to a random high port the server announces, which works through firewalls and NAT.
Updated

FTP sends passwords and files in clear text, so anyone on the network path can read them. Today use SFTP (part of SSH, port 22) or FTPS (FTP with TLS). Chrome and Firefox removed support for ftp:// URLs in 2021.

HTTP client and server implementation

These programs speak HTTP directly over sockets, so you can see exactly what goes on the wire. In real projects you would use a framework or java.net.http.HttpClient, but writing it by hand once is the best way to understand the protocol.

SimpleHTTPServer.java: simple HTTP server implementation

import java.io.*;
import java.net.*;
import java.nio.charset.StandardCharsets;
import java.util.StringTokenizer;

public class SimpleHTTPServer {
    public static void main(String[] args) {
        try {
            ServerSocket serverSocket = new ServerSocket(8000);
            System.out.println("HTTP Server running on port 8000");

            while (true) {
                Socket clientSocket = serverSocket.accept();

                // Handle each request in a separate thread
                new Thread(new RequestHandler(clientSocket)).start();
            }
        } catch (IOException e) {
            System.err.println("Server error: " + e.getMessage());
        }
    }

    private static class RequestHandler implements Runnable {
        private Socket clientSocket;

        public RequestHandler(Socket socket) {
            this.clientSocket = socket;
        }

        @Override
        public void run() {
            try (
                BufferedReader in = new BufferedReader(
                    new InputStreamReader(clientSocket.getInputStream()));
                PrintWriter out = new PrintWriter(clientSocket.getOutputStream(), true)
            ) {
                String requestLine = in.readLine();
                if (requestLine == null) return;

                System.out.println("Request: " + requestLine);

                StringTokenizer tokenizer = new StringTokenizer(requestLine);
                String method = tokenizer.nextToken();
                String path = tokenizer.nextToken();

                // Simple routing
                if ("GET".equals(method)) {
                    if ("/".equals(path)) {
                        sendResponse(out, "200 OK", "text/html",
                            "<html><body><h1>Welcome to Simple HTTP Server</h1></body></html>");
                    } else {
                        sendResponse(out, "404 Not Found", "text/html",
                            "<html><body><h1>404 - Page Not Found</h1></body></html>");
                    }
                } else {
                    sendResponse(out, "405 Method Not Allowed", "text/html",
                        "<html><body><h1>405 - Method Not Allowed</h1></body></html>");
                }
            } catch (IOException e) {
                System.err.println("Error handling request: " + e.getMessage());
            } finally {
                try {
                    clientSocket.close();
                } catch (IOException e) {
                    System.err.println("Error closing client socket: " + e.getMessage());
                }
            }
        }

        // Fixed: HTTP requires CRLF ("\r\n") line endings, and Content-Length
        // counts bytes, not characters. println() would use the OS line separator.
        private void sendResponse(PrintWriter out, String status, String contentType, String content) {
            byte[] body = content.getBytes(StandardCharsets.UTF_8);
            out.print("HTTP/1.1 " + status + "\r\n");
            out.print("Content-Type: " + contentType + "; charset=UTF-8\r\n");
            out.print("Content-Length: " + body.length + "\r\n");
            out.print("Connection: close\r\n");
            out.print("\r\n");
            out.print(content);
            out.flush();
        }
    }
}

Run it and open http://localhost:8000/ in a browser. The server reads only the request line (GET / HTTP/1.1), splits it into method and path, and routes: / gives 200, anything else 404, any method other than GET gives 405.

HTTPClient.java: HTTP client with GET and POST

import java.io.*;
import java.net.*;
import java.util.Scanner;

public class HTTPClient {
    public static void main(String[] args) {
        Scanner scanner = new Scanner(System.in);

        System.out.print("Enter host (e.g., example.com): ");
        String host = scanner.nextLine();

        System.out.print("Use (1) GET or (2) POST? ");
        int choice = scanner.nextInt();
        scanner.nextLine(); // consume newline

        try {
            Socket socket = new Socket(host, 80);   // port 80 = plain HTTP, no TLS
            PrintWriter out = new PrintWriter(socket.getOutputStream(), true);
            BufferedReader in = new BufferedReader(
                new InputStreamReader(socket.getInputStream()));

            // Updated: every HTTP line must end in "\r\n" (CRLF)
            if (choice == 1) {
                // Send GET request
                out.print("GET / HTTP/1.1\r\n");
                out.print("Host: " + host + "\r\n");
                out.print("User-Agent: Simple Java HTTP Client\r\n");
                out.print("Accept: text/html\r\n");
                out.print("Connection: close\r\n");
                out.print("\r\n");
            } else {
                // Send POST request
                String postData = "name=John&email=john@example.com";

                out.print("POST / HTTP/1.1\r\n");
                out.print("Host: " + host + "\r\n");
                out.print("User-Agent: Simple Java HTTP Client\r\n");
                out.print("Content-Type: application/x-www-form-urlencoded\r\n");
                out.print("Content-Length: " + postData.length() + "\r\n");
                out.print("Connection: close\r\n");
                out.print("\r\n");
                out.print(postData);
            }
            out.flush();

            // Read response
            String line;
            while ((line = in.readLine()) != null) {
                System.out.println(line);
            }

            socket.close();
        } catch (IOException e) {
            System.err.println("Client error: " + e.getMessage());
        }

        scanner.close();
    }
}

Connection: close asks the server to close the connection after its response, so the read loop ends. Many big sites (for example www.google.com) answer a plain-HTTP request on port 80 with 301 Moved Permanently to the HTTPS address, and a POST to / is often refused with 405. Both are correct HTTP behaviour, not bugs in the client.

Show the modern way: java.net.http.HttpClient (Java 11+)

Quiz: application protocols

Q1A client times out while sending PUT /students/7 and automatically sends it again. Is that safe to do?

PUT replaces the resource with the same content, so one or two PUTs give the same result. Retrying a POST is what can create duplicates.

Q2What is the main improvement of HTTP/2 over HTTP/1.1?

HTTP/2 keeps the same methods and status codes but sends binary frames and interleaves many streams on one TCP connection. Moving to UDP (via QUIC) is HTTP/3.

Q3Why do most FTP clients use passive mode today?

In active mode the server must connect back into the client, which home routers and firewalls usually block. In passive mode both connections go from client to server. Passive mode adds no encryption; use SFTP or FTPS for that.

Q4Which header is mandatory in every HTTP/1.1 request?

Host tells the server which website is wanted, which lets many sites share one IP address. Content-Type is only needed when there is a body; User-Agent is optional.

5Middleware & Advanced Distribution

What is middleware?

Middleware is connectivity software that enables multiple processes running on one or more machines to interact across a network. Think of the "/" in client/server: middleware is the software that sits on that slash. It was essential for migrating mainframe applications to client/server and for providing communication across heterogeneous platforms, for example a Java client on Windows talking to a C program on a Linux server.

Client application↔Middleware↔OS + network↔Middleware↔Server application

Middleware typically provides: location transparency (find a service by name, not IP), data conversion (byte order, character sets, object formats), reliability (retries, queues, transactions) and security (authentication, encryption).

Analogy

A postal service with translators. You write a letter in your own language and drop it in a box. The service finds the address, carries the letter, translates it on arrival and keeps it safe until the receiver is home. You never deal with trucks, routes or languages.

Example

An online shop uses all of these. The browser calls the order service (RPC/REST, synchronous: the user waits). The order service puts "send confirmation email" in a queue (MOM: the email can go out a few seconds later). It publishes an "order placed" event that the warehouse, analytics and loyalty services each receive (pub/sub). And it saves the order through JDBC (SQL-oriented data access).

Exam tip

"RPC vs MOM": RPC is synchronous and tightly coupled (the caller waits; the server must be up). MOM is asynchronous and loosely coupled (the sender continues; the queue holds the message until the receiver is ready).

Database middleware

ODBC
Open Database Connectivity (1992): a C-language, vendor-neutral API. An application written to ODBC can use any database that has an ODBC driver. Still widely used, for example by Excel and reporting tools.
OLE DB
Microsoft's COM-based enhancement of ODBC that can also reach non-relational data sources. Windows-only. Still supported for SQL Server through the MSOLEDBSQL driver, but new .NET applications use ADO.NET.
JDBC
Java Database Connectivity: the standard Java API (java.sql) for relational databases, independent of the database vendor.

JDBC architecture

Java application→JDBC API→JDBC Driver Manager→JDBC driver→Database

Your code depends only on the interfaces in java.sql. The DriverManager picks the driver that understands the connection URL (jdbc:mysql://..., jdbc:postgresql://...), and that driver speaks the database's own network protocol. In larger applications a javax.sql.DataSource with a connection pool (for example HikariCP) replaces DriverManager.

BasicJDBCExample.java: basic JDBC connection and query (the classic five steps)

import java.sql.*;

public class BasicJDBCExample {
    // Database credentials
    // Updated: MySQL Connector/J 8+ uses "com.mysql.cj.jdbc.Driver";
    // the old name "com.mysql.jdbc.Driver" is deprecated.
    static final String JDBC_DRIVER = "com.mysql.cj.jdbc.Driver";
    static final String DB_URL = "jdbc:mysql://localhost/EMP";
    static final String USER = "username";
    static final String PASS = "password";

    public static void main(String[] args) {
        Connection conn = null;
        Statement stmt = null;

        try {
            // STEP 1: Register JDBC driver
            // (optional since JDBC 4.0 / Java 6: drivers register themselves)
            Class.forName(JDBC_DRIVER);

            // STEP 2: Open a connection
            System.out.println("Connecting to database...");
            conn = DriverManager.getConnection(DB_URL, USER, PASS);

            // STEP 3: Execute a query
            System.out.println("Creating statement...");
            stmt = conn.createStatement();
            String sql = "SELECT id, first, last, age FROM Employees";
            ResultSet rs = stmt.executeQuery(sql);

            // STEP 4: Extract data from result set
            while(rs.next()) {
                // Retrieve by column name
                int id = rs.getInt("id");
                int age = rs.getInt("age");
                String first = rs.getString("first");
                String last = rs.getString("last");

                // Display values
                System.out.print("ID: " + id);
                System.out.print(", Age: " + age);
                System.out.print(", First: " + first);
                System.out.println(", Last: " + last);
            }

            // STEP 5: Clean-up environment
            rs.close();
            stmt.close();
            conn.close();
        } catch(SQLException se) {
            // Handle errors for JDBC
            se.printStackTrace();
        } catch(Exception e) {
            // Handle errors for Class.forName
            e.printStackTrace();
        } finally {
            // Finally block used to close resources
            try {
                if(stmt != null) stmt.close();
            } catch(SQLException se2) {
                // Nothing we can do
            }
            try {
                if(conn != null) conn.close();
            } catch(SQLException se) {
                se.printStackTrace();
            }
        }
    }
}
  1. Register the driver (automatic in modern Java).
  2. Open a connection with a JDBC URL, user and password.
  3. Execute a query through a Statement.
  4. Read the ResultSet row by row: next() moves to the next row and returns false at the end.
  5. Close the result set, statement and connection. Closing twice (in the try and in finally) is harmless; try-with-resources, used in the next tabs, does it once and correctly.

AdvancedJDBCExample.java: PreparedStatement for parameterised queries

import java.sql.*;

public class AdvancedJDBCExample {
    static final String DB_URL = "jdbc:mysql://localhost/EMP";
    static final String USER = "username";
    static final String PASS = "password";

    public static void main(String[] args) {
        // Updated: try-with-resources closes everything automatically.
        // The original reused one pstmt variable for two statements,
        // so the first PreparedStatement was never closed.
        try (Connection conn = DriverManager.getConnection(DB_URL, USER, PASS)) {

            // Using PreparedStatement for parameterized queries
            String sql = "UPDATE Employees SET age = ? WHERE id = ?";
            try (PreparedStatement pstmt = conn.prepareStatement(sql)) {
                // Bind values into the parameters
                pstmt.setInt(1, 35);  // This sets the age
                pstmt.setInt(2, 102); // This sets the ID

                // Execute the update
                int rows = pstmt.executeUpdate();
                System.out.println(rows + " rows affected.");
            }

            // Using PreparedStatement for SELECT with parameters
            sql = "SELECT id, first, last, age FROM Employees WHERE age > ?";
            try (PreparedStatement pstmt = conn.prepareStatement(sql)) {
                pstmt.setInt(1, 30);

                try (ResultSet rs = pstmt.executeQuery()) {
                    // Extract data from result set
                    while(rs.next()) {
                        int id = rs.getInt("id");
                        int age = rs.getInt("age");
                        String first = rs.getString("first");
                        String last = rs.getString("last");

                        System.out.print("ID: " + id);
                        System.out.print(", Age: " + age);
                        System.out.print(", First: " + first);
                        System.out.println(", Last: " + last);
                    }
                }
            }
        } catch(SQLException se) {
            se.printStackTrace();
        }
    }
}

TransactionExample.java: JDBC transaction management

import java.sql.*;

public class TransactionExample {
    static final String DB_URL = "jdbc:mysql://localhost/EMP";
    static final String USER = "username";
    static final String PASS = "password";

    public static void main(String[] args) {
        try (Connection conn = DriverManager.getConnection(DB_URL, USER, PASS)) {

            // Turn off auto-commit to control transactions manually
            conn.setAutoCommit(false);

            try (Statement stmt = conn.createStatement()) {
                // Execute multiple SQL statements as a single transaction
                String sql1 = "UPDATE Employees SET age = 30 WHERE id = 101";
                stmt.executeUpdate(sql1);

                String sql2 = "UPDATE Employees SET age = 35 WHERE id = 102";
                stmt.executeUpdate(sql2);

                String sql3 = "INSERT INTO Employees VALUES (103, 'John', 'Doe', 28)";
                stmt.executeUpdate(sql3);

                // If we reach here without exceptions, commit the transaction
                conn.commit();
                System.out.println("Transaction committed successfully.");

            } catch (SQLException e) {
                // If any error occurs, rollback the transaction
                conn.rollback();
                System.out.println("Transaction rolled back due to error: " + e.getMessage());
            } finally {
                conn.setAutoCommit(true);   // restore the default
            }

        } catch(SQLException se) {
            se.printStackTrace();
        }
    }
}

By default JDBC is in auto-commit mode: every statement is saved permanently as soon as it runs. setAutoCommit(false) groups the three statements into one transaction. If the INSERT fails (for example, id 103 already exists), rollback() undoes the two UPDATEs as well, so the database is never left half-changed.

Atomicity
All statements happen, or none do.
Consistency
The database moves from one valid state to another (constraints still hold).
Isolation
Concurrent transactions do not see each other's half-finished work.
Durability
Once committed, the change survives a crash.
Tip

The MySQL driver is not part of the JDK. Add the Connector/J .jar to the classpath (or the Maven dependency com.mysql:mysql-connector-j), otherwise you get No suitable driver found.

Quiz: middleware and JDBC

Q1A sender must keep working even when the receiver is offline for an hour. Which middleware fits best?

MOM is asynchronous: the queue stores the message until the receiver comes back. RPC is synchronous and fails if the server is down. ODBC is for database access.

Q2Why is PreparedStatement preferred over Statement when values come from the user?

With ? placeholders the SQL structure is fixed before any value is supplied; the driver sends values as data. It can also be faster when the same statement runs many times.

Q3In TransactionExample, the third statement fails. What is in the database afterwards?

With auto-commit off, nothing is permanent until commit(). The exception jumps to the catch block, rollback() runs, and the two updates are undone: atomicity.

Q4Which JDBC driver type is the standard choice today?

Type 4 drivers are a single .jar that talks the database protocol directly, with no native libraries. The Type 1 bridge was removed in Java 8.

6Remote Invocation (RPC & RMI)

RPC: Remote Procedure Call

RPC is a mechanism to execute subroutines on other hosts without including socket code in your programs. The network code is hidden in stub procedures, so calling a remote function looks like calling a local one: result = add(4, 5), even though add runs on another machine.

Client stub
Local procedure with the same signature as the remote one. It marshals the arguments and sends the request.
Server stub (skeleton)
Receives the request, unmarshals the arguments, calls the real procedure, and sends back the result.
Marshalling
Converting parameters into a network format (bytes). Unmarshalling is the reverse.
IDL
Interface Definition Language: a language-neutral description of the remote procedures, from which stubs are generated (for example .x files in ONC RPC, .proto files in gRPC).
Binding
How the client finds the server: a name service or registry (portmapper on port 111 in ONC RPC, the RMI registry on 1099).
  1. The client calls the client stub in the normal way; the client blocks until the reply comes back.
  2. The client stub marshals the procedure ID and parameters into a message.
  3. The OS sends the message to the server machine.
  4. The server stub unmarshals the parameters.
  5. The server stub calls the real procedure on the server.
  6. The procedure returns its result to the server stub, which marshals it and sends it back (steps 6–8).
  7. The client stub unmarshals the result and returns it to the caller, which continues as if it had made a local call (steps 9–10).
Analogy

A travel agent. You ask the agent (client stub) for "a flight to Paris on Friday". The agent fills in the airline's booking form (marshalling), sends it, and the airline's clerk (server stub) reads the form and enters it in the real system (server procedure). The ticket comes back the same way. You only talked to the agent.

Local call vs remote call

SpeedNanosecondsMilliseconds: about a million times slower
FailureCaller and callee fail togetherNetwork or server can fail independently; caller may not know if the call ran
ParametersCan pass pointers / referencesValues are copied (serialized); references need special remote objects

RMI: Remote Method Invocation

RMI is Java's mechanism that allows an object in one JVM to invoke methods on an object running in another JVM. It is RPC made object-oriented and is used to build distributed Java applications.

  • Remote interface: extends java.rmi.Remote; each method declares throws RemoteException.
  • Remote object: implements the interface and is exported (made reachable), usually by extending UnicastRemoteObject.
  • Stub: the client-side proxy. Since Java 5 it is generated automatically at run time; the old rmic compiler was removed in Java 15. Server-side skeletons have not been needed since Java 1.2.
  • RMI registry: a name service on port 1099. The server binds or rebinds a name; the client lookups the name and receives a stub.
  • Parameters: ordinary objects must implement Serializable and are passed by value (copied); remote objects are passed by reference (as a stub).
Server: rebind("Hello", obj)→RMI registry :1099←Client: lookup("Hello")→stub.sayHello()

CORBA

CORBA (Common Object Request Broker Architecture), from the Object Management Group, is a platform- and language-independent framework for building distributed systems. Interfaces are written in OMG IDL and compiled into stubs for C++, Java and other languages; an ORB carries calls using the IIOP protocol. CORBA is now legacy: Java's CORBA and RMI-IIOP modules were removed in Java 11 (2018). See Chapter 4: RMI-IIOP & CORBA.

Security note

RMI transfers objects with Java serialization, which has a long history of remote-code-execution vulnerabilities when it accepts data from untrusted sources. Use RMI only on trusted internal networks, configure serialization filters (jdk.serialFilter), and prefer gRPC or HTTPS APIs for anything exposed to the internet.

RMI implementation examples

Each example has four parts: remote interface, implementation, server, client. In a real project each public class goes in its own .java file, and the interface (plus any serializable data classes) must be on both the client's and the server's classpath.

Hello: basic RMI implementation

// 1. Define the Remote Interface
import java.rmi.Remote;
import java.rmi.RemoteException;

public interface Hello extends Remote {
    String sayHello() throws RemoteException;
}

// 2. Implement the Remote Interface
import java.rmi.RemoteException;
import java.rmi.server.UnicastRemoteObject;

public class HelloImpl extends UnicastRemoteObject implements Hello {
    public HelloImpl() throws RemoteException {
        super();   // exports this object so it can receive remote calls
    }

    public String sayHello() throws RemoteException {
        return "Hello, world!";
    }
}

// 3. Create the Server
import java.rmi.registry.LocateRegistry;
import java.rmi.registry.Registry;

public class HelloServer {
    // Keep a strong reference so the registry is not garbage-collected
    private static Registry registry;

    public static void main(String[] args) {
        try {
            // Create and export the remote object
            HelloImpl obj = new HelloImpl();

            // Bind the remote object to the registry
            registry = LocateRegistry.createRegistry(1099);
            registry.bind("Hello", obj);

            System.out.println("HelloServer ready");
        } catch (Exception e) {
            System.err.println("Server exception: " + e.toString());
            e.printStackTrace();
        }
    }
}

// 4. Create the Client
import java.rmi.registry.LocateRegistry;
import java.rmi.registry.Registry;

public class HelloClient {
    public static void main(String[] args) {
        try {
            // Get the registry
            Registry registry = LocateRegistry.getRegistry("localhost");

            // Look up the remote object
            Hello stub = (Hello) registry.lookup("Hello");

            // Call the remote method
            String response = stub.sayHello();
            System.out.println("Response: " + response);
        } catch (Exception e) {
            System.err.println("Client exception: " + e.toString());
            e.printStackTrace();
        }
    }
}

The server creates the registry inside its own JVM with createRegistry(1099), so no separate program is needed. bind fails with AlreadyBoundException if the name is taken; rebind replaces it. The client's lookup returns a stub that implements Hello, so stub.sayHello() looks like a local call. Two small additions to the original: HelloImpl now imports RemoteException, and the server keeps the registry in a static field.

Calculator: RMI calculator implementation

// Calculator Interface
import java.rmi.Remote;
import java.rmi.RemoteException;

public interface Calculator extends Remote {
    public long add(long a, long b) throws RemoteException;
    public long sub(long a, long b) throws RemoteException;
    public long mul(long a, long b) throws RemoteException;
    public long div(long a, long b) throws RemoteException;
}

// Calculator Implementation
import java.rmi.RemoteException;
import java.rmi.server.UnicastRemoteObject;

public class CalculatorImpl extends UnicastRemoteObject implements Calculator {
    public CalculatorImpl() throws RemoteException {
        super();
    }

    public long add(long a, long b) throws RemoteException {
        return a + b;
    }

    public long sub(long a, long b) throws RemoteException {
        return a - b;
    }

    public long mul(long a, long b) throws RemoteException {
        return a * b;
    }

    public long div(long a, long b) throws RemoteException {
        return a / b;   // b == 0 throws ArithmeticException, which RMI passes back to the client
    }
}

// Calculator Server
import java.rmi.Naming;

public class CalculatorServer {
    public CalculatorServer() {
        try {
            Calculator c = new CalculatorImpl();
            Naming.rebind("rmi://localhost:1099/CalculatorService", c);
        } catch (Exception e) {
            System.out.println("Trouble: " + e);
        }
    }

    public static void main(String args[]) {
        new CalculatorServer();
    }
}

// Calculator Client
import java.rmi.Naming;

public class CalculatorClient {
    public static void main(String[] args) {
        try {
            Calculator c = (Calculator) Naming.lookup("rmi://localhost/CalculatorService");
            System.out.println("Sub: " + c.sub(4, 3));
            System.out.println("Add: " + c.add(4, 5));
            System.out.println("Mul: " + c.mul(3, 6));
            System.out.println("Div: " + c.div(9, 3));
        } catch (Exception e) {
            System.out.println("CalculatorClient exception: " + e);
        }
    }
}

This version uses java.rmi.Naming, which takes URL-style names (rmi://host:port/name). Unlike HelloServer it does not create a registry, so start one first from the JDK's bin folder, in the directory containing your compiled classes:

rmiregistry 1099          # terminal 1 (leave it running)
java CalculatorServer     # terminal 2
java CalculatorClient     # terminal 3
# Output: Sub: 1   Add: 9   Mul: 18   Div: 3

StudentService: RMI with database access

// Student class (serializable)
import java.io.Serializable;

public class Student implements Serializable {
    private static final long serialVersionUID = 1L;   // added: version stamp for serialization
    private int id, percent;
    private String name, branch, email;

    // Getters and setters
    public int getId() { return id; }
    public void setId(int id) { this.id = id; }

    public String getName() { return name; }
    public void setName(String name) { this.name = name; }

    public String getBranch() { return branch; }
    public void setBranch(String branch) { this.branch = branch; }

    public int getPercent() { return percent; }
    public void setPercent(int percent) { this.percent = percent; }

    public String getEmail() { return email; }
    public void setEmail(String email) { this.email = email; }
}

// Remote Interface
import java.rmi.Remote;
import java.rmi.RemoteException;
import java.util.List;

public interface StudentService extends Remote {
    public List<Student> getStudents() throws RemoteException;
}

// Service Implementation
import java.rmi.RemoteException;
import java.rmi.server.UnicastRemoteObject;
import java.sql.*;
import java.util.*;

public class StudentServiceImpl extends UnicastRemoteObject implements StudentService {
    public StudentServiceImpl() throws RemoteException {
        super();
    }

    public List<Student> getStudents() throws RemoteException {
        List<Student> students = new ArrayList<>();

        // Database connection details
        String DB_URL = "jdbc:mysql://localhost:3306/details";
        String USER = "myuser";
        String PASS = "password";
        String sql = "SELECT * FROM student_data";

        // Updated: no Class.forName("com.mysql.jdbc.Driver") needed (JDBC 4.0+),
        // and try-with-resources closes everything even on errors
        try (Connection conn = DriverManager.getConnection(DB_URL, USER, PASS);
             Statement stmt = conn.createStatement();
             ResultSet rs = stmt.executeQuery(sql)) {

            // Extract data from result set
            while(rs.next()) {
                Student student = new Student();
                student.setId(rs.getInt("id"));
                student.setName(rs.getString("name"));
                student.setBranch(rs.getString("branch"));
                student.setPercent(rs.getInt("percentage"));
                student.setEmail(rs.getString("email"));

                students.add(student);
            }
        } catch (SQLException e) {
            throw new RemoteException("Error accessing database", e);
        }

        return students;
    }
}

// Server
import java.rmi.registry.LocateRegistry;
import java.rmi.registry.Registry;

public class StudentServer {
    private static Registry registry;

    public static void main(String[] args) {
        try {
            StudentService service = new StudentServiceImpl();
            registry = LocateRegistry.createRegistry(1099);
            registry.bind("StudentService", service);
            System.out.println("StudentServer ready");
        } catch (Exception e) {
            System.err.println("Server exception: " + e.toString());
            e.printStackTrace();
        }
    }
}

// Client
import java.rmi.registry.LocateRegistry;
import java.rmi.registry.Registry;
import java.util.List;

public class StudentClient {
    public static void main(String[] args) {
        try {
            Registry registry = LocateRegistry.getRegistry("localhost");
            StudentService stub = (StudentService) registry.lookup("StudentService");

            List<Student> students = stub.getStudents();
            for (Student s : students) {
                System.out.println("ID: " + s.getId());
                System.out.println("Name: " + s.getName());
                System.out.println("Branch: " + s.getBranch());
                System.out.println("Percentage: " + s.getPercent());
                System.out.println("Email: " + s.getEmail());
                System.out.println("-----");
            }
        } catch (Exception e) {
            System.err.println("Client exception: " + e.toString());
            e.printStackTrace();
        }
    }
}

This example joins everything in the course into a 3-tier system: the RMI client is the presentation tier, StudentServiceImpl is the application tier, and MySQL is the data tier. The client never sees SQL or database passwords. Student objects travel by value, so they must be Serializable, and the Student class must exist on both sides.

Exam tip

Be ready to list the steps to build an RMI application: (1) define a remote interface extending Remote, every method throwing RemoteException; (2) implement it, extending UnicastRemoteObject; (3) server creates the object and binds it in the registry; (4) client looks it up and calls methods on the stub. Compiling with rmic is no longer a step in current Java.

Quiz: RPC and RMI

Q1What is marshalling?

The client stub marshals the arguments into bytes; the server stub unmarshals them. Finding the server is binding (registry, portmapper).

Q2Why must every method in an RMI remote interface declare RemoteException?

A remote call can fail even when the code is correct: server down, connection lost, timeout. Making it a checked exception forces the programmer to deal with it, which is the honest difference between local and remote calls.

Q3The Student class must implement Serializable because:

Non-remote objects in RMI are serialized into bytes, sent, and rebuilt on the other side. Only remote objects (stubs) are passed by reference. The registry stores stubs, not Student objects.

Q4True or false: CORBA and RMI-IIOP are still included in the current JDK.

False. Both were removed in Java 11 (2018, JEP 320). Plain Java RMI (JRMP) is still in the JDK in the java.rmi module; RMI Activation was removed in Java 17.

Summary

  • Model: clients initiate requests, servers listen and respond over IPC (sockets) using a shared protocol. Servers use threads, thread pools or (Java 21+) virtual threads to serve many clients at once.
  • Trade-offs: central management, scalability, data sharing and security, against cost, complexity, a single point of failure (fixed with redundancy) and congestion.
  • Architectures: fat client vs fat server decides where logic runs. 2-tier sends SQL from every client; 3-tier puts logic in an application server for performance, scalability, reuse and security; N-tier adds load balancers, caches, queues and services. Layers are logical, tiers are physical.
  • Transport: socket = IP + port. TCP: handshake, reliable, ordered byte stream, 20–60 byte header. UDP: connectionless datagrams, 8 byte header, used for DNS, VoIP and QUIC. Read only getLength() bytes of a datagram.
  • HTTP: stateless, media independent, CRLF-terminated text in 1.1, binary multiplexed in HTTP/2, QUIC over UDP in HTTP/3; HTTPS uses TLS 1.2/1.3. GET, HEAD, OPTIONS, TRACE are safe; add PUT and DELETE for idempotent; POST and PATCH are neither.
  • FTP: control on 21, data on 20 (active) or a high port (passive); unencrypted, so use SFTP or FTPS.
  • Middleware: RPC (synchronous), MOM and pub/sub (asynchronous), ORBs (CORBA, legacy) and database APIs (ODBC, OLE DB, JDBC). In JDBC use Type 4 drivers, try-with-resources, PreparedStatement against SQL injection, and transactions for all-or-nothing updates.
  • Remote invocation: stubs marshal parameters and hide the network (10 steps). RMI: Remote interface + RemoteException, UnicastRemoteObject, registry on 1099, Serializable parameters copied by value. CORBA was removed from Java 11; gRPC is the common modern choice.
