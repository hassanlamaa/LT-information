RMI-IIOP, CORBA and Java IDL

CORBA was the industry's big attempt to let objects written in any language, on any operating system, call each other over a network. You will learn how its ORB, IDL and IIOP protocol work, how Java plugged into it with Java IDL and RMI-IIOP, and why today's systems use gRPC and REST instead.

  • Trace a CORBA invocation from client to servant and back.

Status in 2026: legacy technology

Java IDL (the org.omg.* packages, idlj, orbd, tnameserv) and RMI-IIOP (javax.rmi, rmic -iiop) were removed from the JDK in Java 11 by JEP 320. The code on this page compiles on JDK 8 to 10, or on newer Java with a separate ORB library such as JacORB or the Eclipse GlassFish ORB. CORBA itself is still an OMG and ISO standard (ISO/IEC 19500) and runs in older banking, telecom and defence systems, but new projects use gRPC with Protocol Buffers, REST/JSON over HTTP, Apache Thrift or message queues. You still study CORBA because its ideas (IDL, stubs, brokers, naming) are exactly the ideas inside those modern tools.

4.9.3RMI-IIOP and Java IDL

Java RMI (previous page) only connects Java to Java. To talk to programs written in C++, COBOL or Python, Java needed to speak the language of CORBA.

CORBA
Common Object Request Broker Architecture: a standard from the OMG (Object Management Group, an industry consortium) for platform- and language-neutral distributed objects. First version 1991.
ORB
Object Request Broker: the middleware library that finds the target object, sends the request and returns the reply.
GIOP
General Inter-ORB Protocol: the abstract message format ORBs use to talk to each other (Request, Reply, LocateRequest, and so on). Data inside is encoded in CDR (Common Data Representation).
IIOP
Internet Inter-ORB Protocol: GIOP carried over TCP/IP. It is CORBA's standard wire protocol (since CORBA 2.0, 1996), so ORBs from different vendors can interoperate.
IOR
Interoperable Object Reference: the "address" of a CORBA object. It contains the host, port and an object key, and can be written as a string beginning with IOR:.
Java IDL
Java's built-in CORBA implementation (JDK 1.2 to 10): an ORB, the org.omg.* APIs, a naming service (orbd) and the idlj compiler.
idlj
The IDL-to-Java compiler. It reads an .idl file and generates Java stubs, skeletons and helper classes.
Analogy

IIOP is like the international postal standard. Every country (vendor ORB) runs its own post office, but because envelopes and addresses (IORs) follow one standard format, a letter from a Java ORB reaches a C++ ORB.

Java IDL: IDL first

With Java IDL you start from an IDL file and generate Java code from it:

Hello.idl

module HelloApp {
    interface Hello {
        string sayHello();
    };
};
// idlj -fall Hello.idl  → generates client stubs + server skeletons

-fall means "generate files for both client and server". For Hello.idl, idlj produces:

Generated fileRole
_HelloStub.javaClient stub: marshals calls into GIOP requests.
HelloPOA.javaServer skeleton: your servant class extends it.
Hello.java, HelloOperations.javaThe Java interface for the IDL interface.
HelloHelper.javaUtility methods, notably narrow() to cast a generic CORBA reference to Hello.
HelloHolder.javaWrapper used when a Hello is an out or inout parameter.

RMI-IIOP: Java first

RMI-IIOP (added in Java 1.3) took the opposite route: you write normal RMI code with Java interfaces, but the calls travel over IIOP instead of JRMP. It combined RMI's simple programming model with CORBA interoperability, and it was the protocol used between Enterprise JavaBeans (EJB) containers.

  • Remote classes extended javax.rmi.PortableRemoteObject.
  • rmic -iiop generated IIOP stubs and server-side "ties" (the RMI-IIOP name for skeletons).
  • rmic -idl could generate an IDL file from the Java interface, so C++ or other CORBA clients could call the Java object.
  • Clients looked up objects through JNDI and the CORBA naming service.

To be IIOP-compatible, RMI code had to follow some restrictions. The original notes summarise these as "no pass-by-reference"; the precise rules are:

  • Use PortableRemoteObject.narrow() instead of a plain Java cast on references obtained from lookups.
  • Do not rely on RMI's distributed garbage collection (IIOP does not support it); unexport objects explicitly.
  • Avoid names that clash when mapped to IDL (for example method names differing only in letter case), and avoid RMI-only features such as custom socket factories.
  • Remote objects are still passed by reference and serializable objects by value (as CORBA valuetypes), but a non-Java peer must understand those value types, so simple data types are safest.
Exam tip

Java IDL = write IDL, generate Java (IDL-first). RMI-IIOP = write Java, run it over IIOP (Java-first). Both aim at the same thing: interoperability with CORBA objects in other languages.

Knowledge check 4.9.3

QWhat is the primary benefit of RMI-IIOP?

Running RMI over IIOP lets Java objects be called by, and call, CORBA objects in C++, COBOL, Python and so on. It was not faster than JRMP, it still needed stubs and ties (from rmic -iiop), and its whole point was to go beyond Java-only communication.

4.9.4OMG CORBA: Introduction

CORBA is a technical standard for an ORB (Object Request Broker). You can think of it as the object-oriented evolution of RPC: instead of calling a procedure number on a server, a client calls a method on an object reference. It lets applications on different computers, operating systems, CPU types and languages (C++, Java, Python, COBOL, Ada and others) work together. The OMG's slogan was "making software work together".

  • Distributed middleware with network transparency: the client does not see sockets or byte order.
  • Language-independent interface definitions through IDL.
  • The ORB handles location, activation and communication: finding the object, starting its server if needed, and moving the request and reply.
Middleware
Software that sits between applications and the operating system/network and connects distributed parts of a system.
Servant
The programming-language object (for example a Java object) that actually implements a CORBA interface on the server.
Naming Service
A CORBA service (CosNaming) that maps human-readable names like "Bank" to object references, like the RMI registry. In Java IDL it was provided by orbd (earlier tnameserv).
Analogy

The ORB is a telephone switchboard operator. You ask for "the Accounts department" (a name); the operator finds which building and extension it is (location), wakes someone up if the office is closed (activation), and connects the call (communication). You never need to know the building's address.

CORBA invocation steps at run time

  1. The server object starts and registers with the ORB: the servant is activated in an object adapter (POA), and its reference is usually published in the Naming Service.
  2. The client binds to (finds) the server object reference via the ORB, typically by resolving a name in the Naming Service. It receives an IOR, which the ORB wraps in a stub.
  3. The client invokes a method on the object reference, for example account.withdraw(50). The stub marshals the arguments into CDR.
  4. The ORB delivers the request to the server object: the client ORB sends a GIOP Request over IIOP; the server ORB passes it to the POA, which picks the servant, and the skeleton unmarshals and calls the method.
  5. The server returns the result through the ORB: the skeleton marshals the return value (or exception) into a GIOP Reply, and the client stub unmarshals it.

Knowledge check: CORBA basics

QWhat does ORB stand for in CORBA?

ORB = Object Request Broker, the "broker" that carries requests between client and object. It also gives CORBA its name: Common Object Request Broker Architecture.

4.9.5CORBA Architecture: Core Components

The CORBA architecture diagram has a client side (left), a server side (right) and the ORB core in the middle. Learn each box and which side it belongs to.

Interface Repository (IR)

A run-time database of interface definitions (operations, parameter types). Lets programs discover interfaces dynamically.

DII

Dynamic Invocation Interface (client side): build a request at run time without a compiled stub.

Client stubs (IDL stubs)

Precompiled, static invocation code generated from IDL. Fast and type-checked.

ORB interface

APIs to local ORB services used by both sides, e.g. ORB.init(), string_to_object(), resolve_initial_references().

Object Adapter

Mediates between the ORB and servants (server side). The original BOA (Basic Object Adapter) was replaced in CORBA 2.2 (1998) by the POA.

Server skeletons (IDL skeletons)

Static, generated code that unmarshals requests and calls servant methods.

DSI

Dynamic Skeleton Interface (server side): receive requests at run time without precompiled skeletons. The server-side mirror of DII.

Implementation Repository

Stores information on how to locate and start (activate) servers, so a server can be launched on demand when a request arrives.

The ORB core is the switch: it routes requests between objects. The Object Adapter (in practice the POA, Portable Object Adapter) handles activation of servants, generation of object references, and dispatching each incoming request to the right servant.

Static vs dynamic invocation

Client sideServer sideWhen to use
StaticIDL stubIDL skeletonInterface known at compile time (the normal case). Faster, compiler checks types.
DynamicDII (+ Interface Repository)DSIGeneric tools: object browsers, bridges and gateways that must handle interfaces they have never seen.
Memory trick

Invocation is what a client does → DII is client side. Skeletons live on the Server → DSI is server side.

Common mistake

Mixing up the two repositories. The Interface Repository describes what an interface looks like (types). The Implementation Repository describes where and how to start the server that implements it.

Knowledge check: architecture

QWhich component allows a CORBA server to be implemented without compiling IDL-specific skeletons (dynamic dispatch)?

DSI is the server-side dynamic mechanism: one generic method receives every request and inspects it at run time. DII is the tempting wrong answer, but it is the client-side counterpart (dynamic requests without stubs).

4.9.6Interface Definition Language (IDL)

OMG IDL is a declarative language: it only describes interfaces (operations, attributes, exceptions and data types); it contains no implementation code. A compiler then maps the IDL to a real language (Java, C++, Python...). Because both sides are generated from the same file, they always agree on the contract.

IDL supports in / out / inout parameter directions, multiple inheritance of interfaces, modules (namespaces) and user-defined exceptions.

Bank.idl

module Bank {
    exception InsufficientFunds {};
    interface Account {
        readonly attribute string owner;
        long balance();
        void withdraw(in long amount) raises (InsufficientFunds);
        void deposit(in long amount);
    };
};

Compiled with idlj -fall Bank.idl to get stubs, skeletons and helper classes.

Parameter directions

DirectionData flowsJava mapping
inClient → server only. Server reads it.Plain value, e.g. int amount
outServer → client only. Server writes it; client's initial value is ignored.Holder class, e.g. IntHolder
inoutBoth ways. Client sends a value, server may change it and send it back.Holder class, e.g. IntHolder

Java passes primitives by value, so it cannot return a changed int through a parameter. That is why out/inout parameters are wrapped in Holder objects: the server sets holder.value and the client reads it after the call.

Attributes

An IDL attribute is shorthand for accessor operations. A normal attribute maps to a getter and a setter; a readonly attribute maps to a getter only. In Java, readonly attribute string owner; becomes String owner();.

Exceptions

  • System exceptions: about 30 standard exceptions defined by CORBA and raised by the ORB itself, such as COMM_FAILURE, OBJECT_NOT_EXIST, BAD_PARAM, TRANSIENT and UNKNOWN. Any operation can raise them; they do not appear in a raises clause. In Java they are unchecked (org.omg.CORBA.SystemException).
  • User exceptions: declared in IDL with exception and listed in an operation's raises(...) clause, like InsufficientFunds. In Java they are checked exceptions.

Knowledge check: IDL

QWhat does the IDL direction inout indicate?

inout sends the client's value to the server, and the server's (possibly modified) value back to the client. A is in, B is out.

4.9.7Worked Example: a Java IDL Hello Application

This is the classic course lab. It needs JDK 8, 9 or 10 (or an external ORB library on newer Java), because Java IDL was removed in Java 11.

  1. Write the IDL (Hello.idl from section 4.9.3).
  2. Generate code: idlj -fall Hello.idl creates the HelloApp package.
  3. Write the servant: a class that extends the generated skeleton HelloPOA.
  4. Write the server: start the ORB, activate the servant in the root POA, bind it in the Naming Service, call orb.run().
  5. Write the client: start the ORB, resolve the name, narrow it, call the method.
  6. Run: start the naming daemon, then the server, then the client.
import HelloApp.*;
import org.omg.CORBA.*;
import org.omg.CosNaming.*;
import org.omg.PortableServer.*;

class HelloImpl extends HelloPOA {             // the servant
    public String sayHello() { return "Hello from CORBA"; }
}

public class HelloServer {
    public static void main(String[] args) throws Exception {
        ORB orb = ORB.init(args, null);
        POA root = POAHelper.narrow(orb.resolve_initial_references("RootPOA"));
        root.the_POAManager().activate();

        org.omg.CORBA.Object ref = root.servant_to_reference(new HelloImpl());
        NamingContextExt ns = NamingContextExtHelper.narrow(
                orb.resolve_initial_references("NameService"));
        ns.rebind(ns.to_name("Hello"), ref);           // publish the reference

        System.out.println("HelloServer ready");
        orb.run();                                         // wait for requests
    }
}
import HelloApp.*;
import org.omg.CORBA.*;
import org.omg.CosNaming.*;

public class HelloClient {
    public static void main(String[] args) throws Exception {
        ORB orb = ORB.init(args, null);
        NamingContextExt ns = NamingContextExtHelper.narrow(
                orb.resolve_initial_references("NameService"));
        Hello hello = HelloHelper.narrow(ns.resolve_str("Hello")); // IOR → typed stub
        System.out.println(hello.sayHello());
    }
}
# JDK 8–10 only
idlj -fall Hello.idl
javac *.java HelloApp/*.java
orbd -ORBInitialPort 1050 &                                   # naming service
java HelloServer -ORBInitialPort 1050 -ORBInitialHost localhost &
java HelloClient -ORBInitialPort 1050 -ORBInitialHost localhost
# → Hello from CORBA
Common mistake

Using a plain Java cast (Hello) ref instead of HelloHelper.narrow(ref). The object returned by the ORB is a generic CORBA reference, so the cast fails with ClassCastException. narrow checks the type with the remote object and builds the right stub.

4.9.8Advantages of CORBA and its Role as Middleware

Advantages

  • Language, OS and hardware independence.
  • Location transparency: objects can move without client changes.
  • Built on standard IDL: strict interface contracts.
  • Interoperability between vendors via IIOP.
  • Reuse of legacy systems by wrapping them as CORBA objects.
  • Rich standard services: naming, events, transactions, security.

Disadvantages (why it declined)

  • Complex specification and APIs; steep learning curve.
  • IIOP uses dynamic ports, which are hard to pass through firewalls and proxies.
  • Vendor ORBs differed in practice despite the standard.
  • Web services, then REST/JSON and gRPC, offered simpler HTTP-based alternatives.

Middleware (CORBA, RMI, message-oriented middleware such as IBM MQ, .NET remoting and today gRPC or Kafka) connects applications. CORBA is distributed object middleware: it excels at cross-platform, cross-language communication between objects.

Example

A bank keeps its 1990s C++ account system running. It wraps it as a CORBA Account object. A new Java teller application and a Python reporting script both call it through IIOP without anyone rewriting the C++ code.

Knowledge check: advantages

QWhich statement best describes a key advantage of CORBA?

Language and platform independence is CORBA's main purpose. It runs on many operating systems, it is middleware (IDL describes interfaces but is not a programming language), and objects are distributed across machines.

4.9.10Final Exam: RMI-IIOP, CORBA and IDL

Final exam

Q1What protocol does CORBA use for communication between ORBs over TCP/IP?

IIOP is GIOP over TCP/IP, CORBA's standard interoperability protocol. JRMP is plain Java RMI's protocol; SOAP belongs to XML web services.

Q2Which tool generates Java stubs and skeletons from an IDL file?

idlj is the IDL-to-Java compiler. rmic worked from Java classes (not IDL), orbd was the naming/activation daemon, and javac compiles Java. All three Java IDL/RMI tools are gone from modern JDKs.

Q3What does the CORBA Object Adapter (e.g., POA) primarily do?

The POA connects servants to the ORB: it activates them, creates their references, and dispatches incoming requests to them.

Q4Which component allows a CORBA client to construct a request dynamically without pre-compiled stubs?

DII is client-side dynamic invocation. DSI is its server-side mirror. The Interface Repository is often used together with DII to discover the operations, but it does not send requests.

Q5In IDL, an attribute declared as readonly maps to:

A normal attribute gives a getter and a setter; readonly removes the setter.

Q6Which of the following is a system exception in CORBA that can be thrown by any operation?

CORBA::UNKNOWN is one of the standard system exceptions raised by the ORB. InsufficientFunds and UserNotFound would be user exceptions declared in IDL; IOException is a Java class, not CORBA.

Q7What is the main purpose of the Interface Repository?

The Interface Repository holds interface descriptions at run time. Information about server implementations and how to start them is in the Implementation Repository.

Q8RMI-IIOP allows:

RMI-IIOP keeps the RMI programming model (Java interfaces) but uses IIOP on the wire. It did not replace IDL for other languages; rmic -idl could even generate IDL for them.

Q9Which CORBA component acts as a "switch" routing requests between objects?

The ORB core moves requests between clients and objects. The object adapter only dispatches inside one server.

Q10If a parameter in IDL is marked out, it means:

out carries a value back from the server. In Java it is mapped to a Holder object whose value field the server fills.

Q11In which Java version were Java IDL (org.omg.*, idlj, orbd) and RMI-IIOP removed from the JDK?

JEP 320 removed the Java EE and CORBA modules in Java 11 (2018). Java 17 is when RMI Activation was removed; core RMI is still included.

Q12What is an IOR?

An IOR identifies a CORBA object in a vendor-neutral way, so any ORB can use it to reach the object. The Naming Service maps names to IORs.

Q13A team today wants language-neutral, strongly typed RPC between microservices. Which choice is closest in spirit to CORBA but current?

gRPC has an IDL (.proto), generated stubs in many languages and a binary encoding, just like CORBA, but runs over HTTP/2 and is actively maintained. RMI-IIOP is removed from the JDK, and plain RMI is Java-only.

4.9.11Exam Exercises (Based on Official Questions)

Use the quizzes above to practise, then prepare short written answers to these. Try each one before opening the model answer. The practice page has more exercises.

Compare 2-tier vs 3-tier client/server architectures (presentation, logic, data layers).

In 2-tier, the client holds presentation and most business logic and talks directly to the database server. Simple, but every client needs DB drivers and credentials, and logic changes require updating every client. In 3-tier, a middle tier (application server, or an RMI/CORBA/gRPC service) holds the business logic between presentation and data. It scales better, is more secure (only the middle tier touches the database) and is easier to maintain.

Explain RPC characteristics (transparency, marshalling, stubs).

RPC gives access transparency: a remote call looks like a local call. Stubs make this possible; the client stub marshals parameters into a message and the server stub unmarshals and calls the procedure. Marshalling converts data to a machine-independent format (XDR in Sun RPC, CDR in CORBA, Protobuf in gRPC). Parameters are passed by value because there is no shared memory.

Middleware functions: communication, data transformation, transaction management, naming.

Communication: hides sockets and protocols (IIOP, JRMP, HTTP/2). Data transformation: marshalling between formats and byte orders. Transaction management: making several operations all succeed or all fail (CORBA Object Transaction Service, Java JTA). Naming: finding services by name (CORBA Naming Service, RMI registry, DNS).

HTTP methods: safe (GET, HEAD) vs idempotent (GET, PUT, DELETE).

A safe method does not change server state: GET, HEAD, OPTIONS, TRACE. An idempotent method has the same effect whether called once or many times: all safe methods plus PUT and DELETE. POST is neither (and PATCH is not guaranteed idempotent). Every safe method is idempotent, but not every idempotent method is safe (DELETE changes state). This is the HTTP version of RPC's at-least-once rule: idempotent requests can be retried safely.

InetAddress class: represents IP addresses; useful for host resolution.

java.net.InetAddress represents an IPv4 or IPv6 address. InetAddress.getByName("example.com") resolves a host name through DNS; getLocalHost() returns the local machine; getHostAddress() gives the text form. Subclasses are Inet4Address and Inet6Address.

RDA (Remote Database Access): standard for remote SQL execution.

RDA was an ISO standard (ISO/IEC 9579) defining how a client sends SQL statements to a remote database server and receives results, independent of vendor. It is mostly historical; today the same job is done by vendor network protocols with drivers such as JDBC and ODBC, or by putting a service (REST/gRPC) in front of the database.

RMI security via policy files (-Djava.security.policy).

Classically, an RMI program installed a SecurityManager and started with -Djava.security.policy=server.policy; the policy file granted permissions such as java.net.SocketPermission "*:1024-", "connect,accept". This mattered mainly when stub classes were downloaded from a remote codebase. Updated: the SecurityManager was deprecated for removal in Java 17 and permanently disabled in Java 24, so modern RMI security relies on TLS socket factories, firewalls, deserialization filters and not exposing the registry publicly.

Summary

  • CORBA (OMG standard) lets objects in different languages and platforms call each other through an ORB. IIOP (GIOP over TCP/IP) is the wire protocol; IORs identify objects.
  • Java IDL is IDL-first (idlj generates stubs, POA skeletons, helpers, holders). RMI-IIOP is Java-first (RMI over IIOP). Both were removed in Java 11 (JEP 320).
  • Architecture: IDL stubs and DII on the client; IDL skeletons, DSI and the object adapter (POA, which replaced BOA) on the server; Interface Repository (types) and Implementation Repository (server activation); ORB core as the switch.
  • IDL directions: in client→server, out server→client, inout both. readonly attribute gives only a getter. System exceptions come from the ORB, user exceptions from IDL raises.
  • Advantages: language/OS independence, location transparency, standard contracts, legacy wrapping. Declined because of complexity and firewall issues.
  • Modern equivalents: gRPC with Protocol Buffers, REST/JSON over HTTP, Apache Thrift and message queues.
