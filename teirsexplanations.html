Architecture Tiers Explained

Every client/server application does three jobs: it shows things to the user, applies the business rules, and stores data. How you split those jobs across machines (1, 2, 3 or N tiers) decides how well the system scales, how secure it is, and how hard it is to change.

1Introduction to client/server architecture

Client/server architecture is a computing model where the server hosts, delivers and manages most of the resources and services, and the client requests them. A client is whatever sends the request (a browser, a mobile app, a desktop program). A server is whatever waits for requests, does the work and replies.

This architecture is categorised into different tiers based on how responsibilities are divided between client and server. To understand tiers you first need the three jobs every application does.

The three logical layers

Presentation

What the user sees and touches: screens, forms, buttons. It collects input and displays results. Example: the checkout page of an online shop.

Business logic

The rules of the application, also called the application or logic layer. Example: "orders over $50 get free shipping", "stock cannot go below zero".

Data

Storing and retrieving information permanently, usually in a database. Example: the orders and products tables.

Layer vs tier

Tiers describe how application components are separated. The number of tiers determines how the presentation, application processing and data management functions are separated. Textbooks use the two words like this:

Layer
A logical separation of code by responsibility (presentation, business, data). Several layers can run inside one program on one machine.
Tier
A physical (deployment) separation: a part of the system that runs as its own process, usually on its own machine or server, and talks to other tiers over a network.
Monolith
An application built and deployed as one single unit. A monolith can still have clean layers inside it.
Key idea

Layers are about how you organise the code. Tiers are about where that code runs. A 3-layer application can be deployed as 1 tier (all on one PC) or as 3 tiers (three servers).

Common mistake

Some notes say tiers are a "logical" separation. Many sources use the words loosely, but in an exam the safe answer is: layer = logical, tier = physical. Tiers can run on the same physical machine as separate processes (for example, a web server and a database on one small VPS), but the point of a tier is that it can be moved to its own machine.

Analogy

Think of a restaurant. The dining room and waiter are the presentation layer, the kitchen is the business logic, and the pantry and fridge are the data layer. A food truck where one person takes orders, cooks and stores ingredients in the same van is 1-tier. A big restaurant with a separate dining room, kitchen and storeroom is 3-tier.

21-tier architecture (single-tier)

Overview

In a 1-tier architecture, all components of the application exist on a single system. The user interface, business logic and data storage are combined and run on the same machine, usually inside one program. There is no network between the parts, so nothing is "client" or "server" in the network sense.

Examples today

A spreadsheet saved on your laptop, a single-user Microsoft Access database, a desktop accounting tool for one shop that keeps its data in a local embedded database such as SQLite, or an offline mobile game that stores scores on the phone.

Advantages

  • Simple to develop and deploy: install one program.
  • No network latency issues: every call is a local function call.
  • Easier to maintain for small applications.
  • Lower development costs initially.
  • Works offline.

Disadvantages

  • Not scalable: limited to the power of one machine and, usually, one user.
  • Difficult to maintain as the application grows, because UI, rules and data code are tangled together.
  • Single point of failure: if the machine or disk dies, the app and its data are gone.
  • Cannot be distributed across multiple machines, so data is hard to share between users.

Use cases

Single-user applications, small desktop applications, simple mobile apps without backend services, prototypes and tools that must work offline.

Common mistake

Do not treat "1-tier" and "monolithic" as the same thing. 1-tier means everything runs on one machine. Monolithic means the code is built and deployed as one unit. A monolithic web application can still sit in the middle tier of a 3-tier system.

32-tier architecture

Overview

In a 2-tier architecture, the application is split into two parts: a client and a server. In the classic form, the client contains the user interface and the application logic, and the server is a database server. The client talks directly to the database, usually by sending SQL over the local network. This is the original "client/server" model of the 1990s.

Example

A clinic's appointment program installed on five reception PCs. Each PC runs a desktop app (written in C#, Java or Delphi) that opens a connection to one SQL Server on the clinic network and runs queries like SELECT * FROM appointments WHERE day = '2026-11-02'. Older point-of-sale systems and many in-house departmental tools work the same way.

Fat client and thin client variants

2-tier comes in two flavours depending on where the business logic lives:

  • Fat (thick) client 2-tier: the rules are in the client program. This is the usual case and the one exam questions mean by default.
  • Thin client 2-tier: the client only shows screens, and the rules are written as stored procedures and triggers inside the database.

Advantages

  • Several users can share one central database, which 1-tier cannot do well.
  • Simpler to implement than 3-tier: only two kinds of component.
  • Direct communication between client and server, so few network hops.
  • Easier to understand and maintain for small systems.

Disadvantages

  • Business logic is tied to the client, so every change means reinstalling the app on every PC.
  • Limited scalability: every client holds its own database connection, and databases handle only so many.
  • Security concerns: the database must be reachable from every client, and the client often contains database credentials that can be extracted.
  • Network congestion with many clients, because raw query results travel to each client to be processed there.

Use cases

Small to medium business applications, departmental systems and client/server databases on a trusted local network (LAN) with tens of users, not thousands.

Common mistake

A website is not 2-tier just because you can see a browser and "a server". The browser talks to a web/application server, which then talks to the database: that is three tiers. 2-tier means the client connects to the database directly.

43-tier architecture

Overview

In a 3-tier architecture, the application is divided into three logical and physical computing tiers: the presentation tier, the application tier and the data tier. Each tier runs on its own platform (process or server) and can be developed, updated and scaled separately. The key rule is that the client never talks to the database: every request goes through the application tier.

TierJobTypical technology today
PresentationShows pages, collects input, sends requestsBrowser running HTML/CSS/JavaScript (React, Angular, Vue), Android/iOS app
ApplicationChecks input, applies business rules, decides what to read or writeJava (Spring), C# (ASP.NET Core), Node.js, Python (Django/FastAPI), PHP (Laravel)
DataStores data safely, runs queries, enforces constraintsPostgreSQL, MySQL, SQL Server, Oracle, MongoDB

Walk through one request

  1. Presentation: the user clicks "Place order" in the browser. The page sends POST /orders with the basket as JSON over HTTPS.
  2. Application: the server checks the user is logged in, checks stock, works out the total and the shipping rule.
  3. Data: the application server runs INSERT and UPDATE statements inside a transaction.
  4. Back up the chain: the database confirms, the application server returns 201 Created with the order number, and the browser shows "Thank you".
Why it is more secure

The database sits on a private network that only the application tier can reach, usually behind a firewall. Database passwords live on the server, never on users' devices. Users can only do what the application's API allows.

How it scales

If the application servers are stateless, you can run several copies behind a load balancer and add more when traffic grows. This is called horizontal scaling. Updating the business rules means redeploying the server once, not every client.

Advantages

  • Improved scalability and performance for many users.
  • Better security through separation of concerns: the data tier is hidden.
  • Easier to maintain and update each tier on its own.
  • Allows load balancing across several application servers.
  • Different clients (web, mobile) can share the same application tier.

Disadvantages

  • More complex to develop and deploy.
  • Increased network latency: every request takes an extra hop.
  • Higher initial development and hosting costs.
  • Requires more expertise to manage (servers, networking, security).

Use cases

Most web applications: e-commerce sites, online banking, university portals, enterprise systems and SaaS applications.

Exam tip

When asked to "describe 3-tier architecture", name all three tiers, give each one's responsibility in one line, and add the rule that the client never accesses the database directly. Finish with one advantage (security or scalability) and one disadvantage (complexity or latency).

5N-tier architecture

Overview

N-tier (multi-tier) architecture divides an application into more than three tiers that can be distributed across multiple servers. It extends the 3-tier model by splitting the application tier (and sometimes the data tier) into several specialised tiers. "N" just means "any number greater than three".

Common extra tiers

Load balancer / reverse proxy
Receives all traffic and spreads it over many servers; often also handles HTTPS (for example Nginx, HAProxy, a cloud load balancer).
CDN
Content delivery network: copies of images, scripts and pages kept on servers close to users worldwide.
Web tier
Serves pages and static files, separate from the business logic.
API gateway
One entry point for all API calls; checks authentication, applies rate limits, routes each call to the right service.
Business / service tier
The rules, often split into several services (orders, payments, users).
Web services / integration tier
Connects to outside systems: payment providers, email/SMS services, partner APIs, legacy systems.
Cache tier
Keeps frequently read data in memory so the database is not asked the same thing again and again.
Message queue
Lets tiers hand work to each other asynchronously (send the order confirmation email later, not while the user waits).
Data access tier
Code or a service whose only job is talking to the database, so the rest of the system does not write SQL.

N-tier, microservices and the cloud

Modern large systems are almost always N-tier. Two related ideas you should be able to place:

  • Microservices split the business tier into many small, independently deployable services, each owning its own data and talking over APIs (HTTP/REST, gRPC) or messages. They are commonly taught as the most extreme form of N-tier. Strictly speaking, classic N-tier splits the system horizontally by layer, while microservices split it vertically by business capability; in practice a microservice system still has presentation, gateway, service and data tiers.
  • Cloud platforms (AWS, Azure, Google Cloud) sell each tier as a managed service: a managed load balancer, containers or serverless functions for the application tier, and a managed database. You build N-tier systems by connecting these pieces instead of buying physical servers.
Example

A food-delivery app: the phone app (presentation) calls an API gateway, which routes to the restaurants, orders, payments and delivery-tracking services. Orders are written to a database, menus are cached in Redis, payments go out through an integration tier to a card provider, and "your rider is on the way" notifications go through a message queue.

Advantages

  • Maximum scalability and flexibility: scale only the busy tier.
  • Each tier can be optimised independently, even in different languages.
  • Improved fault isolation: one failing service need not take down the rest.
  • Better resource utilisation and independent team ownership.

Disadvantages

  • Most complex to develop and maintain.
  • Highest development and infrastructure costs.
  • Increased network complexity and latency: more hops per request.
  • Requires sophisticated monitoring, logging and automated deployment (DevOps).

Use cases

Large-scale enterprise systems, cloud-native applications, microservices architectures and global web applications such as streaming services, marketplaces and banking platforms.

Common mistake

"More tiers = faster" is false. Each extra tier adds a network hop, so a single request usually gets slower. What improves is throughput: the system can serve far more users at once because each tier can be scaled out.

6Thin clients and thick clients

Where the logic runs decides whether a client is "thin" or "thick". This links directly to the tier models.

Thin client
Does little more than display screens and send input. The server does the processing. Example: a browser showing a server-rendered web page, a remote desktop session.
Thick (fat) client
Does most of the processing locally and uses the server mainly for shared data. Example: the classic 2-tier desktop app, a video editor that syncs projects to the cloud.
Thin clientThick client
Logic runs onServerClient device
Install / updateNothing to install; update the server onceInstall and update on every device

Today

Modern single-page web apps and mobile apps sit in between ("rich clients"): they run a lot of JavaScript or app code for a smooth interface, but the business rules are still enforced on the server. The rule is: never trust the client. Checks done in the browser are for convenience; the application tier must check everything again, because users can modify anything that runs on their own device.

Older versions of this table rated N-tier security as "very high" and 1-tier as "low". Security is not automatic: more tiers give you more places to put firewalls and access checks, but also more components that can be misconfigured. Likewise, N-tier gives the best throughput, not the fastest individual request.

8Choosing a tier model

There is no "best" number of tiers. Pick the simplest model that meets the requirements.

One user, offline

Choose 1-tier. Example: a personal budget app.

Few users, one office LAN

2-tier is acceptable. Example: a 5-PC clinic system.

Users over the internet

Choose 3-tier. Never expose a database to the internet. Example: a university portal.

Millions of users, many teams

Choose N-tier (often microservices on the cloud). Example: a streaming service.

Exam tip

Scenario questions ("a bank wants…", "a small shop needs…") are marked on the justification. Mention number of users, whether they connect over the internet, how often the rules change, and the security of the data. Then name the model.

Try it: a school library with 2 librarians on one PC network, no online access for students. Which model?

2-tier is reasonable: few users, a trusted LAN and a shared database. If students later need to search the catalogue from home over the internet, move to 3-tier so the database is not exposed.

Quiz: Architecture tiers

Q1Which architecture has all components combined in a single system?

In 1-tier, presentation, business logic and data storage all run on one machine, usually in one program.

Q2In which architecture is the business logic typically located on the client side?

Classic 2-tier uses a thick client: UI and business rules on the user's PC, data on the database server. In 3-tier and N-tier the rules move to the server side. (1-tier has no separate client and server at all.)

Q3Which architecture provides the best scalability for large enterprise applications?

N-tier lets each specialised tier be scaled on its own (for example, add more payment-service instances without touching the rest). 3-tier scales well too, but less finely.

Q4What is the main disadvantage of 1-tier architecture?

Everything runs on one machine, so it cannot grow beyond that machine or easily share data among many users. 1-tier is cheap and needs no network, so the first two options are wrong.

Q5Which architecture separates presentation, business logic and data into distinct tiers?

3-tier gives each of the three layers its own tier. 2-tier combines presentation and logic on the client; 1-tier combines all three.

Q6What is the difference between a layer and a tier?

Layers organise code by responsibility; tiers are where that code is deployed. Several layers can run in one tier.

Q7In a 3-tier web application, which tier may connect directly to the database?

Only the application tier talks to the data tier. Keeping the database off the client's path is the main security benefit of 3-tier.

Q8A company must change a tax rule. In which model is the change hardest to roll out?

In thick-client 2-tier, every PC must be updated. In 3-tier or N-tier you redeploy the server or the one service.

Q9Which of these is an extra tier typically found in N-tier systems but not in basic 3-tier?

N-tier keeps the original three tiers and adds specialised ones such as load balancers, API gateways, caches, message queues and integration tiers.

Q10Adding more tiers to a system usually…

Each tier is another network hop, so individual requests get a little slower, while the whole system can serve more users. Complexity and cost go up.

Q11A browser showing pages rendered on the server, with all rules enforced by the server, is an example of a…

A thin client mostly displays and sends input; the processing happens on the server.

Q12An online shop with thousands of internet users should not use 2-tier mainly because…

In 2-tier the client connects straight to the database, so the DB (and its credentials) would be reachable from the internet, and it would also need one connection per user. 3-tier hides the database behind the application tier.

Summary

  • Every application has three layers: presentation, business logic and data. A layer is logical; a tier is where it physically runs.
  • 1-tier: all three on one machine. Simple, fast, offline, but not scalable or shareable.
  • 2-tier: thick client (UI + logic) talks directly to a database server. Fine for a small LAN; hard to update and weak on security at scale.
  • 3-tier: presentation, application and data tiers. The client never touches the database. The standard model for web applications.
  • N-tier: the middle (and data) tiers are split further: load balancers, gateways, services, caches, queues. Most scalable and flexible, most complex. Microservices and cloud systems are modern N-tier designs.
  • More tiers means more throughput and flexibility, but more latency per request, more cost and more to secure and monitor. Choose the simplest model that fits.
