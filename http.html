HTTP & HTTPS

HTTP is the language browsers, apps and APIs use to ask servers for things. HTTPS is the same language sent through an encrypted, authenticated TLS tunnel. Every web or mobile app you will build or secure speaks it, so it pays to know exactly what goes over the wire.

1What HTTP is

HTTP (HyperText Transfer Protocol) is an application-layer protocol for moving resources (web pages, JSON, images, video) between a client and a server. The client always speaks first: it sends a request; the server answers with exactly one response. The server never starts a conversation on its own in plain HTTP.

A resource is anything a URL can name: /index.html, /users/42, /images/logo.png. HTTP does not care what the bytes mean; headers such as Content-Type tell the receiver how to interpret them.

HTTP is stateless: each request is complete on its own, and the server does not automatically remember the previous one. Logins, shopping carts and sessions are built on top of HTTP using cookies or tokens that the client sends again with every request (section 6).

Analogy

HTTP is like ordering at a counter where the cashier has no memory. Every order slip must say who you are and what you want (headers + body). You hand over the slip (request), you get one tray back (response) with a status note on it ("200: here you go", "404: we don't sell that").

Where HTTP sits

HTTP (application)→TLS (for HTTPS)→TCP or QUIC/UDP (transport)→IP (network)

HTTP/1.1 and HTTP/2 run over TCP. HTTP/3 runs over QUIC, which runs over UDP. HTTPS adds TLS between HTTP and the transport (in HTTP/3, TLS 1.3 is built into QUIC itself).

Anatomy of a URL

https://shop.example.com:443/products/42?color=red&size=m#reviews

In HTTP/1.1 a request is plain text: a request line (method, target, version), then headers (one Name: value per line), then an empty line, then an optional body.

What HTTP is

Q1True or false: HTTP is stateless, so the server automatically remembers your previous request.

Stateless means the server does NOT remember earlier requests by itself. State is added with cookies or tokens that the client resends each time.

Q2In https://shop.example.com:443/products/42?color=red&size=m#reviews, which part is never sent to the server?

The fragment is a position inside the page and is handled only by the browser. The query string is tempting because it looks like "extra", but it is part of the request target and the server receives it with the path.

Q3Read this request:
GET /posts/1 HTTP/1.1
Host: jsonplaceholder.typicode.com
Accept: application/json
What is /posts/1?

The request line is method, target, version, so /posts/1 names the resource. It is not the Host (that is the next line, the site name), and a GET like this has no body at all: the body would come after the empty line.

Q4True or false: the Content-Type header tells the receiver how to interpret the bytes of the body.

True. HTTP itself does not care what the bytes mean; Content-Type: application/json or text/html says how to read them. The file extension in the URL does not decide this, even if it often matches.

2The life of a request

What actually happens between typing https://example.com/page and seeing the page? Each step adds latency, which is why newer HTTP versions try to remove round trips.

  1. Parse the URL. The browser splits it into scheme, host, port and path, and checks its cache and the HSTS list (which may force HTTPS).
  2. DNS lookup. The host name is resolved to an IP address (from cache, or by asking a DNS resolver, usually over UDP port 53).
  3. Open a transport connection. For HTTP/1.1 and HTTP/2: a TCP three-way handshake (SYN, SYN-ACK, ACK) to port 443. For HTTP/3: a QUIC handshake over UDP.
  4. TLS handshake (HTTPS only). Client and server agree on keys and the client checks the server's certificate. TLS 1.3 needs one round trip (section 9).
  5. Send the request. Method, path, headers and (for POST/PUT/PATCH) a body, encrypted inside TLS.
  6. Server processes it. Routing, authentication, database queries, building the response.
  7. Receive the response. Status code, headers, body. The browser may now request more resources (CSS, JavaScript, images) found in the HTML.
  8. Reuse or close. HTTP/1.1 keeps the connection open by default (persistent connections) so later requests skip steps 2–4. HTTP/2 and HTTP/3 send many requests in parallel over one connection.
Example

With a 50 ms round-trip time to the server: DNS (≈1 RTT) + TCP (1 RTT) + TLS 1.3 (1 RTT) + request/response (1 RTT) ≈ 200 ms before the first byte of HTML, even if the server answers instantly. That is why connection reuse, HTTP/3 (which merges the transport and TLS handshakes) and CDNs close to the user matter so much.

The life of a request

Q1On a first visit to https://example.com/page over HTTP/1.1 or HTTP/2, what is the correct order?

You need the IP (DNS) before you can connect (TCP), and TLS runs inside the open TCP connection before any HTTP is sent. Putting TLS before TCP is the tempting mistake: TLS messages need a transport connection to travel on.

Q2The round-trip time to a server is 50 ms and the server answers instantly. Roughly how long until the first byte of HTML arrives on a brand-new HTTPS connection (DNS + TCP + TLS 1.3 + request/response)?

Four round trips: DNS, TCP handshake, TLS 1.3 handshake (1 RTT) and the request/response itself, so 4 × 50 ms ≈ 200 ms. 100 ms forgets the handshakes; 400 ms assumes two RTTs per step, which was closer to TLS 1.2.

Q3True or false: with HTTP/1.1 persistent connections, a second request to the same server must repeat the DNS lookup and the TCP handshake.

False. HTTP/1.1 keeps the connection open by default (keep-alive), so later requests skip DNS, TCP and TLS (steps 2–4). Only a new connection pays those costs again.

Q4A normal DNS lookup usually travels over:

DNS resolvers are normally asked over UDP port 53. UDP 443 is tempting because it is also UDP, but that is where QUIC (HTTP/3) runs; TCP 80 and 443 are plain HTTP and HTTPS.

3HTTP request methods (verbs)

The method says what the client wants to do to the resource. Two properties matter for exams and for real systems:

Safe
The method is read-only: it is not meant to change anything on the server. Safe methods: GET, HEAD, OPTIONS, TRACE.
Idempotent
Sending the same request once or ten times leaves the server in the same final state. Idempotent methods: all safe methods plus PUT and DELETE. POST is neither safe nor idempotent. PATCH is not guaranteed to be idempotent.
MethodPurposeSafeIdempotentBodyTypical success
GETRead / retrieve a resourceYesYesNo200 OK
POSTCreate a new resource, or trigger processingNoNoYes201 Created (or 200)
PUTFull update: replace the resource with the bodyNoYesYes200 OK / 204 No Content
PATCHPartial update: change only some fieldsNoNot guaranteedYes200 OK / 204
DELETERemove the resourceNoYesUsually no200 / 204
HEADLike GET but headers only (check size, type, freshness)YesYesNo200 OK
OPTIONSAsk which methods/headers are allowed (used by CORS preflight)YesYesNo204 / 200

Example request lines

GET /users/42 HTTP/1.1
POST /products HTTP/1.1        # with body: { "name": "Laptop" }
PUT /users/42 HTTP/1.1         # with the complete new user object
PATCH /users/42 HTTP/1.1       # with body: { "email": "new@example.com" }
DELETE /posts/7 HTTP/1.1
Analogy

Think of a library catalogue. GET is reading a card. PUT is replacing the whole card with a new one: do it twice and you still have that one card. DELETE is throwing the card away: the second time there is nothing left to throw, the end state is the same. POST is "add a new card": do it twice and you have two cards.

Example: why PATCH is "not guaranteed"

PATCH /users/42 {"email":"a@b.com"} sets a value, so repeating it changes nothing: idempotent in practice. But PATCH /accounts/7 {"op":"increment","field":"balance","by":10} adds 10 each time: not idempotent. The method allows both, so the specification cannot promise idempotency.

Common mistake

"Idempotent" does not mean "returns the same response". The first DELETE /posts/7 may return 200 and the second 404, yet DELETE is still idempotent because the server's state (post 7 is gone) is the same after both. Also, never use GET for actions that change data (GET /deleteUser?id=5): crawlers, link previews and prefetching will trigger it.

Why it matters

When a network request times out, the client cannot know if the server processed it. Idempotent requests can be retried automatically and safely. Payment APIs make POST retryable by asking clients to send a unique Idempotency-Key header, so the server can recognise and ignore duplicates.

HTTP request methods

Q1Which HTTP method is considered "safe" (does not modify server state) and is used to retrieve data?

GET only reads. PUT and DELETE change state (though they are idempotent) and POST creates. Other safe methods are HEAD, OPTIONS and TRACE.

Q2Which HTTP method is NOT idempotent (multiple identical requests may create duplicate resources)?

Two identical POSTs to /orders create two orders. PUT replaces with the same content each time and DELETE leaves the resource deleted, so both end in the same state.

Q3To partially update a resource (e.g. change only the email field), the most appropriate method is:

PATCH sends only the changes. PUT replaces the whole resource, so fields you leave out may be erased.

Q4Which of these request lines is a design mistake?

GET must be safe (read-only). A GET that deletes data will be triggered by crawlers, link previews and prefetching. The PATCH line looks unusual but is correct: it is a partial update of one field.

Q5True or false: the first DELETE /posts/7 returns 200 and the second returns 404, so DELETE is not idempotent.

False. Idempotency is about the server's final state, not the response. After one or ten DELETEs, post 7 is gone, so the state is the same. Different status codes do not break idempotency.

4Status codes

The three-digit status code tells the client what happened. The first digit is the class, so even an unknown code like 418 or 451 can be understood by its class.

ClassMeaningCommon codes
1xxInformational: request received, continue100 Continue, 101 Switching Protocols (e.g. to WebSocket), 103 Early Hints
2xxSuccess200 OK, 201 Created (new resource, often with Location), 204 No Content
3xxRedirection: look elsewhere301 Moved Permanently, 302 Found, 304 Not Modified (use your cached copy), 307/308 Temporary/Permanent Redirect (method kept)
4xxClient error: the request is wrong400 Bad Request, 401 Unauthorized (not authenticated), 403 Forbidden (authenticated but not allowed), 404 Not Found, 405 Method Not Allowed, 409 Conflict, 429 Too Many Requests

Exam tip

401 vs 403 is a classic question. 401: "I don't know who you are" (missing or invalid credentials; log in). 403: "I know who you are, and you are not allowed". And 4xx means fix the request, 5xx means the server has a problem; retrying a 4xx unchanged will not help.

Status codes

Q1A user who is not logged in requests /account. Which status code fits best?

401 means "not authenticated": supply credentials. 403 is for a known user who lacks permission. 5xx would wrongly blame the server.

Q2A 5xx status code means:

5xx = server error (500, 502, 503, 504). Client errors are 4xx, redirects 3xx, success 2xx.

Q3Which status code tells the client "nothing changed, use your cached copy"?

304 is the answer to a conditional request (e.g. If-None-Match) when the cached version is still current. 204 is tempting because it also has no body, but it means "success, nothing to return", not "use your cache".

Q4A server replies with a code you have never seen, 451. What can the client still conclude?

The first digit gives the class, and 4xx means a client error. "Retry later" is the tempting choice, but that fits 5xx (such as 503), where the server is the problem.

Q5True or false: resending a request that got 400 Bad Request, unchanged, is likely to succeed.

False. 4xx means "fix the request"; the same request will get the same answer. Retrying unchanged makes sense only for temporary server-side failures such as 503 or 504.

Headers

Q1Read this response:
HTTP/1.1 201 Created
Location: /posts/101
Content-Type: application/json
What does Location mean here?

With 201 Created, Location points at the new resource. With a 3xx code the same header is the redirect target, which is why "redirect" is tempting, but this is not a 3xx. Cross-origin reading is CORS (Access-Control-Allow-Origin).

Q2A client wants the server to answer in JSON. Which request header expresses that?

Accept lists the formats the client can handle (content negotiation). Content-Type is the tempting one, but it describes the body that is being sent, not the format wanted back.

Q3True or false: header names are case-sensitive, so content-type and Content-Type are different headers.

False. Header names are case-insensitive. HTTP/2 and HTTP/3 even send them all in lowercase, and they still mean the same header.

Q4What does Cache-Control: no-cache mean?

no-cache means "check with the server first" (often answered with 304). The tempting reading "never store" is no-store.

6Cookies and state

Because HTTP is stateless, a server that wants to remember you gives the browser a small piece of data, a cookie. The browser sends it back automatically on every later request to the same site, so the server can look up "session abc123 = user Sara".

HTTP/1.1 200 OK
Set-Cookie: session=abc123; Secure; HttpOnly; SameSite=Lax; Path=/; Max-Age=3600

# every later request from the browser to this site:
GET /cart HTTP/1.1
Host: shop.example.com
Cookie: session=abc123
Secure
Only send the cookie over HTTPS, never plain HTTP.
HttpOnly
JavaScript cannot read it (document.cookie), which limits damage from cross-site scripting (XSS).
SameSite
Strict, Lax or None: whether the cookie is sent on requests started by other sites; protects against cross-site request forgery (CSRF). Modern browsers treat a cookie without it as Lax; None requires Secure.
Max-Age / Expires
How long it lives. Without them it is a session cookie, deleted when the browser session ends.
Analogy

A cookie is a cloakroom ticket. The cloakroom (server) keeps your coat (session data); you only carry the ticket number and show it every time. Anyone who steals the ticket gets your coat, which is why session cookies must be Secure and HttpOnly.

APIs used by mobile apps often send a token instead, in the header Authorization: Bearer <token>. Same idea: the state travels with each request.

Cookies and state

Q1Which cookie attribute prevents JavaScript from reading the cookie?

HttpOnly hides the cookie from document.cookie, limiting XSS damage. Secure restricts it to HTTPS; SameSite controls cross-site sending (CSRF).

Q2The server sends Set-Cookie: session=abc123; Secure; HttpOnly; SameSite=Lax; Path=/; Max-Age=3600. When does the browser stop sending this cookie?

Max-Age=3600 gives it a one-hour lifetime. "When the tab is closed" is tempting, but that describes a session cookie, which has neither Max-Age nor Expires.

Q3Which cookie attribute mainly protects against cross-site request forgery (CSRF)?

SameSite controls whether the cookie is sent on requests started by other sites, which is what CSRF abuses. HttpOnly is tempting but protects against a different attack: JavaScript reading the cookie (XSS).

Q4True or false: modern browsers accept a cookie with SameSite=None only if it also has Secure.

True. SameSite=None lets the cookie travel on cross-site requests, so browsers require it to be HTTPS-only. Without a SameSite attribute at all, browsers treat the cookie as Lax.

7HTTP versions

The meaning of HTTP (methods, status codes, headers) is defined once in RFC 9110 and is the same in every version. What changes between versions is how the messages are put on the wire.

VersionYear / specTransportKey featuresMain limitation
HTTP/1.01996, RFC 1945TCPHeaders, status codes, content typesNew TCP connection for every request
HTTP/1.11997; current text RFC 9112 (2022)TCPText format, persistent (keep-alive) connections, mandatory Host, chunked transferOne request at a time per connection: head-of-line blocking; browsers open ~6 connections per host
HTTP/22015; current text RFC 9113 (2022)TCP (browsers require TLS)Binary framing, many parallel streams multiplexed on one connection, HPACK header compressionA single lost TCP packet stalls all streams (TCP-level head-of-line blocking)
HTTP/32022, RFC 9114QUIC over UDP, TLS 1.3 built inIndependent streams (no TCP head-of-line blocking), faster setup (transport + TLS in 1 RTT, 0-RTT on resumption), connection migration (Wi-Fi → 4G), QPACK header compressionUDP is sometimes blocked by firewalls; clients fall back to HTTP/2
Analogy

HTTP/1.1 is a single-lane road: cars (requests) wait behind each other. HTTP/2 is a multi-lane road built on one bridge: if the bridge (TCP) closes for a moment, every lane stops. HTTP/3 gives each lane its own small bridge (QUIC streams), so one problem only stops one lane.

Common mistake

"HTTP always uses TCP" is no longer true. HTTP/3 runs on QUIC over UDP. A browser usually learns that a server supports HTTP/3 from an Alt-Svc response header (or a DNS HTTPS record) and switches on the next connection. Also note: HTTP/2 Server Push has been removed from major browsers; use 103 Early Hints instead.

HTTP versions

Q1HTTP/3 runs on top of:

HTTP/3 (RFC 9114) uses QUIC over UDP, with TLS 1.3 built in. This removes TCP head-of-line blocking and speeds up connection setup.

Q2What is the main improvement of HTTP/2 over HTTP/1.1?

HTTP/2 multiplexes streams on one TCP connection and compresses headers (HPACK). It still uses TCP; UDP arrived with HTTP/3. The Host header became mandatory in HTTP/1.1.

Q3How does a browser usually learn that a server supports HTTP/3?

The server advertises HTTP/3 with Alt-Svc (or a DNS HTTPS record) and the browser switches on the next connection. 101 is tempting, but it is used to upgrade an HTTP/1.1 connection, for example to WebSocket; it cannot move a TCP connection to QUIC.

Q4True or false: in HTTP/2, a single lost TCP packet can stall every stream on that connection.

True. All HTTP/2 streams share one TCP connection, and TCP delivers bytes in order, so one gap holds everything back (TCP-level head-of-line blocking). HTTP/3 fixes this with independent QUIC streams.

Q5Which RFC is the current text of HTTP/1.1 message syntax?

RFC 9112 (2022) is HTTP/1.1. RFC 1945 is the old HTTP/1.0, RFC 9114 is HTTP/3 and RFC 8446 is TLS 1.3. The meaning shared by all versions (methods, status codes) is in RFC 9110.

8HTTP vs HTTPS

HTTP sends everything in clear text: anyone on the path (public Wi-Fi, a compromised router, an ISP) can read and even modify it; this is a man-in-the-middle (MITM) attack. Default port 80.

HTTPS is HTTP sent inside a TLS connection. TLS gives three guarantees: confidentiality (encryption), integrity (tampering is detected) and authentication (a certificate proves you are talking to the real server). Default port 443. It is essential for the modern web.

Key takeaway

HTTPS protects login credentials, payments and all personal data in transit. Always use HTTPS in production, for every page, not only the login form.

Common mistake

Saying "SSL". SSL 2.0 and 3.0 are broken and prohibited (SSL 3.0 since RFC 7568, 2015), and TLS 1.0/1.1 were deprecated in 2021 (RFC 8996). Today HTTPS means TLS 1.2 or TLS 1.3 (RFC 8446). People still say "SSL certificate" out of habit; the certificates are used with TLS.

Exam tip

What does HTTPS hide? The path, query string, headers, cookies and body are encrypted. It does not hide the server's IP address, and the domain name is usually still visible (in the DNS lookup and in the TLS SNI field) unless encrypted DNS and Encrypted Client Hello are used.

HTTP vs HTTPS

Q1What does HTTPS add to HTTP to provide security?

HTTPS = HTTP inside TLS, which gives confidentiality, integrity and server authentication via certificates. SSL is the obsolete predecessor; today it is TLS 1.2 or 1.3.

Q2The default port for HTTPS is:

443 is HTTPS; 80 is plain HTTP; 8080 is a common alternative for development servers; 22 is SSH.

Q3On HTTPS, which of these can a network eavesdropper still normally see?

Path, query, headers, cookies and body are inside TLS. The IP is needed for routing, and the domain leaks through DNS and the SNI field unless encrypted DNS and Encrypted Client Hello are used.

Q4True or false: today an "SSL certificate" is actually used with TLS 1.2 or TLS 1.3, and SSL 3.0 itself is prohibited.

True. SSL 2.0 and 3.0 are broken and prohibited (SSL 3.0 by RFC 7568), and TLS 1.0/1.1 were deprecated in 2021. The name "SSL certificate" survived out of habit; the same X.509 certificates are used with TLS.

9Inside HTTPS: TLS 1.3, certificates, HSTS

The TLS 1.3 handshake

Before any HTTP data flows, client and server run a handshake. In TLS 1.3 it takes a single round trip (1-RTT), compared with two in TLS 1.2.

  1. ClientHello. The client sends the TLS versions and cipher suites it supports, a random number, the server name (SNI) and a key_share: its half of an ephemeral (EC)Diffie-Hellman key exchange, guessed in advance.
  2. ServerHello. The server picks the cipher suite and sends its own key_share. Both sides can now compute the same shared secret; everything after this point is encrypted.
  3. Certificate + CertificateVerify. The server sends its certificate chain and signs the handshake with its private key, proving it owns the certificate.
  4. Server Finished. A MAC over the whole handshake, so any tampering with earlier messages is detected.
  5. Client verifies, sends Finished and immediately its first encrypted HTTP request. From now on both sides use fast symmetric encryption (e.g. AES-GCM or ChaCha20-Poly1305).
Key idea

Asymmetric cryptography (key exchange and signatures) is used only during the handshake, to agree on keys and prove identity. The bulk data is encrypted with fast symmetric keys. Because the key exchange is ephemeral, TLS 1.3 always has forward secrecy: stealing the server's private key later does not decrypt recorded past sessions.

Certificates and the chain of trust

A certificate (X.509) says "the public key K belongs to example.com", signed by a Certificate Authority (CA). The browser checks:

Server certificate (example.com)signed by →Intermediate CAsigned by →Root CA in your OS/browser trust store
  • The chain of signatures leads to a root the device already trusts.
  • The domain in the address bar matches a name in the certificate (Subject Alternative Name).
  • The certificate is within its validity dates and has not been revoked.

Free, automated CAs such as Let's Encrypt (using the ACME protocol) made HTTPS universal. Maximum certificate lifetimes are being shortened by the CA/Browser Forum (from 398 days towards 47 days by 2029), so automatic renewal is now the norm.

Common mistake

Clicking through a certificate warning, or disabling certificate validation in code "to make it work". That removes authentication, so an attacker can impersonate the server and read everything despite the encryption.

HSTS

If a user types example.com, the first request may go out over plain HTTP and be redirected to HTTPS; an attacker can intercept that first request (an SSL stripping attack). HSTS fixes this: the site sends

Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

and the browser then refuses to use plain HTTP for that site for the given time (here one year), upgrading every request to HTTPS itself and not allowing users to bypass certificate errors. Sites on the browser HSTS preload list are protected even on the very first visit.

Mixed content

An HTTPS page that loads a script, stylesheet or iframe over http:// has mixed content. Browsers block such active content, because a modified script would control the whole secure page; images and media are upgraded to HTTPS automatically or blocked. Fix: load every resource over HTTPS.

Inside HTTPS: TLS 1.3, certificates, HSTS

Q1How many round trips does a full TLS 1.3 handshake need before the client can send its request?

TLS 1.3 needs 1-RTT (TLS 1.2 needed 2). 0-RTT exists only when resuming an earlier session, and its early data can be replayed, so it is limited to safe requests.

Q2In the TLS 1.3 handshake, how does the server prove that it really owns its certificate?

Only the holder of the private key can produce the CertificateVerify signature. Sending the certificate is the tempting answer, but certificates are public: anyone can copy and send one.

Q3What does the HSTS header tell the browser?

Strict-Transport-Security makes the browser upgrade every request to HTTPS itself, defeating SSL-stripping attacks. Cross-origin reading is CORS, not HSTS.

Q4True or false: because TLS 1.3 uses an ephemeral key exchange, an attacker who steals the server's private key later can decrypt sessions they recorded earlier.

False. That is exactly what forward secrecy prevents: the session keys came from one-time (ephemeral) Diffie-Hellman values that were thrown away, so the long-term private key does not reveal them.

Q5An HTTPS page contains <script src="http://cdn.example.com/app.js">. What does a modern browser do?

A script loaded over plain HTTP could be modified in transit and would then control the secure page, so browsers block active mixed content. Images and media may be upgraded automatically, which is why "loads it normally" is tempting, but scripts are not.

10CORS: why the playground can call an API

Browsers enforce the same-origin policy. An origin is the triple scheme + host + port, e.g. https://hassanlamaa.github.io. JavaScript on this page may send a request to another origin, but it may only read the response if that server opts in with CORS headers:

Access-Control-Allow-Origin: *

JSONPlaceholder sends exactly this, so the playground below works from a static GitHub Pages site. For "non-simple" requests (PUT, PATCH, DELETE, or a JSON Content-Type), the browser first sends an automatic preflight OPTIONS request to ask permission, then the real one.

Common mistake

CORS is not a server security wall. It is a rule the browser follows to protect users. curl, Postman or a Java program ignore CORS completely. Protect APIs with authentication, not with CORS.

CORS

Q1Why can JavaScript on a GitHub Pages site read responses from JSONPlaceholder?

The other server must opt in with CORS headers. HTTPS alone is not enough, and PUT/PATCH/DELETE work too because the server answers the preflight OPTIONS request.

Q2Which of these has the same origin as https://lt.example.com?

An origin is scheme + host + port; the path does not matter. The first option changes the scheme, the second the port, and the last the host, so each of those is a different origin.

Q3True or false: CORS prevents curl or a Java program from calling an API that does not send Access-Control-Allow-Origin.

False. CORS is a rule that browsers follow to protect users. curl, Postman and Java ignore it completely, which is why APIs must be protected with authentication, not CORS.

Q4From this page, which fetch makes the browser send a preflight OPTIONS request first?

Non-simple requests (PUT, PATCH, DELETE, or a JSON Content-Type) need permission first. A simple GET is tempting because it is also cross-origin, but simple requests are sent directly; only reading the response needs the CORS header.

12HTTP from Java

Since Java 11, the standard library includes java.net.http.HttpClient: a modern client that supports HTTP/1.1 and HTTP/2, TLS, timeouts, redirects and asynchronous calls. Prefer it to the old HttpURLConnection.

HttpClientDemo.java

import java.io.IOException;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.time.Duration;

public class HttpClientDemo {
    public static void main(String[] args) {
        // One client can be reused for many requests (it pools connections).
        HttpClient client = HttpClient.newBuilder()
                .version(HttpClient.Version.HTTP_2)          // falls back to HTTP/1.1 if needed
                .connectTimeout(Duration.ofSeconds(10))
                .followRedirects(HttpClient.Redirect.NORMAL)
                .build();

        // GET: read a resource
        HttpRequest get = HttpRequest.newBuilder(
                    URI.create("https://jsonplaceholder.typicode.com/posts/1"))
                .header("Accept", "application/json")
                .timeout(Duration.ofSeconds(10))
                .GET()
                .build();

        // POST: create a resource with a JSON body
        String json = "{\"title\":\"From Java\",\"body\":\"HttpClient demo\",\"userId\":1}";
        HttpRequest post = HttpRequest.newBuilder(
                    URI.create("https://jsonplaceholder.typicode.com/posts"))
                .header("Content-Type", "application/json; charset=UTF-8")
                .POST(HttpRequest.BodyPublishers.ofString(json))
                .build();

        try {
            HttpResponse<String> r1 = client.send(get, HttpResponse.BodyHandlers.ofString());
            System.out.println("GET  -> " + r1.statusCode() + " via " + r1.version());
            System.out.println(r1.body());

            HttpResponse<String> r2 = client.send(post, HttpResponse.BodyHandlers.ofString());
            System.out.println("POST -> " + r2.statusCode());   // 201 Created
            System.out.println(r2.body());
        } catch (IOException e) {
            System.err.println("Network error: " + e.getMessage());
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();                // restore the interrupt flag
            System.err.println("Request interrupted");
        }
    }
}
Tip

For non-blocking code, use client.sendAsync(request, BodyHandlers.ofString()), which returns a CompletableFuture. On Java 21+, plain blocking send calls inside virtual threads scale to thousands of concurrent requests. Java does not apply CORS: it can call any server.

Outdated code

The constructor new URL(String) is deprecated since Java 20 because it does not validate URLs properly. Parse with URI and convert when an API still needs a URL:

import java.net.MalformedURLException;
import java.net.URI;
import java.net.URL;

public class UrlDemo {
    public static void main(String[] args) throws MalformedURLException {
        // URL old = new URL("https://example.com/a?b=1");     // deprecated since Java 20
        URL url = URI.create("https://example.com/a?b=1").toURL();
        System.out.println(url.getHost() + " " + url.getPath() + " " + url.getQuery());
    }
}

HTTP from Java

Q1In HttpClientDemo, what does this line print for the POST to https://jsonplaceholder.typicode.com/posts?
System.out.println("POST -> " + r2.statusCode());

Creating a resource with POST returns 201 Created, as the comment in the code and the playground show. 200 is tempting because it is the general success code, but this API reports the creation precisely.

Q2Which line is outdated in new Java code?

The URL(String) constructor is deprecated since Java 20 because it validates poorly. URI.create(...).toURL() is tempting to flag because it is longer, but it is the recommended replacement.

Q3Which checked exceptions must code that calls client.send(request, BodyHandlers.ofString()) handle?

send declares IOException (network failures) and InterruptedException (the waiting thread was interrupted), which is why the demo catches both. UnknownHostException is a subclass of IOException, but SQLException has nothing to do with HTTP.

Q4True or false: java.net.http.HttpClient applies the browser's CORS rules, so it can only read responses from servers that send Access-Control-Allow-Origin.

False. CORS is enforced only by browsers. A Java program can call any server; the lesson's tip says this explicitly.

Q5On Java 21+, what lets plain blocking client.send(...) calls scale to thousands of concurrent requests?

Virtual threads are cheap, so blocking in send costs little and thousands can wait at once. HTTP/2 is tempting because it multiplexes requests, but it does not make blocking threads cheaper; sendAsync is the other route.

13Final review

Final review: mixed questions from the whole lesson

Q1A mobile app's PUT /profile request times out and the app cannot tell whether the server processed it. What is true?

Sending the same PUT again leaves the server in the same state, so automatic retries are safe. "A second profile" is what could happen with POST, which is not idempotent.

Q2A site redirects http:// to https:// with a 301 but sends no HSTS header. Which attack still works against the first plain-HTTP request?

The first request leaves in clear text, so an attacker can intercept it and never pass on the redirect. HSTS (and the preload list) makes the browser use HTTPS itself. CORS is unrelated: it controls cross-origin reading, not encryption.

Q3True or false: HTTP/3 still uses TLS, because TLS 1.3 is built into QUIC.

True. HTTP/3 runs over QUIC over UDP, and QUIC integrates the TLS 1.3 handshake, merging transport and TLS setup into one round trip. "UDP means no encryption" is the tempting mistake.

Q4A login API wants to start a browser session. Which response fits best?

The server stores state in the browser with Set-Cookie, protected by Secure, HttpOnly and SameSite. The Cookie option is tempting, but Cookie is the request header the browser sends back, not something a server sets.

Q5The Java client is built with .version(HttpClient.Version.HTTP_2) but the server only speaks HTTP/1.1. What happens?

HTTP/2 is negotiated (with ALPN over TLS); if the server does not support it, HttpClient uses HTTP/1.1, as the comment in the demo says. You can check what was used with response.version().

Q6True or false: status 401 means "we know who you are, but you are not allowed".

False. That describes 403 Forbidden. 401 Unauthorized means the client is not authenticated: credentials are missing or invalid, so it should log in.

Summary

  • HTTP is a stateless request/response protocol: request line + headers + body, answered by status line + headers + body.
  • Methods: GET (safe), POST (create, not idempotent), PUT (replace, idempotent), PATCH (partial, not guaranteed idempotent), DELETE (idempotent). Safe methods: GET, HEAD, OPTIONS, TRACE.
  • Status classes: 1xx info, 2xx success, 3xx redirect, 4xx client error, 5xx server error. 401 = not authenticated, 403 = not allowed.
  • State comes from cookies (use Secure, HttpOnly, SameSite) or tokens in Authorization.
  • HTTP/1.1 (RFC 9112) is text over TCP; HTTP/2 (RFC 9113) multiplexes binary streams over TCP; HTTP/3 (RFC 9114) runs over QUIC/UDP.
  • HTTPS = HTTP over TLS 1.2/1.3 on port 443: encryption, integrity, authentication via CA-signed certificates. TLS 1.3 handshakes in 1 RTT with forward secrecy. HSTS forces HTTPS; avoid mixed content.
  • Browsers apply CORS; servers opt in with Access-Control-Allow-Origin. In Java use HttpClient (Java 11+) and URI.create(...).toURL() instead of new URL(String).
