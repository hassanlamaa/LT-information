1Principles

Client/server is a distributed model where clients request services and servers provide them. Clients usually handle presentation (the user interface), while servers centralise data and services so that many clients can share them.

Client
A program that starts the conversation by sending a request, for example a web browser, a mobile banking app or an email app. It is the active side.
Server
A program that waits ("listens") for requests and answers them, for example a web server or a database server. It is the passive side. The word also describes the machine that runs such programs.
Service
The job the server offers: serving web pages, storing files, running queries, delivering mail.
Key idea

"Client" and "server" are roles, not types of hardware. A laptop can run a server program, and a big server can act as a client when it asks another server (for example a database) for data.

Analogy

A restaurant. You (the client) read the menu and place an order. The kitchen (the server) waits for orders, prepares them and sends the dish back. The menu and the way you order are the protocol. The kitchen serves many tables at once, and if the kitchen closes, nobody eats: that is the single point of failure.

1.1 Communication (request/response)

Every client/server exchange follows the same cycle: the client sends a request, the server processes it, and the server returns a response.

  • Client sends a request → server processes → server returns a response.
  • Protocol: the agreed rules for the conversation: message format, order and meaning (HTTP, FTP, SMTP, etc.). Without a shared protocol the two sides cannot understand each other.
  • IP address: identifies a host (a machine) on the network, for example 192.168.1.10 (IPv4) or 2001:db8::10 (IPv6).
  • Port: a 16-bit number (0–65535) that identifies a service endpoint on that host. The IP address finds the building; the port finds the apartment.
  • Scheduling: servers prioritise, queue and limit requests (for example with rate limits and thread pools) to protect their resources when many clients arrive at once.

Scenario: online banking

  1. The browser (client) sends your login to the bank's web server over HTTPS.
  2. The web server passes the request on; behind it, database servers are queried (and they may chain to other servers).
  3. The application server applies business logic: is the password right, is the account locked, which accounts may this user see?
  4. The web server responds with your account data, formatted as a page.

Notice that one user action triggered several client/server exchanges. The web server was a server to your browser and a client to the application and database servers.

1.2 Advantages & disadvantages

AdvantagesDisadvantages
Centralised management (backup, security, administration in one place)Server cost and complexity (hardware, licences, skilled staff)
Scalability and flexible resource growth (add CPU, RAM or more servers)Single point of failure: if the only server goes down, its service is unavailable to every client
Enhanced data sharing and access control (one copy of the data, one place to set permissions)Potential congestion when many clients send requests at the same time
Common mistake

Saying "if the server fails, the whole network fails". The network keeps working; the service that server provided becomes unavailable. Real systems reduce this risk with redundancy: several servers behind a load balancer, database replicas, and backups in another location.

Exam tip

When asked for advantages and disadvantages, give a matched pair and a mitigation. Example: "Centralisation makes backups easy, but creates a single point of failure; this is reduced with redundant servers and load balancing."

2Communication & Protocols

A client reaches a service with three pieces of information: the server's IP address, the port of the service, and the transport protocol (TCP or UDP). The combination of IP address + port + protocol on each side is called a socket. Programs read from and write to sockets the way they read and write files.

Ports (well-known examples)

  • Well-known ports: 0–1023. Reserved for standard services. On Linux and macOS, a normal user cannot open a server on them without extra privileges.
  • Registered ports: 1024–49151. Assigned by IANA to specific applications (for example 3306 MySQL, 5432 PostgreSQL, 8080 alternative HTTP).
  • Dynamic (ephemeral) ports: 49152–65535. Picked automatically by the operating system for the client side of a connection.
Example

When your browser opens https://example.com, the connection might be 192.168.1.20:51344 → 93.184.215.14:443. The server port (443) is fixed and well known; the client port (51344) is ephemeral and changes every time.

TCP and UDP

TCP

  • Reliable, connection-oriented, in-order delivery.
  • Use cases: web, email, file transfer (HTTP/1.1 and HTTP/2, FTP, SMTP, SSH…).
  • Header 20 bytes minimum, up to 60 with options; flow control and congestion control.

UDP

  • Unreliable (best effort), connectionless, fast; each datagram travels on its own.
  • Use cases: DNS, VoIP, live streaming, online games, SNMP, DHCP, and QUIC (which carries HTTP/3).
  • Header 8 bytes; applications handle ordering and reliability if they need them.
FeatureTCPUDP
ConnectionSet up first with a three-way handshake (SYN, SYN-ACK, ACK)None: just send
ReliabilityLost segments are retransmittedLost datagrams stay lost
OrderBytes arrive in the order sentDatagrams may arrive out of order
Data unitByte stream (no message boundaries)Separate messages (datagrams)
Header size20–60 bytes8 bytes
Speed / latencySlower to start, steadyLower latency, no handshake
Java classesSocket, ServerSocketDatagramSocket, DatagramPacket
Analogy

TCP is a phone call: you dial, the other person answers, and you both know if the line drops. UDP is sending postcards: each one is independent, cheap and fast, but some may never arrive and they can arrive in any order.

Common mistake

"UDP is useless because it is unreliable." UDP is chosen exactly when a late packet is worse than a lost one (a voice call cannot wait for a retransmission) or when the application adds its own reliability. QUIC, the transport under HTTP/3, is built on UDP and adds reliability and encryption itself.

Exam tip

For "TCP or UDP?" questions, name the deciding property: needs every byte in order (file, web page, email) → TCP; needs low delay and tolerates loss (voice, live video, games, simple DNS lookups) → UDP.

3Server Types & Roles

Servers are classified by the service they provide. One physical machine can host several of these roles, and one role can be spread over many machines.

File server

Centralised file storage and retrieval. Clients open, save and share files over protocols such as SMB (Windows shares) or NFS.

Database server

Runs a DBMS. Clients send SQL; the server executes the queries and returns only the result rows. Examples: PostgreSQL, MySQL, Oracle, Microsoft SQL Server.

Transaction server

Groups SQL statements into atomic transactions: all succeed or none do. This is the basis of OLTP (Online Transaction Processing), such as card payments and seat bookings.

Groupware server

Collaboration tools: shared calendars, mail, shared documents, online meetings. Examples: Microsoft Exchange, or cloud suites such as Microsoft 365 and Google Workspace.

Web server

Speaks HTTP and serves static content (HTML, CSS, images) from disk. Examples: Nginx, Apache HTTP Server, Microsoft IIS.

Application server

Generates dynamic content and runs the business logic layer. Examples: Apache Tomcat, WildFly, or a Node.js, Spring Boot or Django application.

Transaction
A group of operations treated as one unit. Example: "take 100 from account A and add 100 to account B" must never half-happen.
ACID
The four guarantees of a transaction: Atomicity (all or nothing), Consistency (rules stay true), Isolation (concurrent transactions do not interfere), Durability (once committed, it survives a crash).
Static vs dynamic content
Static content is the same file for everyone (a logo). Dynamic content is built per request (your account balance).
NeedServer type
Staff share a folder of reportsFile server
Search 2 million student records with SQLDatabase server
Process thousands of card payments per second safelyTransaction server (OLTP)
Team calendar and meeting roomsGroupware server
Serve the university's public HTML pages and imagesWeb server
Show each student their own timetableApplication server
Tip

The line between web server and application server is blurred today: Nginx often serves static files and forwards dynamic requests to an application server behind it (a "reverse proxy"). In exams, keep the classic split: web server = static, application server = dynamic + business logic.

4Architectures (2-Tier, 3-Tier, N-Tier)

An application has three kinds of work: presentation (what the user sees), business logic (the rules) and data (storage). A tier is a part of the system that runs separately, usually on its own machine. The architectures differ in where they put these three kinds of work.

2-tier

Client: UI + some logic⇄Database server: data + logic

The client talks directly to the database server. Simple, with high performance on a local network, but limited scalability: every client holds a database connection, business rules are duplicated in every client, and updating logic means updating every installed client.

Example: a desktop stock-control program in a small shop that connects straight to a database on the back-office PC.

3-tier

Client: presentation⇄Application server: business logic⇄Database server: data

A middle tier holds the business logic. Better scalability and security: the database is no longer exposed to clients, the logic lives in one place, and the middle tier can be duplicated behind a load balancer.

Example: a university portal: browser → web/application server → student database.

N-tier

Client⇄Web tier⇄Services / microservices⇄Cache⇄Databases

Multiple middle-tier components (services, microservices, caches, message queues). Improved maintainability and load distribution, because each part can be scaled, updated and secured separately, at the cost of more network hops and more operational complexity.

Criterion2-tier3-tierN-tier
Where is business logic?Client and/or databaseApplication serverSpread across several services
ScalabilityLowGoodVery good
SecurityDatabase exposed to clientsDatabase hidden behind middle tierEach tier isolated; more to secure
MaintenanceUpdate every clientUpdate one middle tierUpdate services independently
Complexity / costLowestMediumHighest
Typical useSmall LAN appsMost web applicationsLarge-scale and cloud systems
Common mistake

Mixing up tiers and layers. Layers are a logical split in the code (presentation, logic, data classes). Tiers are a physical split into separately running parts. A 3-layer program can still run as a single tier on one machine.

Exam tip

"Why is 3-tier more secure than 2-tier?" Answer: clients never connect to the database directly; only the application server does, so the database can sit on a private network and the business rules are enforced on a machine the user does not control.

5Programming Examples

The classic examples from the course notes, cleaned up so they compile, with corrections marked in comments. All of them use java.net, which is still the standard socket API in current Java (JDK 21 and 25 are the long-term-support releases).

Key idea

Every TCP server follows the same pattern: create a ServerSocket on a port → accept() a client → get input/output streams → read request, write response → close. The client mirrors it: create a Socket to host:port → write → read → close.

  1. new ServerSocket(port) reserves the port and starts listening.
  2. accept() blocks (waits) until a client connects, then returns a new Socket for that one client.
  3. getInputStream() / getOutputStream() give byte streams; wrap them in readers and writers to work with text lines.
  4. close() the client socket when done; the ServerSocket keeps listening for the next client.

TCP socket example

A simple server that uppercases one line of input, and a client that sends a line and prints the response. Run the server first, then the client in a second terminal.

TCPServer.java

import java.io.*;
import java.net.*;

public class TCPServer {
    public static void main(String args[]) throws Exception {
        String clientSentence;
        String capitalizedSentence;
        ServerSocket welcomeSocket = new ServerSocket(6789);

        while (true) {
            Socket connectionSocket = welcomeSocket.accept();   // waits for a client
            BufferedReader inFromClient = new BufferedReader(new
                InputStreamReader(connectionSocket.getInputStream()));
            DataOutputStream outToClient = new
                DataOutputStream(connectionSocket.getOutputStream());

            clientSentence = inFromClient.readLine();
            capitalizedSentence = clientSentence.toUpperCase() + '\n';
            outToClient.writeBytes(capitalizedSentence);
            connectionSocket.close();   // added: release this client's socket
        }
    }
}

TCPClient.java

import java.io.*;
import java.net.*;

public class TCPClient {
    public static void main(String argv[]) throws Exception {
        String sentence;
        String modifiedSentence;
        BufferedReader inFromUser = new BufferedReader(new InputStreamReader(System.in));
        Socket clientSocket = new Socket("localhost", 6789);

        BufferedReader inFromServer = new BufferedReader(new
            InputStreamReader(clientSocket.getInputStream()));

        sentence = inFromUser.readLine();

}
Common mistake

Forgetting the '\n'. readLine() waits until it sees a line ending, so if the client sends text without one, both programs hang. Also note that DataOutputStream.writeBytes() keeps only the low byte of each character, so it is safe for plain ASCII only. For any language (Arabic, French accents) use new PrintWriter(new OutputStreamWriter(out, StandardCharsets.UTF_8), true).

Modern version with try-with-resources and UTF-8 
try (ServerSocket server = new ServerSocket(6789)) {
    while (true) {
        try (Socket s = server.accept();
             var in  = new BufferedReader(new InputStreamReader(s.getInputStream(), StandardCharsets.UTF_8));
             var out = new PrintWriter(new OutputStreamWriter(s.getOutputStream(), StandardCharsets.UTF_8), true)) {
            String line = in.readLine();
            if (line != null) out.println(line.toUpperCase());
        }   // streams and socket are closed automatically, even after an exception
    }
}

UDP socket example

The same uppercase service over UDP. There is no accept() and no connection: the server simply receives a datagram, reads the sender's address and port from it, and sends a datagram back.

UDPServer.java

import java.io.*;
import java.net.*;

class UDPServer {
    public static void main(String args[]) throws Exception {
        try {
            DatagramSocket serverSocket = new DatagramSocket(9876);
            byte[] receiveData = new byte[1024];
            byte[] sendData  = new byte[1024];

            while (true) {
                receiveData = new byte[1024];
                DatagramPacket receivePacket =
                    new DatagramPacket(receiveData, receiveData.length);
                System.out.println("Waiting for datagram packet");
                serverSocket.receive(receivePacket);

                // corrected: use only the bytes actually received, not the whole 1024-byte buffer
                String sentence = new String(receivePacket.getData(), 0, receivePacket.getLength());
                InetAddress IPAddress = receivePacket.getAddress();
                int port = receivePacket.getPort();
                System.out.println("From: " + IPAddress + ":" + port);
                System.out.println("Message: " + sentence);

                String capitalizedSentence = sentence.toUpperCase();
                sendData = capitalizedSentence.getBytes();
                DatagramPacket sendPacket =
                    new DatagramPacket(sendData, sendData.length, IPAddress, port);
                serverSocket.send(sendPacket);
            }
        } catch (SocketException ex) {
            System.out.println("UDP Port 9876 is occupied.");
            System.exit(1);
        }
    }
}

UDPClient.java

import java.io.*;
import java.net.*;

class UDPClient {
    public static void main(String args[]) throws Exception {
        try {
            String serverHostname = new String("127.0.0.1");
            if (args.length > 0)
                serverHostname = args[0];

            BufferedReader inFromUser =
                new BufferedReader(new InputStreamReader(System.in));
            DatagramSocket clientSocket = new DatagramSocket();
            InetAddress IPAddress = InetAddress.getByName(serverHostname);
            System.out.println("Attempting to connect to " + IPAddress +
                               " via UDP port 9876");

            byte[] sendData = new byte[1024];
            byte[] receiveData = new byte[1024];

            System.out.print("Enter Message: ");
            String sentence = inFromUser.readLine();
            sendData = sentence.getBytes();
            System.out.println("Sending " + sendData.length + " bytes to server.");
            DatagramPacket sendPacket =
                new DatagramPacket(sendData, sendData.length, IPAddress, 9876);
            clientSocket.send(sendPacket);

            DatagramPacket receivePacket =
                new DatagramPacket(receiveData, receiveData.length);
            System.out.println("Waiting for return packet");
            clientSocket.setSoTimeout(10000);   // wait at most 10 s: UDP may lose the reply

            try {
                clientSocket.receive(receivePacket);
                String modifiedSentence =
                    new String(receivePacket.getData(), 0, receivePacket.getLength());
                InetAddress returnIPAddress = receivePacket.getAddress();
                int port = receivePacket.getPort();
                System.out.println("From server at: " + returnIPAddress + ":" + port);
                System.out.println("Message: " + modifiedSentence);
            } catch (SocketTimeoutException ste) {
                System.out.println("Timeout Occurred: Packet assumed lost");
            }
            clientSocket.close();
        } catch (UnknownHostException ex) {
            System.err.println(ex);
        } catch (IOException ex) {
            System.err.println(ex);
        }
    }
}
Why the timeout matters

With TCP, a lost segment is resent automatically. With UDP, if the reply is lost, receive() would wait forever. setSoTimeout(10000) makes it give up after 10 seconds and throw SocketTimeoutException, which is how a UDP client detects loss.

DayTime protocol (TCP)

The smallest useful server: when a client connects, it sends the current date and time and closes the connection. The real Daytime protocol (RFC 867) uses port 13; the example uses 9090 because ports below 1024 need administrator rights on most systems.

DateServer.java

import java.io.IOException;
import java.io.PrintWriter;
import java.net.ServerSocket;
import java.net.Socket;
import java.time.ZonedDateTime;

/**
 * A TCP server that runs on port 9090.  When a client connects, it
 * sends the client the current date and time, then closes the
 * connection with that client.  Arguably just about the simplest
 * server you can write.
 */
public class DateServer {
    public static void main(String[] args) throws IOException {
        ServerSocket listener = new ServerSocket(9090);
        try {
            while (true) {
                Socket socket = listener.accept();
                try {
                    PrintWriter out = new PrintWriter(socket.getOutputStream(), true);
                    // original: out.println(new Date().toString());  java.util.Date is legacy;
                    // java.time (Java 8+) is the current date/time API.
                    out.println(ZonedDateTime.now().toString());
                } finally {
                    socket.close();
                }
            }
        } finally {
            listener.close();
        }
    }
}

Tip

The try … finally { socket.close(); } pattern in DateServer guarantees the socket is closed even if writing fails. Since Java 7 the shorter form is try (Socket socket = listener.accept()) { … }, which closes it automatically.

GUI chat (multithreaded)

The servers above handle one client at a time: while one client is being served, the others wait. A chat server must serve many clients at the same time, so it starts a new thread for each client. The main thread only accepts connections; each Handler thread talks to one client.

The chat uses its own tiny text protocol:

MessageSent byMeaning
SUBMITNAMEServer"Send me a screen name." Repeated until the name is unique.
(a name)ClientThe requested screen name.
NAMEACCEPTEDServerName registered; the client may now send messages.
(any text)ClientA chat message to broadcast.
MESSAGE name: textServerA broadcast message to display.

ChatServer.java

import java.io.BufferedReader;
import java.io.IOException;
import java.io.InputStreamReader;
import java.io.PrintWriter;
import java.net.ServerSocket;
import java.net.Socket;
import java.util.Set;
import java.util.concurrent.ConcurrentHashMap;

/**
 * A multithreaded chat room server.  When a client connects the
 * server requests a screen name by sending the client the
 * text "SUBMITNAME", and keeps requesting a name until
 * a unique one is received.  After a client submits a unique
 * name, the server acknowledges with "NAMEACCEPTED".  Then
 * all messages from that client will be broadcast to all other
 * clients that have submitted a unique screen name.  The
 * broadcast messages are prefixed with "MESSAGE ".
 *
 * Because this is just a teaching example to illustrate a simple
 * chat server, there are a few features that have been left out.
 * Two are very useful and belong in production code:
 *
 *     1. The protocol should be enhanced so that the client can
 *        send clean disconnect messages to the server.
 *
 *     2. The server should do some logging.
 */
public class ChatServer {

    /** The port that the server listens on. */
    private static final int PORT = 9001;

    /**
     * The set of all names of clients in the chat room.  Maintained
     * so that we can check that new clients are not registering name
     * already in use.
     * Corrected: the original used a plain HashSet, which is not thread-safe.
     */
    private static final Set<String> names = ConcurrentHashMap.newKeySet();

    /**
     * The set of all the print writers for all the clients.  This
     * set is kept so we can easily broadcast messages.
     * Corrected: a plain HashSet can throw ConcurrentModificationException
     * when one thread broadcasts while another adds or removes a client.
     */
    private static final Set<PrintWriter> writers = ConcurrentHashMap.newKeySet();

    /**
     * The application main method, which just listens on a port and
     * spawns handler threads.
     */
    public static void main(String[] args) throws Exception {
        System.out.println("The chat server is running.");
        ServerSocket listener = new ServerSocket(PORT);
        try {
            while (true) {
                new Handler(listener.accept()).start();
            }
        } finally {
            listener.close();
        }
    }

    /**
     * A handler thread class.  Handlers are spawned from the listening
     * loop and are responsible for dealing with a single client
     * and broadcasting its messages.
     */
    private static class Handler extends Thread {
        private String name;
        private Socket socket;
        private BufferedReader in;
        private PrintWriter out;

        /**
         * Constructs a handler thread, squirreling away the socket.
         * All the interesting work is done in the run method.
         */
        public Handler(Socket socket) {
            this.socket = socket;
        }

        /**
         * Services this thread's client by repeatedly requesting a
         * screen name until a unique one has been submitted, then
         * acknowledges the name and registers the output stream for
         * the client in a global set, then repeatedly gets inputs and
         * broadcasts them.
         */
        public void run() {
            try {
                // Create character streams for the socket.
                in = new BufferedReader(new InputStreamReader(
                    socket.getInputStream()));
                out = new PrintWriter(socket.getOutputStream(), true);

                // Request a name from this client.  Keep requesting until
                // a name is submitted that is not already used.  Checking and
                // adding must happen as ONE atomic step: the original did this
                // inside synchronized (names) { ... }; add() on a concurrent
                // set does the same and returns false if the name exists.
                while (true) {
                    out.println("SUBMITNAME");
                    name = in.readLine();
                    if (name == null) {
                        return;
                    }
                    if (names.add(name)) {
                        break;
                    }
                }

                // Now that a successful name has been chosen, add the
                // socket's print writer to the set of all writers so
                // this client can receive broadcast messages.
                out.println("NAMEACCEPTED");
                writers.add(out);

                // Accept messages from this client and broadcast them.
                while (true) {
                    String input = in.readLine();
                    if (input == null) {
                        return;
                    }
                    for (PrintWriter writer : writers) {
                        writer.println("MESSAGE " + name + ": " + input);
                    }
                }
            } catch (IOException e) {
                System.out.println(e);
            } finally {
                // This client is going down!  Remove its name and its print
                // writer from the sets, and close its socket.
                if (name != null) {
                    names.remove(name);
                }
                if (out != null) {
                    writers.remove(out);
                }
                try {
                    socket.close();
                } catch (IOException e) {
                }
            }
        }
    }
}

 * already in use.  When the server sends a line beginning
 * with "NAMEACCEPTED" the client is now allowed to start
 * sending the server arbitrary strings to be broadcast to all
 * chatters connected to the server.  When the server sends a
 * line beginning with "MESSAGE " then all characters following
 * this string should be displayed in its message area.
 */
public class ChatClient {

    BufferedReader in;
    PrintWriter out;
    JFrame frame = new JFrame("Chatter");
    JTextField textField = new JTextField(40);
    JTextArea messageArea = new JTextArea(8, 40);

    /**
     * Constructs the client by laying out the GUI and registering a
     * listener with the textfield so that pressing Return in the
     * listener sends the textfield contents to the server.  Note
     * however that the textfield is initially NOT editable, and
     * only becomes editable AFTER the client receives the NAMEACCEPTED
     * message from the server.
     */
    public ChatClient() {
        // Layout GUI
        textField.setEditable(false);
        messageArea.setEditable(false);
        frame.getContentPane().add(textField, "North");
        frame.getContentPane().add(new JScrollPane(messageArea), "Center");
        frame.pack();

        // Add Listeners
        textField.addActionListener(new ActionListener() {
            /**
             * Responds to pressing the enter key in the textfield by sending
             * the contents of the text field to the server.    Then clear
             * the text area in preparation for the next message.
             */
            public void actionPerformed(ActionEvent e) {
                out.println(textField.getText());
                textField.setText("");
            }
        });
    }

    /** Prompt for and return the address of the server. */
    private String getServerAddress() {
        return JOptionPane.showInputDialog(frame,
            "Enter IP Address of the Server:",
            "Welcome to the Chatter", JOptionPane.QUESTION_MESSAGE);
    }

    /** Prompt for and return the desired screen name. */
    private String getName() {
        return JOptionPane.showInputDialog(frame,
            "Choose a screen name:",
            "Screen name selection", JOptionPane.PLAIN_MESSAGE);
    }

    /** Connects to the server then enters the processing loop. */
    private void run() throws IOException {
        Socket socket = new Socket(getServerAddress(), 9001);
        in = new BufferedReader(new InputStreamReader(socket.getInputStream()));
        out = new PrintWriter(socket.getOutputStream(), true);

        // Process all messages from server, according to the protocol.
        while (true) {
            String line = in.readLine();
            if (line == null) break;                       // server closed
            if (line.startsWith("SUBMITNAME")) {
                out.println(getName());
            } else if (line.startsWith("NAMEACCEPTED")) {
                SwingUtilities.invokeLater(() -> textField.setEditable(true));
            } else if (line.startsWith("MESSAGE")) {
                String text = line.substring(8) + "\n";
                // Swing components must be updated on the event thread.
                SwingUtilities.invokeLater(() -> messageArea.append(text));
            }
        }
        socket.close();
    }

    /** Runs the client as an application with a closeable frame. */
    public static void main(String[] args) throws Exception {
        ChatClient client = new ChatClient();
        client.frame.setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);
        client.frame.setVisible(true);
        client.run();
    }
}
Common mistake

Handling clients inside the accept() loop without threads. The second user then cannot connect until the first leaves. The fix is one thread (or one task in a thread pool) per client. Since Java 21, virtual threads make this cheap even for thousands of clients: Thread.ofVirtual().start(handler) or Executors.newVirtualThreadPerTaskExecutor().

Exam tip

Be ready to explain why the name check must be atomic: two clients could both ask for "Ali" at the same moment; if "check" and "add" are separate steps, both checks pass and both get the name. A synchronized block or a concurrent set's add() (which returns false if the element exists) prevents this race condition.

Note on Swing

Swing (javax.swing) is still part of the JDK and fine for learning, but it is considered legacy for new desktop apps; JavaFX or a web front end is more common today. The networking code is identical either way.

6HTTP Protocol (Case Study)

HTTP (HyperText Transfer Protocol) is the application-level protocol of the web. A client (usually a browser) sends a request naming a resource and a method; the server answers with a status code, headers and usually a body.

Key ideas

  • Application-level protocol. HTTP/1.1 and HTTP/2 run over TCP (default port 80, or 443 for HTTPS); HTTP/3 runs over QUIC, which uses UDP port 443.
  • Stateless: each request is independent and the server does not remember earlier requests by itself. Applications add state with cookies, sessions and tokens.
  • "Connectionless" describes HTTP/1.0, which opened a new TCP connection for every request and closed it after the response. Since HTTP/1.1, connections are persistent (kept open and reused) by default, and HTTP/2 and HTTP/3 send many requests in parallel over one connection.
  • Media-type independent via MIME types: any data can be sent as long as the Content-Type header says what it is (text/html, image/png, application/json).
  • Methods: GET, HEAD, POST, PUT, DELETE, OPTIONS, TRACE, CONNECT, and PATCH (added in RFC 5789).
  • Status codes: 1xx informational, 2xx success, 3xx redirection, 4xx client error, 5xx server error.

HTTPS

HTTPS is HTTP sent inside a TLS (Transport Layer Security) connection, on port 443. TLS encrypts the traffic, proves the server's identity with a certificate, and detects tampering. The current version is TLS 1.3 (2018); TLS 1.2 is still accepted; TLS 1.0 and 1.1 are deprecated (RFC 8996, 2021), and the old name "SSL" refers to versions that are all broken. Browsers now mark plain-HTTP pages as "Not secure".

Common mistake

"401 and 403 mean the same thing." 401 Unauthorized means "you have not proven who you are" (log in). 403 Forbidden means "I know who you are, and you are not allowed".

Minimal HTTP server (from source)

The course notes show the main loop of a hand-written HTTP server on port 8000. Each accepted socket is wrapped in an HttpRequest object that reads the request and writes the response.

Main loop, as in the course notes

public static void main(String[] args) {
    try {
        System.out.println("\n\n\t\tThe HTTP Server is running..");
        System.out.println("\n\n\t\tStop server using Ctrl + C");
        ServerSocket soc = new ServerSocket(8000);
        while (true)
        {
            Socket inSoc = soc.accept();
            HttpRequest request;
            try {
                request = new HttpRequest(inSoc);

            } catch (Exception ex) {

            }
        }
    } catch (Exception ex) {
        System.out.println("Error2");
    }
}

The heart of it is these five lines: build a request handler for the client socket, process it, and report errors without crashing the server.

try {

The notes do not include HttpRequest. Here is a minimal version so the server actually runs; open http://localhost:8000/ in a browser to test it.

HttpRequest.java (minimal, added)

import java.io.*;
import java.net.Socket;
import java.nio.charset.StandardCharsets;

class HttpRequest {
    private final Socket socket;

    HttpRequest(Socket socket) { this.socket = socket; }

    void process() throws IOException {
        try (Socket s = socket;
             BufferedReader in = new BufferedReader(
                 new InputStreamReader(s.getInputStream(), StandardCharsets.US_ASCII));
             OutputStream out = s.getOutputStream()) {

            String requestLine = in.readLine();          // e.g. "GET /index.html HTTP/1.1"
            if (requestLine == null) return;
            String line;
            while ((line = in.readLine()) != null && !line.isEmpty()) {
                // skip the headers until the blank line
            }

            String status, body;
            if (requestLine.startsWith("GET ")) {
                status = "200 OK";
                body = "<h1>It works</h1>";
            } else {
                status = "405 Method Not Allowed";
                body = "<h1>405 Method Not Allowed</h1>";
            }
            byte[] bytes = body.getBytes(StandardCharsets.UTF_8);
            String head = "HTTP/1.1 " + status + "\r\n"
                        + "Content-Type: text/html; charset=utf-8\r\n"
                        + "Content-Length: " + bytes.length + "\r\n"
                        + "Connection: close\r\n\r\n";      // HTTP lines end with CRLF
            out.write(head.getBytes(StandardCharsets.US_ASCII));
            out.write(bytes);
        }
    }
}
Security note

Do not copy parts of the request (such as the path) straight into the HTML response: an attacker can put a script in the URL and it will run in the victim's browser (reflected cross-site scripting, XSS). Real servers also limit header size and time out slow clients.

Current Java APIs

For real work you rarely write HTTP by hand. Java includes java.net.http.HttpClient (Java 11+, supports HTTP/2), a built-in lightweight server com.sun.net.httpserver.HttpServer, and the jwebserver command (Java 18+) that serves a folder over HTTP for testing. The legacy HttpURLConnection still works but is no longer the recommended client.

7FTP Protocol (Case Study)

FTP (File Transfer Protocol, 1971, current standard RFC 959 from 1985) is used to transfer files between hosts. Its unusual feature is that it uses two separate TCP connections:

  • Control connection, port 21: stays open for the whole session and carries commands and replies (login, change directory, "send me this file").
  • Data connection: opened for each file transfer or directory listing. In active mode the server connects back to the client from port 20. In passive mode (PASV) the client connects to a random high port that the server announces; passive mode is the norm today because client-side firewalls and NAT block incoming connections.

FTP supports ASCII mode (text files; line endings are converted between systems) and binary mode (exact byte copy; use it for images, archives, executables). Common client commands: put, get, cd, lcd, mput, mget, and more.

Example

Uploading a report with a classic command-line client: ftp files.example.edu → log in → binary → lcd C:\reports → cd uploads → put q3.pdf → bye. The lcd/cd pair is a favourite exam question: one is local, one is remote.

FTP security: FTP vs FTPS vs SFTP

Plain FTP sends everything in cleartext, including the username and password. Anyone who can capture traffic on the path (public Wi-Fi, a compromised router) can read them. For this reason plain FTP should not be used across untrusted networks, and Chrome and Firefox removed built-in FTP support in 2021.

Common mistake

"SFTP is FTP with SSL." No: that is FTPS. SFTP is part of the SSH family, unrelated to FTP apart from its purpose, and uses port 22.

8Security Essentials for Client/Server Systems

The IT security side of this course applies the CIA triad (Confidentiality, Integrity, Availability) to each part of the model. A server is valuable because many clients depend on it, which also makes it the main target.

Key idea

Never trust the client. The client runs on a machine the user controls, so any check done only in the client (a hidden field, a disabled button, JavaScript validation) can be bypassed. Every security decision must be enforced again on the server.

Exam tip

If asked how to secure the TCP chat example, list: run it over TLS (SSLServerSocket), authenticate users instead of accepting any name, limit message size and rate, and log connections (one of the two features the original comment says is missing).

9Check your understanding

Quiz: whole course

Q1In the client/server model, which side starts the communication?

The client is the active side: it sends a request. The server is passive: it listens on a port and only responds. Processing power has nothing to do with the roles.

Q2What does a port number identify?

The IP address identifies the host; the port (0–65535) identifies the service on that host, such as 443 for HTTPS. The network card is identified by its MAC address.

Q3Which service is the best fit for UDP?

A voice call needs low delay and can tolerate a lost packet; waiting for a retransmission would cause gaps. The other three need every byte, delivered in order, so they use TCP.

Q4The ephemeral (dynamic) port range is:

0–1023 are well-known ports, 1024–49151 are registered ports, and 49152–65535 are the dynamic/ephemeral ports that the operating system assigns to the client side of a connection.

Q5Which server type generates dynamic content and runs business logic?

The application server builds content per request (your timetable, your balance) and holds the business rules. A web server in the classic split serves static files; a file server stores files; groupware supports collaboration.

Q6What is the main security benefit of 3-tier over 2-tier?

In 3-tier, only the application server talks to the database, so the database can be hidden on a private network and the business rules are enforced on a server the user cannot modify.

Q7In the Java TCP server, what does welcomeSocket.accept() do?

accept() blocks until a client connects and returns a dedicated Socket for it. The port was already opened by new ServerSocket(6789). UDP has no accept; it uses receive().

Q8Why does the UDP client call setSoTimeout(10000)?

UDP does not retransmit lost datagrams. Without a timeout, receive() would block forever if the reply never arrives. After 10 seconds it throws SocketTimeoutException, and the client reports the packet as lost.

Q9Why does the chat server create a new Handler thread for each client?

Each Handler blocks on readLine() for its own client. If the main thread did that, no other client could connect. One thread per client (or a virtual thread in Java 21+) lets the server keep accepting.

Q10True or false: since HTTP/1.1, a new TCP connection is opened and closed for every single request by default.

That was HTTP/1.0. HTTP/1.1 made persistent connections the default, and HTTP/2 and HTTP/3 multiplex many requests over one connection. HTTP is still stateless, which is a different property.

Q11HTTP/3 runs on top of which transport?

HTTP/3 (RFC 9114, 2022) uses QUIC, which runs over UDP and has TLS 1.3 built in. HTTP/1.1 and HTTP/2 use TCP.

Q12A server returns 403. What does it mean?

403 Forbidden: you are not permitted. 404 is Not Found, 500 is a server error, 301 is Moved Permanently. 401 would mean you have not authenticated yet.

Q13In FTP, which port carries the commands such as USER, RETR and STOR?

Port 21 is the control connection for commands and replies. Port 20 is the server's data port in active mode. Port 22 is SSH/SFTP; 443 is HTTPS.

Q14Which statement about secure file transfer is correct?

FTPS = FTP + TLS (ports 21/990 plus data ports). SFTP = SSH File Transfer Protocol, a separate protocol on port 22. Plain FTP encrypts nothing, not even the password.

Summary

  • Client and server are roles: the client sends requests, the server listens on a port and responds, following an agreed protocol.
  • An IP address finds the host; a port finds the service. Well-known ports are 0–1023; clients use ephemeral ports 49152–65535.
  • TCP is reliable, ordered and connection-oriented; UDP is fast, connectionless and best effort. HTTP/3 runs on QUIC over UDP.
  • Server types: file, database, transaction (OLTP), groupware, web (static) and application (dynamic, business logic).
  • 2-tier is simple but exposes the database; 3-tier adds a business-logic tier for scalability and security; N-tier splits further into services.
  • Java servers: ServerSocket → accept() → streams → close; UDP uses DatagramSocket and timeouts; multiple clients need threads.
  • HTTP is stateless, uses methods and status codes, and today runs as HTTP/1.1, HTTP/2 and HTTP/3, almost always inside TLS 1.3 (HTTPS).
  • FTP uses a control connection (21) and data connections; it is cleartext, so use SFTP (22) or FTPS instead.
