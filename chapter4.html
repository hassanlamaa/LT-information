Remote Procedure Call (RPC)

RPC lets a program call a function that runs on another computer as if it were a normal local call. It is the idea behind Sun RPC, NFS, Java RMI, CORBA and today's gRPC. Once you understand stubs, marshalling and call semantics, every one of these systems looks familiar.

4.1Introduction to RPC

Remote Procedure Call (RPC) allows a program to execute a subroutine (a procedure or function) on another host without writing any socket code by hand. The programmer writes result = add(2, 3); behind the scenes the call is turned into a network message, sent to a server, executed there, and the result is sent back.

The network details are hidden inside two small pieces of generated code called stubs. A stub is a stand-in procedure with the same name and parameters as the real one. The client stub pretends to be the remote procedure; the server stub (often called the skeleton) pretends to be the caller on the server side.

Analogy

Ordering food by phone. You (the client) say "one pizza, large" to the person on the phone (the client stub). They write it on an order slip in a standard format (marshalling), send it to the kitchen (network), where a cook reads the slip (server stub unmarshals) and makes the pizza (the real procedure). The pizza comes back the same way. You never walk into the kitchen.

Local call vs remote call

In a local call the caller pushes the parameters onto the stack, jumps to the procedure, and the procedure returns a value. RPC copies this model: the client "pushes" parameters into a message, "jumps" by sending it, and "returns" when the reply arrives. The difference is that the two sides no longer share memory or a CPU.

Why RPC?

RPC enables distributed computing with the familiar procedure-call style. Programmers already know how to call functions, so splitting an application across machines becomes much easier than designing raw message protocols over sockets.

Characteristics of RPC

  • The called procedure runs in a different process, usually on a different machine.
  • There is no shared address space between client and server. A memory address on the client means nothing on the server.
  • Parameters are therefore passed by value (copied into the message). Pointers and references cannot be passed as addresses; if a parameter points to data, the stub copies the data itself.
  • Client and server may run on different architectures and operating systems (for example little-endian x86 vs big-endian SPARC), so data must be converted to a common format.
  • A remote call can fail in ways a local call cannot: the network can lose a message, or the server can crash halfway (a partial failure).

Features

Simple syntax

A remote call looks like an ordinary function call.

Well-defined interface

The procedures are described in an interface file, so client and server agree on names and types.

Efficient

Messages are compact (binary) and the protocol is simple, so calls are fast compared with hand-written text protocols.

Hides network complexity

Sockets, byte order and retransmission are handled by the stubs and the runtime library.

Common mistake

Saying "RPC is exactly like a local call". It looks like one, but it is slower (milliseconds instead of nanoseconds), it can fail independently, and it cannot share pointers. Good RPC code always handles timeouts and remote errors.

Knowledge check 4.1

QWhich of the following is NOT a characteristic of RPC?

RPC does not allow passing pointers or references, because there is no shared memory: an address on the client is meaningless on the server. Parameters are copied into the message (passed by value). A, C and D are all true characteristics.

4.2RPC Model and Mechanism

Every RPC system is built from the same parts. Learn these definitions; they come back in RMI, CORBA and gRPC.

Client stub
Local procedure the client calls. It marshals the arguments, sends the request and waits for the reply.
Server stub (skeleton)
Receives the request on the server, unmarshals the arguments and calls the real procedure.
Dispatcher
Server code that reads the procedure number in the request and picks which server stub to run.
Marshalling
Packing parameters into a flat, machine-independent byte format for sending. Also called serialization.
Unmarshalling
The reverse: rebuilding local data values from the received bytes.
XDR
eXternal Data Representation (RFC 4506): the standard format Sun RPC uses for marshalled data (big-endian, 4-byte aligned).
RPC runtime
The library that handles sockets, timeouts and retransmission underneath the stubs.

The call, step by step

  1. Client calls the client stub as if it were the real procedure, for example add(2, 3).
  2. Client stub marshals the arguments into an XDR message, together with the program, version and procedure numbers.
  3. The RPC runtime sends the message over the network (UDP or TCP) and the client blocks, waiting.
  4. The server dispatcher receives the message and selects the right server stub using the procedure number.
  5. The server stub unmarshals the arguments and calls the real server procedure.
  6. The procedure runs and returns its result to the server stub.
  7. The server stub marshals the result into a REPLY message and sends it back.
  8. The client stub unmarshals the result and returns it to the caller, which continues as if a local call had finished.

Data representation: why XDR?

Different machines store numbers differently. An int of value 1 is stored as 01 00 00 00 on a little-endian x86 PC but as 00 00 00 01 on a big-endian machine. If bytes were copied directly, the server could read 16,777,216 instead of 1. XDR solves this by defining one external format: the sender converts to XDR (marshalling), the receiver converts from XDR to its own local format (unmarshalling). This gives machine independence.

Example

Marshalling add(2, 3) in XDR gives eight bytes: 00 00 00 02 00 00 00 03. Each integer is 4 bytes, big-endian. A string such as "hi" becomes a 4-byte length (00 00 00 02) followed by the bytes 68 69 and two padding bytes, because XDR keeps everything aligned to 4 bytes.

Synchronous, asynchronous and one-way RPC

StyleWhat the client doesTypical use
SynchronousBlocks until the reply arrives.Most calls: "get balance", "add".
AsynchronousContinues after the server acknowledges the request; the server processes it later and the result is collected later (callback or future).Long jobs, such as generating a report.
One-way (fire-and-forget)Sends the request and never waits for any reply.Logging, notifications, where losing one message is acceptable.

Knowledge check 4.2

QWhat is the role of a stub in RPC?

Stubs handle marshalling and the network exchange so the remote call looks local. The procedure itself runs on the server (not in the stub), and port allocation is the port mapper's job.

4.3Identification: Program, Version and Procedure Numbers

On one machine, a function is identified by its name. Across a network, names are awkward, so Sun RPC (also called ONC RPC, defined in RFC 5531) identifies every remote procedure with three numbers:

Program number
Identifies a group of related procedures, i.e. one service. Example: NFS is program 100003.
Version number
Lets a service evolve. A server can offer version 2 and version 3 at the same time, so old clients keep working while new clients use new features.
Procedure number
Identifies one specific function inside that program version. Procedure 0 is always the "null procedure", used to ping a server.
Program 0x20000001→Version 1→Procedure 1 = ADD

Program number ranges

Program numbers are 32-bit values divided into ranges. Originally Sun Microsystems assigned the first range; today the registry is kept by IANA.

RangeWho assigns it
0x00000000 – 0x1fffffffDefined centrally (originally Sun, now IANA). Well-known services like NFS and mountd.
0x20000000 – 0x3fffffffUser-defined (local administrator). Use this range for your own programs and course exercises.
0x40000000 – 0x5fffffffTransient: generated dynamically by applications at run time.
0x60000000 – 0xffffffffReserved.
Exam tip

If asked "why use version numbers?", answer: so a server can support several revisions of the same protocol at once, which allows the protocol to evolve while staying backward compatible with old clients.

Knowledge check 4.3

QWhy do we use version numbers in RPC?

Version numbers let a server support several revisions of a service at the same time, so the protocol can change without breaking old clients. Ports are handled by the port mapper; encryption is not related.

4.4Dynamic Port Mapping and the Port Mapper

A client needs a port number to reach a server. Why not give each RPC program a fixed port? Because program numbers are 32-bit (over 4 billion values) but TCP/UDP ports are only 16-bit (65,536 values), so there is no one-to-one mapping. Instead, RPC servers take any free port when they start and register it with a directory service.

That directory is the port mapper, called rpcbind on modern Linux and BSD systems. It always listens on the well-known port 111 (both TCP and UDP) and keeps a table that maps (program number, version, protocol) to a port.

  1. Server starts and binds to any free port, for example 40512.
  2. Server registers with the port mapper: "program 0x20000001, version 1, TCP → port 40512".
  3. Client asks the port mapper on port 111: "which port has program 0x20000001 version 1?"
  4. Port mapper replies 40512.
  5. Client sends the actual RPC directly to port 40512. Later calls reuse that port.

Pseudocode

// Server side, at start-up
portMapper.Register(programNumber, version, "tcp", myPort)

// Client side, before the first call
port = portMapper.Lookup(programNumber, version, "tcp")   // asks port 111

Linux terminal: list registered RPC programs

$ rpcinfo -p localhost
   program vers proto   port  service
    100000    4   tcp    111  portmapper
    100003    3   tcp   2049  nfs
    100005    3   udp  20048  mountd
Analogy

A hotel reception desk. Guests (servers) get whatever room is free and tell reception their room number. Visitors (clients) always go to reception first (port 111) and ask "which room is Mr. NFS in?".

Security note

Port 111 should never be open to the internet. Exposed rpcbind services have been abused for reconnaissance and for DDoS amplification attacks, so firewalls normally block it from outside networks.

Knowledge check 4.4

QThe RPC port mapper listens on which well-known port?

The port mapper (rpcbind) uses port 111 on both TCP and UDP. Port 80 is HTTP, 443 is HTTPS and 8080 is a common alternative HTTP port.

4.5RPC Call Semantics

Suppose the client sends a request and no reply arrives before the timeout. Did the request get lost, did the server crash before running it, or did it run and only the reply get lost? The client cannot tell. Call semantics describe what the RPC system promises about how many times the procedure was executed.

SemanticsHow it worksGuaranteeGood for
At least onceClient keeps retrying until it gets a reply.Executed one or more times (if a reply arrives).Idempotent operations only.
At most onceServer remembers request IDs and filters duplicates; client reports an error if unsure.Executed zero or one time, never twice.Non-idempotent operations such as money transfers.
Exactly onceWould need retries plus duplicate filtering plus surviving crashes (logging, transactions).Executed exactly one time.Ideal but very hard; impossible to guarantee in general if the server can crash.

An operation is idempotent if executing it several times has the same effect as executing it once. "Read account balance" and "set temperature to 21°C" are idempotent. "Add $100 to account" and "append a line to a log" are not: a retry would add $200 or write the line twice.

Example

You call withdraw(100) with at-least-once semantics. The server runs it, but the reply is lost. The client retries, and the server runs it again: $200 is withdrawn. With at-most-once semantics, the server sees the same request ID, does not run it again, and resends the saved reply.

Today

Modern APIs make non-idempotent operations safe to retry by adding an idempotency key: a unique ID the client sends with each request so the server can recognise duplicates. Payment APIs such as Stripe work this way.

Exam tip

"Which semantics for an idempotent operation?" → at least once (retrying is harmless and it is the simplest to implement). "Which for a bank transfer?" → at most once.

Knowledge check 4.5

QWhich semantic is most suitable for an idempotent operation like "get temperature sensor value"?

Reading a sensor twice does no harm, so the client can simply retry until it gets an answer. At-most-once would work too but adds unnecessary duplicate tracking; exactly-once is expensive and unnecessary here. "Zero once" does not exist.

4.6RPC Authentication

Each RPC CALL message carries a credential (who the caller claims to be) and a verifier (evidence that the claim is true). Sun RPC defined several "flavors":

FlavorWhat is sentSecurity
NULL (AUTH_NONE)Nothing.None. Used for public services and the null procedure.
UNIX style (AUTH_UNIX, now AUTH_SYS)Hostname, user ID (UID), group IDs (GIDs), timestamp.Weak: the client simply states its UID and the server trusts it. Anyone with root on a client can claim any UID.
DES (AUTH_DES, also AUTH_DH)Network name plus an encrypted timestamp, using a DES session key agreed with Diffie-Hellman.Strong for its time, because the identity is proven cryptographically. Today 56-bit DES and the small Diffie-Hellman key are considered broken.
SHORT (AUTH_SHORT)A short handle the server issued after a first full authentication.Saves bandwidth on later calls; only as strong as the first authentication.
Updated fact

Modern ONC RPC (for example NFSv4) uses RPCSEC_GSS (RFC 2203), which plugs in Kerberos v5 for authentication, integrity and encryption. AUTH_DES is obsolete. In other RPC systems, such as gRPC, security comes from TLS plus tokens (for example OAuth 2.0 bearer tokens).

Knowledge check 4.6

QWhich authentication method uses the Data Encryption Standard (DES) to provide strong security?

DES authentication proves identity with an encrypted timestamp, so it was the strong option in classic Sun RPC. UNIX style only states the UID, NULL sends nothing, and SHORT reuses a handle. Remember that DES itself is no longer considered secure today; RPCSEC_GSS with Kerberos replaced it.

4.7RPC Message Format

Sun RPC has exactly two kinds of message, CALL and REPLY, both encoded in XDR. The fields of a CALL are:

FieldMeaning
Message ID (XID)Random number chosen by the client. The reply carries the same XID so the client can match replies to requests, and the server can detect duplicates.
Message type0 = CALL, 1 = REPLY. This is what distinguishes the two.
RPC versionVersion of the RPC protocol itself (always 2).
Program numberWhich service.
Version numberWhich version of that service.
Procedure numberWhich function.
Credential and verifierAuthentication fields (flavor + data), see 4.6.
ArgumentsThe marshalled parameters.

A REPLY contains the XID, type = REPLY, a status (accepted or denied), a verifier, and then either the marshalled results or an error code such as PROG_UNAVAIL or PROC_UNAVAIL.

Knowledge check 4.7

QWhat distinguishes a CALL message from a REPLY message in RPC?

Every RPC message has a message-type field: 0 means CALL and 1 means REPLY. Ports and payload sizes vary and do not identify the message kind; RPC has no checksum field of its own (UDP/TCP provide one).

4.8RPC Language and the rpcgen Compiler

Writing stubs by hand is tedious and error-prone. Instead, you describe the interface once in an interface definition language (IDL). Sun's IDL is called RPC Language (RPCL); it looks like C and is saved in a .x file. The rpcgen compiler reads that file and generates the code for you.

calc.x

struct operands {
    int a;
    int b;
};

program CALC_PROG {
    version CALC_VERS {
        int ADD(operands) = 1;     /* procedure number 1 */
        int SUB(operands) = 2;
    } = 1;                         /* version number 1 */
} = 0x20000001;                  /* user-defined program number */

Running rpcgen -a calc.x produces:

FileContents
calc.hHeader file: constants and C structs shared by both sides.
calc_clnt.cClient stub: functions like add_1() that marshal and send.
calc_svc.cServer skeleton: main(), port mapper registration and the dispatcher that calls your procedure.
calc_xdr.cXDR routines that convert operands to and from XDR.
calc_client.c, calc_server.c, MakefileTemplates (only with -a); you fill in the real logic.
Key idea

This "write the interface, generate the stubs" pattern is the heart of every RPC system: .x + rpcgen (Sun RPC), .idl + idlj (CORBA), .proto + protoc (gRPC), .thrift + thrift (Apache Thrift).

Practical note

On current Linux distributions, Sun RPC lives in the libtirpc library and rpcgen is a separate package (it was removed from glibc in version 2.32). Compile with -ltirpc and -I/usr/include/tirpc.

Knowledge check 4.8

QWhat is the main output of rpcgen?

rpcgen generates C source code: the client stub, the server skeleton (with the dispatcher), XDR conversion routines and a header. You still compile them yourself; it does not produce binaries or Java bytecode.

4.9Practical: Java RMI (Remote Method Invocation)

Java RMI is RPC for objects. Instead of calling a procedure, a Java program calls a method on an object that lives in another JVM. RMI was created by Sun Microsystems (JDK 1.1, 1997); Java is now owned by Oracle and RMI is still part of the JDK in the java.rmi module.

Architecture

Client→Stub→Remote Reference Layer→Transport (JRMP over TCP)→Skeleton / dispatcher→Remote object
Stub
Client-side proxy. Implements the same remote interface, marshals the call (using Java serialization) and sends it.
Skeleton
Server-side proxy that unmarshals and calls the real object. Since Java 1.2 a generic dispatcher does this job, so no skeleton classes are generated.
Remote Reference Layer
Decides how a reference behaves (for example a single unicast server object).
Transport layer
Manages TCP connections. The RMI wire protocol is called JRMP (Java Remote Method Protocol).
RMI registry
A simple naming service: servers bind a name to an object, clients lookup the name to get a stub. Started with rmiregistry; default port 1099.

Four steps to build an RMI application

  1. Define the remote interface: extends java.rmi.Remote; every method declares throws RemoteException.
  2. Implement it in a class that extends UnicastRemoteObject (or is exported with UnicastRemoteObject.exportObject).
  3. Create the server: create the object and bind()/rebind() it in the registry under a name.
  4. Create the client: lookup() the name, cast to the interface, and call methods.
import java.rmi.*;

// Remote interface: the contract shared by client and server
public interface Calculator extends Remote {
    long add(long a, long b) throws RemoteException;
    long sub(long a, long b) throws RemoteException;
    long mul(long a, long b) throws RemoteException;
    long div(long a, long b) throws RemoteException;
}
import java.rmi.*;
import java.rmi.server.UnicastRemoteObject;

public class CalculatorImpl extends UnicastRemoteObject implements Calculator {
    public CalculatorImpl() throws RemoteException { super(); } // exports the object
    public long add(long a, long b) { return a + b; }
    public long sub(long a, long b) { return a - b; }
    public long mul(long a, long b) { return a * b; }
    public long div(long a, long b) { return a / b; }  // b == 0 throws ArithmeticException to the client
}
import java.rmi.registry.*;

public class CalculatorServer {
    public static void main(String[] args) throws Exception {
        Registry reg = LocateRegistry.createRegistry(1099); // or run "rmiregistry" separately
        reg.rebind("CalculatorService", new CalculatorImpl());
        System.out.println("Calculator server ready");
    }
}
import java.rmi.Naming;

public class CalculatorClient {
    public static void main(String[] args) throws Exception {
        // lookup returns a stub that implements Calculator
        Calculator c = (Calculator) Naming.lookup("rmi://localhost:1099/CalculatorService");
        System.out.println("4 + 5 = " + c.add(4, 5));
        System.out.println("9 / 3 = " + c.div(9, 3));
    }
}

Run it: javac *.java, then java CalculatorServer in one terminal and java CalculatorClient in another. No rmic step is needed.

RMI + JDBC: a remote database example

A classic course example: a remote method reads the student_data table from MySQL and returns a List<Student>. The client never connects to the database directly; only the RMI server holds the database credentials. This is a three-tier design (client → RMI server → database).

StudentService.java and Student.java

public interface StudentService extends Remote {
    List<Student> getStudents() throws RemoteException;
}

// Sent BY VALUE: must be Serializable so RMI can copy it to the client
public class Student implements java.io.Serializable {
    private int id; private String name; private String branch;
    // constructor + getters ...
}

// In StudentServiceImpl.getStudents():
try (Connection con = DriverManager.getConnection("jdbc:mysql://localhost:3306/school", user, pass);
     PreparedStatement ps = con.prepareStatement("SELECT id, name, branch FROM student_data");
     ResultSet rs = ps.executeQuery()) {
    while (rs.next()) list.add(new Student(rs.getInt(1), rs.getString(2), rs.getString(3)));
}
Key idea

In RMI, remote objects (that implement Remote) are passed by reference: the client gets a stub. Ordinary serializable objects (like Student) are passed by value: the client gets a copy. A parameter that is neither causes a marshalling error at run time.

Common mistake

Forgetting throws RemoteException on a method of the remote interface. The compiler accepts it, but exporting the object fails at run time with "illegal remote method encountered".

Security warning

RMI uses Java deserialization, which has been a major source of remote code execution attacks. Never expose an RMI registry (port 1099) to the internet.

Knowledge check 4.9 (RMI)

QWhich RMI component acts as a proxy on the client side?

The stub lives in the client JVM, implements the remote interface and forwards each call. The skeleton is the server-side counterpart, the registry is the naming service, and the transport layer only moves bytes.

4.10RPC Today: gRPC, REST and Friends

The ideas in this chapter are still everywhere, only the tools changed. Classic Sun RPC survives mainly inside NFS. New systems usually pick one of these:

gRPC

Google's open-source RPC framework (2015, now a CNCF project). Interfaces are written in Protocol Buffers (.proto); protoc generates stubs in about a dozen languages; calls travel over HTTP/2 with TLS. Supports streaming and deadlines.

REST / JSON over HTTP

Not RPC strictly speaking: you act on resources with HTTP methods (GET, POST, PUT, DELETE). Human-readable and works in every browser. Often described with OpenAPI.

Apache Thrift

Created at Facebook; IDL plus code generation, similar idea to gRPC with pluggable transports.

Message queues

Kafka, RabbitMQ and similar: asynchronous messaging instead of calls. The sender does not wait, which suits one-way and long-running work.

A tiny gRPC example

calculator.proto (the interface, like a .x file)

syntax = "proto3";
package calc;

service Calculator {
  rpc Add (AddRequest) returns (AddReply);
}
message AddRequest { int64 a = 1; int64 b = 2; }   // numbers are field tags, not values
message AddReply   { int64 sum = 1; }

client.py (Python; stubs generated by grpcio-tools)

import grpc, calculator_pb2 as pb, calculator_pb2_grpc as rpc

channel = grpc.insecure_channel("localhost:50051")        # use secure_channel + TLS in production
stub = rpc.CalculatorStub(channel)                        # the client stub
reply = stub.Add(pb.AddRequest(a=2, b=3), timeout=2.0)    # looks like a local call
print(reply.sum)                                          # 5

Everything from this chapter is visible: an IDL (.proto), generated stubs, binary marshalling (Protocol Buffers instead of XDR), and a timeout because the network can fail. Instead of a port mapper, the client is given a host and port directly or uses DNS / a service registry.

Exam tip

The core answer to "RPC vs RMI": RPC calls procedures and is language-neutral (in principle), passing data by value; RMI calls methods on objects, is Java-only, and can pass remote objects by reference and serializable objects by value.

4.11Chapter 4 Final Exam: RPC Mastery

Fourteen questions covering every section. Answer each one to see the explanation.

Final exam

Q1What does RPC stand for?

RPC = Remote Procedure Call: calling a procedure that runs in another process, usually on another machine.

Q2Which component in RPC converts parameters to the external data representation before transmission?

The client stub marshals the arguments into XDR before sending. The skeleton does the reverse on the server (unmarshalling arguments); the dispatcher only chooses the procedure; the port mapper only maps program numbers to ports.

Q3Which protocol/port does the RPC port mapper use by default?

The port mapper (rpcbind) listens on port 111 over both TCP and UDP. ICMP has no ports at all.

Q4Which RPC call semantics guarantee that the server executes the request at most once, returning an error if uncertain?

At-most-once filters duplicate requests and reports an error rather than risk a second execution. Exactly-once would also promise that it ran, which cannot be guaranteed if the server crashes.

Q5Which authentication method in RPC relies on UNIX user IDs and hostnames (weak security)?

AUTH_UNIX (now called AUTH_SYS) sends hostname, UID and GIDs in clear, and the server trusts them. It is weak because a client can claim any UID.

Q6In Java RMI, what is the purpose of the rmiregistry?

The registry maps names to remote object references (default port 1099). Stubs are generated dynamically by the JVM, and the registry provides no encryption.

Q7XDR (eXternal Data Representation) is used to solve which problem?

XDR defines one common format (big-endian, 4-byte aligned) so machines with different byte orders and word sizes read the same values.

Q8Which of the following is an idempotent RPC operation (suited for "at least once" semantics)?

Reading a value has no side effect, so repeating it is harmless. A transfer or append done twice changes the result; delete-and-create produces a new record (new ID) each time.

Q9In the RPC identification scheme, a program number groups related procedures. Version numbers are used to:

One server can offer versions 1 and 2 of the same program at once, so old clients keep working while the protocol evolves.

Q10Which rpcgen output provides the dispatcher that receives incoming requests and calls the appropriate server procedure?

The server skeleton (*_svc.c) contains main(), registers with the port mapper and holds the dispatch routine that switches on the procedure number.

Q11Why can't each RPC program simply use its program number as its port number?

There are far more possible program numbers (232) than ports (216), so a dynamic mapping through the port mapper is needed.

Q12True or false: since Java 1.2, an RMI server needs a generated skeleton class for every remote object.

False. Since Java 1.2 the RMI runtime dispatches calls generically, and since Java 5 even stubs are created dynamically. The rmic tool was removed in Java 15.

Q13In gRPC, what plays the role that XDR plays in Sun RPC?

Protocol Buffers is gRPC's interface language and its binary serialization format, just as RPCL and XDR are for Sun RPC. HTTP/2 is the transport and TLS the security layer.

Q14An RMI remote method returns List<Student>. What must be true of Student?

Student is plain data, so RMI sends it by value using Java serialization. Without Serializable the call fails with a marshalling exception. Only remote objects (implementing Remote) are passed by reference.

Summary

  • RPC makes a remote call look like a local procedure call. Stubs hide the network: the client stub marshals and sends, the server stub (skeleton) unmarshals and calls.
  • No shared memory means parameters are passed by value; XDR gives a machine-independent data format.
  • Sun RPC identifies procedures by program, version and procedure numbers. The port mapper (rpcbind, port 111) maps programs to dynamic ports.
  • Call semantics: at-least-once (only for idempotent operations), at-most-once (duplicate filtering), exactly-once (ideal, very hard).
  • Authentication flavors: NULL, UNIX (weak), DES (strong for its time, obsolete now; replaced by RPCSEC_GSS/Kerberos), SHORT.
  • rpcgen turns a .x interface into client stub, server skeleton, XDR routines and header.
  • Java RMI is object-oriented RPC for Java: remote interface, UnicastRemoteObject, registry on port 1099. Skeletons and rmic are gone; Activation was removed in Java 17.
  • Today: gRPC (Protocol Buffers over HTTP/2), REST/JSON, Thrift and message queues do the same job.
