1Understanding client/server architecture

Client/server architecture is a distributed application structure that divides tasks or workloads between service providers (servers) and service requesters (clients). The client starts the conversation by sending a request; the server does the work and returns a response.

Example

Your browser (client) sends GET /timetable to the university web server; the server returns the HTML page. One server answers thousands of browsers at once.

Analogy

A client is a customer at a counter, the server is the shop assistant. Customers come and ask; the assistant does not walk out and start conversations. In peer-to-peer (P2P), by contrast, everyone is both customer and assistant: each node can request from and serve to the others, as in BitTorrent.

Client/server basics

Q1In client/server architecture, which side starts the conversation?

The client (service requester) sends a request and the server (service provider) answers. The server starting the conversation is the tempting wrong answer: like a shop assistant, it waits for customers to come and ask.

Q2Your browser sends GET /timetable to the university web server, which returns the HTML page. In this exchange the web server is the client.

False. The browser sends the request, so it is the client; the web server does the work and returns the response, so it is the server.

Q3Which arrangement describes peer-to-peer rather than client/server?

In peer-to-peer every node is both client and server. The other two options describe client/server: a central server answering many clients, and the counter analogy where only customers start the conversation.

2Quick recap: the tier models

Applications have three layers: presentation (UI), business logic (rules) and data (storage). A layer is a logical grouping of code; a tier is where it physically runs. The tier models differ in how they place those layers on machines.

ModelWhere things runRemember it by
1-tierUI, logic and data in one program on one machineSimple, offline, not scalable
2-tierThick client (UI + logic) → database serverClassic client/server; client talks straight to the DB
3-tierClient → application server → databaseThe client never touches the DB; standard for the web
N-tierClient → load balancer → web → gateway → services → cache / queue / DBMost scalable, most complex; includes microservices
Thick (fat) client
Does most processing on the user's device and uses the server mainly for shared data. Example: a desktop accounting app in a 2-tier system.
Thin client
Mostly displays and sends input; the server does the processing. Example: a browser showing server-generated pages.
Microservices
A modern N-tier style where the business tier is split into small services by capability (orders, payments), each deployed and scaled independently.
Common mistake

"More tiers make each request faster" is false. Each tier adds a network hop. What more tiers improve is throughput (users served at once), flexibility and fault isolation.

Exam tip

Words like always, never and only in a true/false statement are a warning sign. Check whether there is any counter-example before you answer True.

Tier models recap

Q1In which model does the client never touch the database, making it the standard for the web?

In 3-tier every request goes through the application server, so the database stays hidden. 2-tier is the tempting wrong answer: there the client talks straight to the database.

Q2A browser showing pages generated on the server is an example of a thick client.

False. The browser mostly displays results and sends input while the server does the processing, which is a thin client. A thick client, such as a desktop accounting app in 2-tier, does most processing on the user's device.

Q3The statement "more tiers make each request faster" is false. What do more tiers actually improve?

Each tier adds a network hop, so a single request gets slightly slower, but the system can serve far more users at once and parts can change or fail independently. "Fewer hops" is wrong: more tiers mean more hops.

3Evolution of client/server architectures

Real N-tier systems often add more tiers again: a load balancer in front, a cache (such as Redis) and a message queue (such as Kafka) beside the database, and an integration tier for outside services like payment providers. See Architecture Tiers Explained for the full picture.

Evolution of the architectures

Q1In Figure 2, what does the 2-tier client contain?

The 2-tier client holds the UI and the logic, and the server holds the database. "App services and data access" is tempting, but those are the extra tiers shown in N-tier.

Q2Real N-tier systems often add a load balancer, a cache, a message queue and an integration tier for outside services such as payment providers.

True. These are the typical extra tiers beyond the four boxes in Figure 2. Answering False assumes N-tier is limited to the four tiers in the diagram, but "N" means any number greater than three.

Q3An online shop wants to send order-confirmation emails without making the customer wait. Which extra N-tier component fits?

A message queue lets one tier hand work to another asynchronously, so the email is sent later while the customer gets an instant reply. A cache is tempting, but it speeds up repeated reads; it does not hand off work.

4True/false quiz

Decide whether each statement is true or false. You get immediate feedback and an explanation after each answer.

Part A: The client/server model

Q1In client/server architecture, the server always initiates the communication with clients.

False. Clients initiate communication by requesting services; the server waits and responds. (Push features such as notifications still rely on a connection the client opened first.)

Q2A web browser is an example of a client in client/server architecture.

True. A web browser sends requests (for example GET /index.html) to web servers and displays the responses.

Q3Peer-to-peer architecture is the same as client/server architecture.

False. In peer-to-peer, every node can act as both client and server and there is no central server. In client/server the roles are fixed.

Q4One server can serve many clients at the same time.

True. Servers handle many concurrent requests, for example using threads or asynchronous I/O. That is the whole point of a shared server.

Q5A machine can never be a client and a server at the same time.

False. "Client" and "server" are roles. In 3-tier, the application server is a server to the browser and a client of the database.

Part B: Tier architectures

Q6In a 1-tier architecture, the presentation, business logic and data storage are all combined in a single system.

True. In 1-tier, all components exist in a single system (usually one program on one machine) without network separation.

Q7A 2-tier architecture is also known as a client/server architecture.

True. 2-tier is the classic client/server model: the client handles presentation and business logic, the server manages data storage. Note that 3-tier and N-tier are client/server architectures too; 2-tier is simply the original form.

Q8In a 3-tier architecture, the business logic is typically located on the client side.

False. In 3-tier, business logic lives in its own tier (the application tier) on the server side, not on the client.

Q9N-tier architecture allows for better scalability than 2-tier architecture.

True. Each N-tier tier can be scaled independently based on demand, while 2-tier is limited by the number of direct database connections and by thick clients.

Q10The main advantage of 1-tier architecture is its high scalability for large user bases.

False. 1-tier has very poor scalability because everything is on one machine. Its real advantages are simplicity, low cost and no network latency.

Q11A layer and a tier mean exactly the same thing.

False. A layer is a logical grouping of code (presentation, logic, data); a tier is a physical deployment unit. Several layers can run in one tier.

Q12In a 2-tier architecture, the client usually connects directly to the database server.

True. There is no middle tier, so the client sends queries straight to the database. This is why 2-tier is weaker on security.

Q13In a well-designed 3-tier web application, the browser may send SQL directly to the database.

False. The browser only talks to the application tier. The database sits on a private network that only the application tier can reach.

Q14In 3-tier, business rules can be changed without reinstalling software on every user's computer.

True. The rules live on the application server, so you update and redeploy the server once. In thick-client 2-tier, every client would need updating.

Q15Adding more tiers always makes each individual request faster.

False. Each tier is another network hop, so a single request usually gets slightly slower. More tiers improve throughput and flexibility, not per-request speed.

Q16N-tier systems often include components such as load balancers, caches and message queues.

True. These are typical extra tiers: the load balancer spreads traffic, the cache reduces database load, and the queue passes work between tiers asynchronously.

Part C: Clients and modern systems

Q17Thick clients contain most of the application logic and require minimal server interaction.

True. Thick (fat) clients process most data locally and contact the server mainly to store and retrieve shared data.

Q18Microservices architecture is an example of N-tier architecture.

True, in the sense used in this course: microservices extend the N-tier idea by splitting the application tier into independently deployable services. Strictly, classic N-tier splits by layer and microservices split by business capability, so some books treat them as related but separate styles.

Q19A thin client does most of its processing on the server.

True. A thin client mainly displays results and sends input; the server does the work. A browser showing server-rendered pages is the usual example.

Q20Validating input with JavaScript in the browser is enough to enforce business rules.

False. Users can change or skip anything that runs on their own device. Browser checks improve the experience; the application tier must enforce the rules. Never trust the client.

Q21Cloud platforms let you build each tier from managed services, such as a managed load balancer and a managed database.

True. AWS, Azure and Google Cloud sell each tier as a service, so teams assemble N-tier systems without running physical servers.

Q22In an N-tier system, a failure in one service always brings down the whole application.

False. Fault isolation is one of N-tier's advantages: if the recommendations service fails, a well-designed shop can still take orders. ("Always" is the giveaway.)

Summary

  • Clients request, servers respond; in peer-to-peer every node can do both.
  • 1-tier: all in one. 2-tier: thick client talks straight to the DB. 3-tier: the client goes through an application server. N-tier: more specialised tiers.
  • Layers are logical, tiers are physical.
  • More tiers: better scalability, flexibility and fault isolation; more complexity and latency per request.
  • Thin clients leave processing to the server; never rely on client-side checks for business rules.
