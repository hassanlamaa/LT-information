1Scenario Questions

Each scenario describes a real situation. Pick an answer to see a short explanation, then open the worked answer for the full reasoning.

Scenario 1: Cross-language banking

A bank has a legacy C++ CORBA server that exposes an Account interface (IDL). A new Java client uses RMI-IIOP to communicate with it. Which statement is true?

IIOP is a language-neutral protocol, so a Java client with stubs generated from the same IDL can call the C++ server directly.
Worked answer: Scenario 1

B. The IDL file is the shared contract. Running an IDL compiler for Java (idlj -fall Account.idl in JDK 8–10, or JacORB's IDL compiler today) generates a Java stub. The stub marshals calls into CDR and sends GIOP requests over IIOP, which the C++ ORB understands.

  • A is wrong: interoperability exists precisely so legacy servers need not be rewritten.
  • C is wrong: C++ and Java both have standard OMG language mappings.
  • D is wrong: JRMP is Java-only; IIOP is the one that crosses languages.

Precision point: starting from an existing IDL is technically the Java IDL (IDL-first) approach; RMI-IIOP is Java-first. Both speak IIOP, which is what makes the answer true.

Scenario 2: Dynamic vs static invocation

A developer wants to build a generic CORBA browser that can invoke any method on any object without knowing the interface at compile time. Which CORBA component should they use?

DII builds requests at run time, and the Interface Repository tells the browser which operations and parameter types exist.
Worked answer: Scenario 2

B. The browser is a client that does not know interfaces in advance, so static stubs (A) are impossible: they must be compiled from known IDL. It first asks the Interface Repository for the object's interface description (operation names and parameter types), then builds a Request object with the DII, adds arguments and calls invoke(). Skeletons (C) and the object adapter (D) are server-side and do not help a client.

Scenario 3: IDL direction misuse

In an IDL definition: void transfer(in long amount, out long newBalance); The client passes amount = 100 and a variable balance. After the call, which statement is correct?

in = client to server only; out = server to client only.
Worked answer: Scenario 3

C. amount is in: it travels only to the server, and any change the server makes is not sent back. newBalance is out: the client's initial value is ignored, and the server's value is returned. In Java the generated signature is:

void transfer(int amount, org.omg.CORBA.IntHolder newBalance);
// client:
IntHolder balance = new IntHolder();
account.transfer(100, balance);
System.out.println(balance.value);   // value set by the server

Note that IDL long maps to Java int (32-bit).

Scenario 4 (new): Choosing call semantics

A mobile app calls transferMoney(from, to, 500). Sometimes the network drops the reply and the app retries. Which design is correct?

A transfer is not idempotent, so blind retries could move the money twice. Duplicate detection by request ID is required.
Worked answer: Scenario 4

B. Running a transfer twice moves 1,000 instead of 500, so the operation is not idempotent and at-least-once (A) is dangerous. TCP (C) guarantees delivery only while the connection is alive; if the connection breaks after the server ran the transfer but before the reply arrived, the client still cannot know. One-way (D) gives the user no confirmation. The fix is at-most-once: the client attaches a unique request ID (today called an idempotency key), and the server remembers processed IDs and resends the stored reply for a retry.

Scenario 5 (new): Legacy CORBA on modern Java

Your team runs Java 21 and must call an existing C++ CORBA service. A colleague types idlj and gets "command not found". What is the best explanation and fix?

JEP 320 removed Java IDL and RMI-IIOP from the JDK in Java 11. External ORBs still work.
Worked answer: Scenario 5

B. Since Java 11 the JDK has no org.omg packages, idlj, orbd or rmic (rmic itself was removed in Java 15), so D also fails. Two practical options: (1) add a standalone ORB such as JacORB or the Eclipse GlassFish ORB as a dependency and use its IDL compiler; (2) longer term, write a thin adapter next to the C++ service that exposes it through gRPC or REST, so new clients do not depend on CORBA at all.

Protocols, references and naming

Q1How are GIOP and IIOP related?

GIOP defines the message formats in the abstract; IIOP is GIOP carried over TCP/IP. "Java-only" is tempting, but that describes JRMP, not GIOP; both GIOP and IIOP are language-neutral.

Q2A client receives the string IOR:000000000000001… by e-mail. What can it do with it?

An IOR encodes the host, port and object key, so the ORB can turn it back into an object reference. IDL compilation is tempting, but that produces stubs from interface definitions; an IOR identifies one object, not an interface.

Q3The Naming Service lets clients find an object by a human-readable name instead of handling a raw IOR string.

True. The Naming Service (CosNaming) maps names such as "Hello" to object references, which clients get with resolve_str. It is tempting to think the client still needs the IOR, but the service hands it over behind the scenes.

3Matching: CORBA Components

Choose the term that matches each description. Descriptions 1 to 4 are the original set; 5 and 6 are new. Each term is used once.

[1] Routes requests and acts as a switch between objects.
[2] Allows servers to receive requests without pre-compiled skeletons (runtime binding).
[3] Stores available object interfaces (types, methods) for dynamic lookup.
[4] Mediates ORB and servants, handles activation & reference generation.
[5] Lets a client build and send a request at run time without a stub.
[6] Knows how to locate and start a server process on demand.
Pick a term for every description.
Worked answer: matching

[1] ORB Core · [2] DSI · [3] Interface Repository · [4] POA · [5] DII · [6] Implementation Repository.

The usual traps: DII (client side) vs DSI (server side), and Interface Repository (describes types) vs Implementation Repository (describes how to start servers).

CORBA components

Q1A server object sits idle and its process is not running. A client call arrives. Which repository knows how to locate and start that server?

The Implementation Repository describes how to start servers on demand. The Interface Repository is the tempting wrong answer: it describes interface types (operations and parameters), not how to launch processes.

Q2DSI is the client-side way to build requests at run time without a stub.

False. That is DII. DSI (Dynamic Skeleton Interface) is the server-side counterpart: it lets a server receive requests without a pre-compiled skeleton.

Q3Which component handles servant activation and generates object references on the server?

The POA mediates between the ORB and the servants: it activates them and creates their references. The ORB core is tempting, but its job is routing requests between objects, not managing servants.

4IDL Coding Challenge

Write an IDL interface for a TemperatureSensor that:

  • Has a readonly attribute location (string).
  • Has an operation getTemp() returning a float.
  • May raise a user exception SensorError (with no extra data).
The checker looks for the five required parts. It is a pattern check, not a full IDL compiler.
Worked answer: IDL challenge 
module Sensors {
    exception SensorError {};                 // user exception, no data members
    interface TemperatureSensor {
        readonly attribute string location;    // getter only
        float getTemp() raises (SensorError);
    };
};

Points to check: the exception is declared before it is used; raises lists it in brackets; every declaration ends with a semicolon, including the closing }; of the interface and module. In Java, location becomes String location() and getTemp() becomes float getTemp() throws SensorError.

IDL attributes and exceptions

Q1Where must exception SensorError {}; appear in the IDL file?

IDL names must be declared before they are used, so the exception comes before the interface that raises it. "Anywhere" is tempting if you are used to Java, where declaration order inside a class does not matter.

Q2Which line correctly declares that getTemp may throw SensorError?

IDL uses the keyword raises with the exception names in brackets. throws is the Java keyword, and raises without brackets is a syntax error.

Q3In Java, readonly attribute string location; becomes a method called getLocation().

False. The Java mapping uses the attribute name with no get/set prefix, so it becomes String location(). It is tempting to answer True because JavaBeans getters use get, but the IDL mapping does not.

5More Exercises

Short written exercises in the style of exam questions. Write your answer on paper first.

Exercise 5.1: Order the steps

Put these CORBA run-time steps in the correct order: (a) ORB delivers the request to the server object; (b) client invokes a method on the object reference; (c) server object starts and registers with the ORB; (d) server returns the result through the ORB; (e) client finds the object reference via the ORB/Naming Service.

Worked answer 5.1

c → e → b → a → d. The server must exist and be registered before anyone can find it; the client must hold a reference before it can call; the request travels (stub → ORB → IIOP → ORB → POA → skeleton → servant) and the reply comes back the same way.

Exercise 5.2: Client side or server side?

Classify each: IDL stub, IDL skeleton, DII, DSI, POA, Holder class used for an out parameter.

Worked answer 5.2
Client sideServer side
IDL stub, DII, Holder class (the client creates it and reads .value after the call)IDL skeleton, DSI, POA

Holders are generated for both sides, since the servant also receives a holder to fill in, but the question is usually asked from the client's view.

Exercise 5.3: IDL to Java mapping

Give the Java signatures generated for this IDL:

interface Counter {
    attribute long step;
    long long next(inout short calls);
};
Worked answer 5.3 
int  step();                                   // getter  (IDL long → int)
void step(int newStep);                        // setter  (not readonly, so a setter exists)
long next(org.omg.CORBA.ShortHolder calls);  // long long → long; inout → Holder

The two classic traps: IDL long is Java int, and IDL long long is Java long. Java accessors use the attribute name with no get/set prefix.

Exercise 5.4: Find the bugs

This Java IDL client does not work. Find three problems.

ORB orb = new ORB();
NamingContextExt ns = (NamingContextExt) orb.resolve_initial_references("NameService");
Hello h = (Hello) ns.resolve_str("Hello");
System.out.println(h.sayHello());
Worked answer 5.4
  1. ORB is abstract and is never created with new; use ORB.init(args, null), which also reads -ORBInitialHost/-ORBInitialPort from the command line.
  2. The naming reference must be converted with NamingContextExtHelper.narrow(...), not a Java cast.
  3. Same for the object: HelloHelper.narrow(ns.resolve_str("Hello")). A plain cast throws ClassCastException because the ORB returns a generic org.omg.CORBA.Object.

Bonus: on Java 11 or later the code will not even compile without an external ORB, because org.omg.* was removed.

Exercise 5.5: Java IDL vs RMI-IIOP

In two or three sentences, explain the difference between Java IDL and RMI-IIOP, and say when each would have been chosen.

Worked answer 5.5

Java IDL is IDL-first: you start from an OMG IDL file (often an existing one from a C++ system) and generate Java stubs and skeletons with idlj. RMI-IIOP is Java-first: you write ordinary RMI interfaces in Java and run them over IIOP (with rmic -iiop), optionally exporting IDL for other languages. Choose Java IDL to join an existing CORBA system; choose RMI-IIOP when Java developers own the service but CORBA or EJB clients must reach it. Both were removed in Java 11.

Exercise 5.6: Translate IDL to Protocol Buffers

Rewrite the TemperatureSensor interface from Exercise 4 as a gRPC service.

Worked answer 5.6 
syntax = "proto3";
package sensors;

service TemperatureSensor {
  rpc GetLocation (Empty) returns (LocationReply);   // readonly attribute → getter RPC
  rpc GetTemp     (Empty) returns (TempReply);
}
message Empty {}
message LocationReply { string location = 1; }
message TempReply     { float celsius = 1; }

gRPC has no user exceptions: SensorError becomes an error status such as UNAVAILABLE returned by GetTemp. Many teams use the standard google.protobuf.Empty type instead of defining their own.

Exercise 5.7: System or user exception?

Classify: COMM_FAILURE, InsufficientFunds, OBJECT_NOT_EXIST, SensorError, BAD_PARAM.

Worked answer 5.7

System (raised by the ORB, possible on any operation, unchecked in Java): COMM_FAILURE, OBJECT_NOT_EXIST, BAD_PARAM. User (declared in IDL, listed in raises, checked in Java): InsufficientFunds, SensorError.

6Mixed Quiz: RPC, RMI and CORBA

Mixed quiz

Q1Which part of IIOP's name tells you it runs over TCP/IP?

GIOP is the abstract protocol; IIOP is GIOP specialised for TCP/IP, hence "Internet" Inter-ORB Protocol.

Q2Which object adapter replaced the BOA in CORBA 2.2?

The Portable Object Adapter fixed the BOA's under-specification, making server code portable between ORB vendors.

Q3What does HelloHelper.narrow(obj) do?

narrow checks the remote type and returns a properly typed stub. A plain Java cast would fail.

Q4True or false: a readonly attribute in IDL generates both a getter and a setter in Java.

Only a getter. A normal (non-readonly) attribute gets both.

Q5IDL long maps to which Java type?

IDL long is 32-bit, so it maps to Java int. IDL long long maps to Java long.

Q6Which call semantics is safe for getBalance() with simple retries?

Reading a balance is idempotent, so repeating it is harmless and retries are fine.

Q7What is the default port of the Java RMI registry?

rmiregistry uses 1099 by default. Port 111 is Sun RPC's port mapper; 1050 is just a common choice for -ORBInitialPort in Java IDL labs.

Q8Which JDK change removed org.omg.CORBA, idlj and javax.rmi?

JEP 320 removed the Java EE and CORBA modules in Java 11. JEP 407 (Java 17) removed RMI Activation; JEP 411 deprecated the Security Manager.

Q9Which pair are the dynamic counterparts of stubs and skeletons?

DII replaces the stub on the client; DSI replaces the skeleton on the server.

Q10Which modern technology is the closest equivalent of CORBA's IDL + stubs + binary encoding?

gRPC uses an IDL (.proto), generates stubs for many languages and encodes messages in binary, all carried over HTTP/2.

Key points to remember

  • IIOP = CORBA's protocol over TCP/IP; the POA (object adapter) connects servants to the ORB; the ORB core routes requests.
  • Static: stub (client) + skeleton (server). Dynamic: DII (client) + DSI (server), with the Interface Repository describing types.
  • in → client to server, out → server to client, inout → both; out/inout map to Holder classes in Java.
  • Use Helper.narrow(), never a plain cast, on CORBA references.
  • Non-idempotent operations need at-most-once semantics (duplicate detection).
  • Java IDL and RMI-IIOP were removed in Java 11; use an external ORB for legacy systems and gRPC or REST for new ones.
